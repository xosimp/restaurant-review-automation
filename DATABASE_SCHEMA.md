# Database Schema — Cavnar AI

Single SQLite database (`reviews.db`), WAL mode, on a Railway persistent volume in production. Schema lives across `models.py` (`init_db()` + `ensure_columns()` + a dozen `init_*()` helpers for tables that didn't exist from day one), `auth.py` (`init_auth()`), `push.py`, `webhooks.py`, `guest_marketing.py`, `sales_audits.py`, `ops.py` (`init_ops`), `ai_utils.py` (`init_ai_ops`), `billing_jobs.py` (`init_billing`), `admin_events.py` (`init_admin_events`), `admin_ops.py` (`init_admin_ops`), `offboarding.py` (`init_offboarding`) — all called from `init_db` — plus `platform_monitor.init_platform_tables` and `provider_health.init_provider_health`, which `hosted_dashboard.py`'s boot block calls, and a few single-table owners (`milestones`, `home_brief`). All of it runs at boot. There is no schema version table — schema migrations are additive `ALTER TABLE ADD COLUMN` statements guarded by `try/except`. One-time DATA migrations are recorded by name in `data_migrations` so they never run twice (the first, 9/29/26: `email_log.sent_at` from Chicago wall time to UTC). **257 table names** after the memory round (9/29/26; 212 before it); the count is the `CREATE TABLE IF NOT EXISTS` names across non-test Python (`python3 scripts/repo_inventory.py`), and this file lists them by area rather than re-deriving each one. The tables the admin-console fix round added (9/29/26) are in *Operations, audit and billing ledgers* below; the memory round's 45 are in the area each belongs to (*People and shifts*, *Ask Cavnar*, *Recommendations*, *AI reads*, *Events and public history*, *The change log and what outlives a prune*, *Intelligence engine* and the rest); *Retention* says how long each ledger is kept, and which are kept forever.

`restaurant_id` is the tenant boundary on essentially every table below it — every read must filter by it from the authenticated session, never from client-supplied input.

## Core identity

### `restaurants` (models.py)
The tenant row (243 columns on 9/29/26). Everything else hangs off `restaurants.id`. The list below is by purpose, not exhaustive; the authoritative column set is the four touch points — the `Restaurant` dataclass, the migration lists (`init_db()`'s ALTERs and `ensure_columns()`), `update_restaurant().allowed`, and `get_restaurant()`'s hydration — and a column missing from any one of them is a bug, not a documentation gap. Not itemised here: the per-type alert channel matrix (`alert_*`, `al_<type>_email|sms|push`, `alert_quiet_*`, `alert_max_per_day`), every POS/OAuth credential column (`toast_*`, `square_*`, `clover_*`, `rpower_*`, `gmb_*`, `ig_*`/`fb_*` — encrypted at rest by `credentials.py`), the 2FA columns, the automation switches (`auto_*`, `send_delay_minutes`, `weekly_plan_enabled`), `category` (the intelligence cohort), `organization_id`, `row_version`, `paused_until`, `deletion_requested_at`.
- **Identity/contact**: `name`, `owner_email`, `owner_name`, `owner_phone`, `google_place_id`, `yelp_business_id`
- **Brand voice**: `voice_notes`, `neighborhood`, `vibe`, `known_for`, `sign_off_name`, `never_say`
- **Revenue target**: `monthly_revenue_target` is the one stored figure (0 = none). A weekly figure (`weekly_revenue_target`, accepted by `models.update_restaurant` and every settings route) is stored as weekly × `metrics.WEEKS_PER_MONTH` (52/12) and read back with `models.weekly_revenue_target(r)`, to the cent — there is no weekly column (9/28/26).
- **Labor settings**: `hourly_rate`, `labor_target_pct`, `week_start_day` (0=Mon, for FLSA overtime on the employer's own workweek), scheduling JSON blobs (`role_rates_json`, `close_times_json`, `role_close_buffer_json`, `role_minimums_json`, `role_strength_json`, `shift_leader_rules_json`, `quality_weights_json`), `sched_notes`; `person_rates_json` (`{"Kailey Gordon": 17.5}`, 9/30/26 — `models.person_rates`): one person's own hourly rate where it differs from their role's; a shift costs the POS's pay for the punch first, then this, then the person's pay on their other punches (`labor.rate_book`: RPOWER sends $0 on many PM and bartender punches), then the role's rate, then the median of the role's people, then the blended rate (`labor._shift_rate`; a drafted week is priced the same way through `labor.person_rate_book` → `schedule_economics.priced_cost`); a pay field (`PAY_FIELDS`), so a change re-costs the history. `salaried_staff_json` (`[{name, annual}]`, owner, 9/28/26 — `models.salaried_staff`): salaried people are costed by salary, never by the hour — `labor._analyse_for_restaurant` drops their punches from hourly labor (and so from `labor_daily_history`), and `labor.salaried_summary` / `dsr.access._live_salaries` put annual ÷ 52 ÷ trading days a week (`models.open_days_per_week`, from `open_times_json`/`close_times_json`, 7 when unset) on each day with sales, **inside** the owner's labor % since 9/30/26 (the target judges the all-in figure; `labor_daily_history` stays hourly and the share is added on read), owner-only (`dsr.access.OWNER_ONLY_PREFIXES` carries `salaried`; `models.viewer_sees_salaries`). The schedule's hours budget judges hourly labor only
- **Location grouping**: `location_group`, `location_name` (multi-location clients)
- **Food cost**: `inventory_frequency`, `delivery_days`, `inventory_notes`, `food_cost_target`, `inventory_updated_at` (never written by anything — every freshness reading uses `MAX(ingredients.last_recount_at)` instead, as `ordering.count_freshness` does. Candidate for future cleanup after additional verification; do not delete.)
- **Billing/contract**: `stripe_customer_id`, `docusign_envelope_id`, `contract_status` (pending / sent / delivered / signed / declined / voided — the last three from DocuSign Connect, written only for the restaurant's CURRENT envelope and never over `signed`, `webhook_routes._docusign_state`), `contract_signed_at` (UTC, set once when the envelope completes), `billing_status` (trial / active / past_due / paused / churned / canceled / internal — `models.in_service` is false for paused, churned and canceled; `models.is_paying` is true for active and past_due only), `pause_reason` (self / dispute / refund / admin, `models.PAUSE_REASONS`: a dispute holds the whole group, a full refund only the location that paid; `models.pause_lock` and `billing_hold` read it — only a `self` pause is the owner's to resume, the rest only an admin's lift-hold clears, and a hold survives churn; a NULL reason on a paused row with no `paused_until` reads as an admin lock), `paused_until`, `converted_at` (UTC, set once at the first paid checkout, else the first paid invoice with money in it). `contract_signed_at` and `converted_at` were backfilled at boot from the event ledger (`billing_jobs._backfill_lifecycle_stamps`, NULLs only). Every change to `billing_status`, `pause_reason`, `paused_until`, `contract_status`, `stripe_customer_id`, `service_tier` or a `module_*` flag writes a `billing_status_history` row inside `update_restaurant`'s own transaction (`models.BILLING_HISTORY_FIELDS`), attributed by `models.billing_context` (else the request's endpoint and signed-in user, else `system`)
- **Access control**: `service_tier` (trial/starter_reviews/starter_labor/starter_inventory/starter_marketing/full) auto-sets `module_reviews`/`module_labor`/`module_inventory`/`module_marketing` booleans, which can be overridden per client
- **Integrations**: `gmb_revoked_at` (UTC, stamped by `gmb.get_valid_token` when Google revokes the grant; the console raises it as a failing integration)
- **Ops**: `is_demo` (seed data may be reset — never true for a real client; also the only thing that lets "demo" Toast credentials load the synthetic feed, `toast.demo_allowed`), `demo_cleared_at` (UTC, stamped when admin turns `is_demo` off, with `learning_since`: the seeded rows stay — never hard-deleted, the seed's daily labor rows marked `source='seed'` — and nothing recorded before `learning_since` teaches any learner, its own or the platform's — `models.learning_eligible(r, since=)` / `learning_rows_sql`), `internal_notes` (Will-only), `pos_system`, `digest_day`/`digest_enabled`, `last_fetched_at`, `last_active_tab`, `last_activity`
- **Misc computed/cached**: `latitude`/`longitude`/`weather_cache_json`/`weather_cached_at` (geocoded once, cached forecast), `email_theme`, `marketing_emails_opt_out`, `timezone`

### `users` / `sessions` / `login_history` (auth.py)
- `users`: one row per login, `restaurant_id` FK, `username`/`email` unique, `password_hash`, `is_admin`, `is_active`, `role` ∈ `permissions.py`'s roles — `owner` (multi-location), `client` (the primary login and DB default; shown as Co-owner), `manager`, `member` (Teammate), `employee` (PIN identity, staff portal only), `support` (Cavnar staff, read-only admin). `two_fa_enabled` / `two_fa_method` (email | sms; fix round 9/29/26 — | app, an authenticator app, R10 9/29/26: its secret is in `user_totp`, never on this row) are an INTERNAL login's own second factor (admin and support): the restaurant-wide 2FA switch never applies to one, and it never uses the restaurant's backup codes (`user_backup_codes` below). `create_user` enforces the password policy (8 or more characters, not in a known breach) unless the secret is generated (`generated=True`).
- `sessions`: `token` PK (the SHA-256 of the bearer), `expires_at` and `last_active` in SQLite's `YYYY-MM-DD HH:MM:SS` UTC form and compared through `datetime()` — rows written in ISO form (`…T…+00:00`) outlived their expiry to the end of that UTC day as text, and `auth.normalize_session_rows` rewrites them at boot; the nightly prune compares `expires_at` as text too, so it must stay in this form. `ip_address`, `user_agent`, `device_type` (`web`, `ios`, `staff_pin`, `admin-view-as`), `active_restaurant_id`, and since 9/29/26 `two_factor_at` (this session passed a second factor), `reauth_at` (the last password step-up, read by `auth.recent_auth_required` — 15 minutes), `acting_admin_id` (on a view-as session, the admin behind it) and `read_only` (a view-as a support login opened; on the row, so it fails closed). Lifetimes: 30 days absolute with an 8-hour inactivity rule on the web (iOS and staff PIN sessions are exempt from the inactivity rule); staff PIN sessions 14 hours; an internal login's session 12 hours absolute (`auth.ADMIN_SESSION_HOURS`, old rows capped at boot); a view-as session 2 hours absolute from when it was opened, never extended (`auth.VIEW_AS_HOURS`). Hard-deleted on revoke and device-dedup; an expired row goes a day after `expires_at` (`ops._RETENTION_DAYS`).
- `login_history`: append-only (a row is never edited) — independent of `sessions`, this is what the Account "sign-in activity" view reads, so a login stays visible regardless of what later happens to the session it produced. Kept 90 days, pruned nightly by the retention registry (`login_history` on `created_at`, floor 60) and at every boot by `auth.prune_login_history`, which reads the SAME window from the registry (`ops.retention_days`) — never a number of its own — and prunes nothing when that window is off or refused. Before rows go, each login's month is summarised into `engagement_monthly` (`history_rollups.roll_engagement`). `idx_login_history_created` (`auth.AUTH_INDEXES`, made at boot with the table) serves both deletes — `idx_login_history_user` leads with `user_id` and serves the Account view.
- `trusted_devices`: "remember this device 30 days" for 2FA, one row per device (superseded a single-column approach that only held the last device).
- `two_fa_backup_codes`: hashed, single-use fallback codes generated at 2FA setup.
- `login_attempts` (models.py, used by `security.py`): durable login throttling. `kind` is `account` (a failure against a username), `ip`, `anon` (an attempt naming no account), `account_ip` (an account and address pair — internal logins are locked per address, so a stranger's guesses cannot lock the admin out from everywhere) and `reauth` (a wrong step-up password: five end the session). Rows older than two days are pruned daily (`scheduler.run_prune_login_attempts`).
- `user_backup_codes` (auth.py, 9/29/26): an internal login's own hashed, single-use backup codes (`user_id`, `code_hash`, `used_at`). A restaurant's `two_fa_backup_codes` never pass an admin and his never pass them.
- `user_passkeys` (auth.py `AUTH_SCHEMA`, owner, 9/30/26 — `passkeys.py`): one row per passkey a login added in Account → Security — `user_id`, `credential_id` (the authenticator's id, base64url, unique), `public_key` (the COSE public key it signs with — public, so kept in off-site backups: `KEEP_COLUMNS`), `sign_count` (only ever rises; a lower one is a cloned key and refused), `transports`, `aaguid`, `backed_up`, `name` (the device kind it was added on), `created_at`, `last_used_at`. Removed one at a time by its login. Bounded at `passkeys.MAX_PASSKEYS_PER_LOGIN` (10) per login, so no retention entry.
- `passkey_challenges` (auth.py `AUTH_SCHEMA`, 9/30/26): one WebAuthn challenge per ceremony — `challenge` (PK, base64url), `purpose` (`register` | `login`), `user_id` (a registration's login; NULL for a sign-in, where the passkey names the login), `created_at`. Single use (deleted when answered), and every row older than `passkeys.PASSKEY_CHALLENGE_MINUTES` (5) is deleted whenever a new one is issued.
- `user_totp` (auth.py `AUTH_SCHEMA`, R10 9/29/26): an internal login's authenticator-app (TOTP, RFC 6238) state, one row per login at most — `user_id` (PK), `secret` (the active secret), `pending_secret` + `pending_expires_at` (the secret a QR code was just shown for; dead after 15 minutes, active only once a code from the app confirms it), `last_step` (the last 30-second step a code was accepted for — each step passes once), `activated_at`, `updated_at`. Both secrets are Fernet ciphertext under `CREDENTIAL_KEY` (`enc:v1:`; enrolment is refused without a working key, and a value that is not ciphertext is never trusted). Its own table so the secret never rides on the `users` row every session lookup loads. Emptied by `auth.clear_user_two_factor` (disable, admin reset, break-glass) and `auth.clear_user_totp` (a switch back to email or SMS); emptied from every off-site backup (`SCRUB_TABLES`). Bounded by the number of internal logins, so no retention entry.
- `users.policy_notice_dismissed` (TEXT, 9/29/26): the Privacy Policy / Terms change (`policy_notice.POLICY_UPDATED_ON`, ISO) this login dismissed the 30-day dashboard notice for — per login, so a later change (a new date) shows again. One value per row; kept with the login.
- `organizations` + `restaurants.organization_id`: the owner-level grouping above a location group (backfilled from `location_group` + `owner_email`).
- `preferences` (`preferences.py`, memory audit 9/29/26) — who a setting belongs to. PK (`scope`, `scope_id`, `key`), `value` JSON, `set_by`, `set_at`. `scope` `org` (`scope_id` = the organisation key): a group owner's default for every location, written by `preferences.apply_to_all_locations` (only `preferences.ORG_KEYS` — voice, never-say, briefing, quiet hours, the daily cap and the alert matrix; never auto-approve), which also writes the value onto every location's own `restaurants` column, so a location's setting stays where every reader already reads it; `scope` `login` (`scope_id` = `"<user_id>:<restaurant_id>"`): a login's own notification choices (`preferences.LOGIN_KEYS` — push on/off, muted alert types, their own quiet hours), BOUNDED by the location's — they can only take alerts off their own phone, never turn on a type the owner turned off; `preferences.UNMUTABLE_TYPES` (health, issue, issue_escalated, coverage, critical_low) cannot be muted. `push.fire_push` applies them. Resolution: login → location → organisation → product default. Bounded by its keys, kept until changed. It has no `restaurant_id` column (the scope id carries it), so `delete_restaurant` does not reach its rows.

### Staff portal (auth.py `AUTH_SCHEMA`)
- `memberships`: an employee's identity at a restaurant (name, job role, PIN hash, `pos_id`), the row the staff portal signs in against. `schedule_texts_at` (TEXT, NULL = off) is the employee's own "text me when my schedule is posted", set only from their unchecked-by-default box in the staff portal; the signup consent covers the one-time code alone. A published week is texted only when it is set and `TWILIO_STAFF_MESSAGING_SERVICE_SID` is configured (`people.reach`, Friction #17).
- `membership_pin_attempts`, `portal_attempts`, `portal_nonces`: PIN lockout, portal throttling, one-time nonces. A lockout lasts 15 min × 2^(lockouts in the last day), capped at 24 h (`lockout_count`, `last_locked_at`); `portal_attempts.ok=1` marks a hit that ended well, which counts toward the 300-per-5-min ceiling but not the 30 failures (SEC-18/19).
- `two_fa_challenges`: one row per 2FA sign-in attempt (`purpose='login'`) or per login's "Send test code" (`'setup'`); the code and the pending secret are keyed hashes only, single-use, 10 minutes. `restaurants.two_fa_code/two_fa_pending/two_fa_expires` are no longer read and are blanked at boot (SEC-20/39).
- `view_as_sessions`: who opened each admin view-as session (by session-token hash) and whether it is read-only (opened by support; SEC-12). Since 9/29/26 the session row itself carries `acting_admin_id` and `read_only`, so this table is history only (candidate for future cleanup after additional verification); `ai_utils`' attribution reads `flask.g`'s acting admin first, then the session row's `acting_admin_id`, and `opened_by` only when that is NULL. Its rows older than 2 days are deleted whenever a view-as opens (`auth.record_view_as_session`) — deliberately not in the retention registry (one pruner per table).
- `staff_portal_tokens`: the per-restaurant portal links; `staff_signups`: the claim-your-name flow.
- `permission_grants`, `login_prefs`: see *Strategic foundations* below.

## Reviews

### `reviews` (models.py)
`restaurant_id` + `platform` (google/yelp/csv/manual) + `external_id` — **unique on `(restaurant_id, platform, external_id)`**, deliberately including `restaurant_id` in the key (a global-unique key let two tenants sharing a `google_place_id` silently steal each other's reviews). Carries the raw review (`author`, `rating` 1–5, `text`, `review_date`, `fetched_at`), Claude's analysis (`sentiment`, `categories` JSON, `summary`, `urgency`), and the response workflow (`draft_response`, `response_status`: pending/drafted/approved/posted/skipped, `approved_at`, `posted_at`, `draft_edited`, `regenerate_count`, `deleted_at`). `response_action` is approved_as_is / edited / regenerated / **auto_approved** / **bulk_approved** — `auto_approved` is the auto-approve rule's own approval and `bulk_approved` a publish-many (approve-all, Home's "Publish N replies") of an unedited, unregenerated draft; neither is counted by `auto_approve_trust` or used as a style example, and a regenerated draft counts against trust like an edit. A bulk publish only ever posts `models.BULK_PUBLISHABLE_SQL`: recent (`REPLY_OWED_MAX_AGE_DAYS`), not urgent, not `draft_needs_review`; `update_draft` never overwrites an approved or posted reply. `original_draft` is the model's text as it stood before the owner's first edit (kept, never overwritten; reset by a regenerate). At a person's approval (never the auto-approve rule's or a bulk publish's) `models.record_reply_edit` compares it with the approved reply (`reply_edits.compare`) and stores `edit_distance` (word edit distance, 0–1), `edit_category` (unchanged / light / heavy / rewrite) and `edit_signals` (JSON, a closed vocabulary: shortened, lengthened, removed/added exclamations, apology, invitation) — read by the drafter's few-shot order (an edited reply first) and its OWNER'S EDITS note. `skipped_at` dates a skip, which counts against the band's trust.

Who approved a reply (memory audit 9/29/26, `ensure_columns`): `approved_by` (the login — for a view-as session, the admin behind it), `approved_role` (`permissions.answer_authority`: principal / delegate / admin, or `rule` for the auto-approve rule) and `approved_via` (normal / view_as / rule), set by the statement that approves it and cleared with it; NULL on replies approved before the capture. `draft_edited_via` is `view_as` once an admin or support login acting through view-as changed the draft since the model wrote it, else `normal`; NULL until a person edits; reset by each fresh model draft. `models.reply_voice_sql` is the one predicate for "approved in the owner's voice": never `approved_via` or `draft_edited_via` `view_as`; the account holder (`approved_role` principal) or a delegate holding the `reviews.voice` grant — and, for auto-approve trust (`trust=True`), the account holder alone; a NULL `approved_role` (before the capture) still counts, behind every known one. The style examples, the OWNER'S EDITS note and auto-approve trust read only through it, banded by star rating (`models.REPLY_BANDS` 1-2 / 3 / 4-5; a short band borrows only from the 3-star band beside it). `idx_reviews_gbp_name` (partial, reviews with a `review_name`) serves `intelligence.provenance.google_connected_ids`.

- `reply_draft_rejections` (9/29/26) — a reply draft the owner turned down by asking for another (a regenerate, or Ask rewriting it): `review_id`, `rating`, `draft_hash`, `words`, `signals` (the closed vocabulary of `reply_edits.draft_signals`), `how`, `user_id`, `authority`. **Never the draft's text.** Kept 90 days (registry, floor 90) for the drafter's edit note (`models.get_reply_rejection_signals`).
- `review_retags` (9/29/26) — an owner's or manager's correction to how a review was tagged (`field` category / sentiment / severity / dish, `before_json`, `after_json`, `user_id`, `authority`; `review_signals.retag`). The review row takes the correction; this keeps what it was and who changed it, and the analyser reads the recent ones as this restaurant's examples. One row per changed field; kept forever.

### `review_requests`
Outbound "please leave us a review" asks — tracks `customer_phone`, send state. `review_id` / `matched_at` (9/29/26): the review a request produced, matched by the guest's name when reviews are fetched (`review_signals.match_review_requests`); NULL until matched.

### `response_templates`
Saved canned-response templates per restaurant.

## Labor / Scheduling

### `schedule_history`
One row per generated schedule: `week_start`/`week_end`, `hours_scheduled`/`hours_budget`/`labor_target`, the full `schedule_csv`, `summary_json`, and (added later) `quality_json` — the Shift Quality Engine's full evaluation for that schedule — plus `edited_at`/`edited_by` when a manager hand-edits a published schedule. `published_at`/`published_by` mark the moment it went to staff: the staff portal, the payroll-week hours check and `schedule_publish_trust` read only rows with `published_at` set — a draft is never "the schedule". `review_json` is the rule sweep (`schedule_rules.summarize`), `generation_seconds` the model time, `weather_json` the forecast the draft saw, `economics_json` what it was written against (`projected_revenue` and its source, `labor_budget_dollars`, `daily_target_hours`, `demand_data_through` — the Schedule Studio's labor % and savings for a reopened week, 9/26/26).

### `schedule_versions`
Every state a schedule has been in — `(history_id, version)` unique, `reason` in `generated | edited | fixes | published`, the CSV, `quality_json`, `diff_json` against the previous version, `saved_by`. `schedule_versions.learned_patterns` reads the recurring edits back into the next draft. `saved_authority` (9/29/26) is `permissions.answer_authority` of the save; `admin` for an admin's hand whoever the caller named. Invariant: an admin's save is never the manager's word — `schedule_versions.LEARNABLE_SQL` leaves out a version with `saved_authority` `admin` or `saved_by` `support:…`, and `NOT_SUPPORT_TOUCHED_SQL` leaves out every week one of those touched, for every learner.

`schedule_standing_patterns` (`schedule_intel.py`, 9/29/26) — what the draft has learned and keeps: one row per `(restaurant_id, pattern_key)` UNIQUE — `kind` (moved_off / moved_on / retime_start and the live window's other kinds), `employee`, `role`, `day`, `daypart`, `time`, `text`, `editors`, `first_learned`, `last_confirmed`, `times_applied`, `times_overridden`, `checked_through` (the last published week read), `status` active / retired / ruled, `rule_note`, `ruled_by`. A pattern the live window learns (and the owner has not dismissed) becomes a row; every published week that keeps it confirms it; it retires only when a manager's own edits reverse it `STANDING_RETIRE_AFTER` (2) times — never because nobody had to make the correction again. "Make it a rule" writes it into the person's own availability (`staff_settings`) and marks it `ruled`. `refresh_standing_patterns` skips a restaurant that may not teach (`models.learning_eligible`). Kept forever. Re-audit 9/29/26 (boot ALTERs in `init_schedule_intel`): `person_id`; `detail` (JSON: `was_role`, `delta`, `names`); `times_confirmed` (weeks the manager's own hand kept it — the draft had not carried it, or they edited that slot and kept it; `times_applied` also counts weeks the draft merely carried it, and the weeks that taught it count as neither — reading starts after the newest of them); `last_overridden` (two reversals retire it only inside `STANDING_OVERRIDE_WINDOW_DAYS`, 56, of each other); `retired_at` / `retired_week` (the published week that retired it — the live window's older copy is held back from the draft and cannot revive it; only evidence newer than that week brings it back, and the live pattern that is merely the reversal of a retired one is not stored); `dormant_at` with status `dormant` (a person pattern whose person has had no shift for `people.MEMORY_GONE_DAYS` against the restaurant's own newest shift, or is inactive — out of the draft and the memory lines, woken when they return; a week the person did not work does not test their pattern). Names are canonicalised through `people.canonical_names`, and the table is in `people.NAME_STORES` (a rename or merge re-keys it; two rows on one key fold). Headcount rows are confirmed/retired against the draft and, while active, feed `schedule_learning.learned_headcount_adjustments` after the live window forgets them.

### `staff_settings` / `staff_pairs`
The roster's facts: `active` (a deactivated person is never scheduled, whatever the shift history says), `employment_type` (full/part), `min_hours`/`max_hours`, `daypart_availability` (JSON weekday → any/morning/night/off), `is_minor`. Keyed by `(restaurant_id, employee_name)` like every staff table. `staff_pairs` is `prefer`/`avoid` between two names, stored once whichever way round it was typed.

### `demand_signals`
Owner-entered facts about specific dates: `kind` event, reservations or post (a scheduled post since the re-audit fix round, 9/29/26, CROSSMODULE-7 — never an event: no `event_memory` flag, no baseline exclusion, never "assumed busier", no trim suppression; its lift only where the marketing module measured posts like it; the boot migration `demand_signals.migrate_post_signals` re-kinds old rows and removes a cancelled or failed post's signal, and `remove_by_ref` does it live on cancel and on a publish that failed with nothing sent), `label`, `covers`, `lift_pct`, `source` (manual, csv, or a future sync — and since 9/29/26 `campaign` / `post`, a marketing signal `demand_signals.record_marketing` writes, its lift measured or NULL). ### `labor_history` / `labor_daily_history`
Per-period and per-day labor % / sales / hours — the source for the Labor ribbon chart and Ask Cavnar's "how is today going" answer.

Invariants (CA3 F3):
- `labor_daily_history.sales` is the day's NET sales by business date (`pos.py`'s sales contract), or **NULL when the day has no figure** — never 0. `labor_pct` is NULL whenever `sales` is. `models.save_labor_daily_history` writes NULL for a missing figure and never lets a NULL overwrite a figure already on file for that date (the day keeps its sales, re-costed against the new labor). Readers filter `sales IS NOT NULL AND sales > 0` — rows from before this rule carry 0 for a missing figure, and the one-time boot backfill `models.backfill_missing_sales_null` (idempotent; data only) rewrites those to NULL when labor was on the books and no POS evidence of a sale exists that date (`dsr_metrics sales.net`, `pos_intraday`, `menu_item_sales`). A $0 row with POS evidence is left for a person.
- `labor_history` holds a period only when it had sales (`save_labor_snapshot` refuses `total_sales <= 0`), and `get_labor_history` never returns a legacy `total_sales = 0` row — a 0.0% "previous upload" is not a period. The labor alert (`notify.check_daily_alerts`) also needs the period to be at least `LABOR_ALERT_MIN_PERIOD_DAYS` (7) long.
- Provenance (Data Freshness fix round, DH1-9 / DH2-3): `labor_daily_history.source` (the writer — a provider name for a POS pull), `provider`, `synced_at` (UTC) and `final` (boot ALTERs). A POS pull (`pos.save_synced_shifts` → `save_labor_daily_history(provenance=)`) stamps the days inside its window; a day past `pos.complete_through` — the last business day that had ENDED when it was read (its close from the restaurant's hours, else the 5am boundary) — is `final=0`, provisional, until a later pull re-reads it whole. NULL (older rows, uploads) reads as final. `data_freshness` dates `pos`, `sales` and archive-dated `labor` by final days only (`COALESCE(final, 1) = 1`), so "Sales through" always names a whole day. Days outside the pulled window keep their provenance.
- Learners read final days through ONE predicate (memory audit 9/29/26): `canonical_facts.FINAL_SQL` / `final_sql(alias)` — `COALESCE(final, 1) != 0` AND `models.own_history_sql()`, so a converted demo's seeded day (`source='seed'`) is no final day either (a demo's own screens keep them). The ONE nightly net per business date is `canonical_facts.net_series`, each figure with its basis (`dsr_net` — the report's own net, an imported workbook, or a POS whose daily total is built the same way — or `pos_daily_total`); two figures are compared only on one basis. `labor_daily_history.sales` and `dsr_metrics` `sales.net` are both kept forever where they live and neither is in the retention registry.
- `labor_daily_history.basis` (9/29/26, `ensure_columns`): the costing basis the day was last costed on (the rates, the salaried set, where the labor came from).
- `labor_history` periods (9/29/26, `ensure_columns`): `kind` is `payroll_week` (the only kind the product writes now — calendar payroll weeks derived from `labor_daily_history` by `models.refresh_labor_periods`, kept current `LABOR_PERIOD_WEEKS` (53) back), `period` (one a caller stored explicitly) or `rolling_window` (the legacy overlapping 14/28-day windows every sync used to append — marked once at boot by `models.backfill_labor_periods` and **never read**); `basis`, `days`, `updated_at`, and `recosted_from` (the labor % the row held before a recost on a new basis). Invariant: a period is REPLACED IN PLACE (`save_labor_snapshot`) — a payroll week keyed by its start, an explicit period by start and end — never a second row for the same period, so a recost cannot read as "labor's down 1.6 points from last upload".

### `alert_contacts`
Who gets alerted and on which channels (email/SMS/push), per restaurant — separate from the login `users` table since an alert recipient need not have dashboard access.

### `device_tokens` / `push_deliveries`
APNs tokens per user/restaurant; delivery attempts and outcomes for push. `disabled_reason` PARKS a token rather than deleting it — `get_device_tokens(for_delivery=True)` skips it and the next app launch re-registers and clears it. Only Apple's own "this token is gone" (`_PERMANENT_FAILURE_REASONS`) deletes a row.

### `home_dismissals`
Attention items a user has dismissed from the Home brief, so a handled issue doesn't keep resurfacing. Every answer here is also written to rec_ledger (see Recommendations below), which is what the rest of the product reads.

**Lifecycle.** `open` → `accepted` | `completed` | `implemented` | `dismissed` | `expired` | `superseded`. A snooze keeps it open with `snoozed_until`. An episode unanswered 14 days after it was CREATED — after its chain began, for one that replaced an unanswered episode (`chain_started_at`) — closes `expired` (nightly `expire_stale`) — ignored, and in every acceptance denominator. A "Not today" on an episode the job had just expired reopens it, snoozed (B17); an open episode inside a snooze is not shown again (`present` returns None, the same rule `silenced_keys` reads). An open episode re-shown with a materially different figure (±$25 and ±25%) or target, once it is 20 hours old, closes `superseded` and a new one begins; so does every other open key of a one-live-at-a-time kind (`REPLACING_KINDS`) when a new one is shown, and every open line of an old model read when a new read is presented (`present_many(replaces=…)`) — superseded is neither answered nor ignored and counts in no rate. `implemented` is set where the change is actually made (a price applied, a supplier order sent, a reply posted to Google, a campaign or win-back sent, a post published, a schedule edited to carry the recommendation out, a week published); it moves open / expired / accepted to `implemented` and stamps `implemented_at` on any status (Done stays `completed`) — but only on an episode that is live or accepted, or ended (answered, superseded, or went stale) within `IMPLEMENT_ATTACH_DAYS` (28): a change made today is not the one a card ignored in March asked for (B15). A check-in's "yes" names its episode (`rec_id`) and always attaches. The nightly `sync_existing` carries older ledgers' answers in, links every tracker to its episode and copies its verdict and abandonment — not windowed.

**What an answer holds (memory audit, 9/29/26).** Every answer is kept in `rec_events` for good; what `rec_ledger.answer_silence(key, event, kind, reason_code, reason)` decides is only how long it silences the key everywhere (`rec_instances.silenced_until`, with `silence_rule` and `silenced_at`) — one Done or one "Pass" used to hold 3,650 days on every key. By kind and by the owner's reason (`REASON_EFFECT`: already_doing → taken, bad_timing → defer, too_costly / doesnt_fit / other → decline, dont_trust_data → distrust; a free reason that names a time — "not now", "after the holidays" — defers like bad timing):
- Done (or a "taken" reason): a situational kind (`SITUATIONAL_KINDS`, and every `diag_` / `schedule_` / `insight_` key) `SITUATIONAL_DONE_DAYS` (60) at most; a recurring kind until its next occurrence (`RECURRING_DONE_DAYS`: slow_day 6, list_idle 30, category_dip 28, post_this_week 7); any other `DONE_DAYS` (365).
- "Not for us": `DECLINE_DAYS` (365), a recurring kind a season (`RECURRING_DECLINE_DAYS`, 90). Hide: `SILENCE_DAYS["hide"]` (14). Accepted or implemented: `ACCEPTED_QUIET_DAYS` (14) while its outcome is measured.
- Bad timing: a snooze of `BAD_TIMING_DAYS` (28), in no acceptance denominator. Don't trust the data: held until the source is re-verified (`rec_distrust`), `DISTRUST_HOLD_DAYS` (90) at most.
- **Safety cycle:** `stock_low` / `critical_low` never past the current stock-out — `SAFETY_CYCLE_DAYS` (7) at most, and lifted the moment a count or a delivery of the item is recorded after the answer (`silenced_keys`).
- **Re-arming:** a situational Done that a build which evaluated the kind saw CLEAR (stamping `trigger_clear_at`) and then sees firing again is re-armed, once the answer is `REARM_MIN_DAYS` (14) old (`rec_ledger.reconsider`; `silence_rule` `rearmed`).
- **Reopening:** an answered, still-silenced key reopens as a new episode that names the one it follows (`reopened_from`, `previous_answers`) when its figure is at least `REOPEN_FACTOR` (2×) the answered one and $25 more — or, for a taken answer, its target moved; never for a bad-timing, safety or snooze silence (`reopen_change`).
- **Per-login silences:** a delegate's decline and an admin's view-as answer silence for that login only (`rec_silences`) and never train the owner's preferences.

Answers from before these rules were brought back to what each holds now, counted from the answer, once at boot (`cap_answer_silences`, `cap_recurring_silences` — on the ledger and on Home's own `home_dismissals` rows).

## Strategic foundations

- `recommendation_outcomes` — one tracked change: metric, baseline window/value/detail, `evaluate_on`, verdict. Partial unique index on (restaurant_id, source_key) while `status='tracking'`. The episode it measures holds its id in `rec_instances.tracker_id`. Rec-ROI columns (boot ALTERs after the CREATE; `outcomes.init_outcomes` fills older rows at boot): `module` (who is credited — the recommendation's own module in the value vocabulary `labor|inventory|reviews|marketing|intel|other`, not the metric's), `baseline_kind` (`prior window` | `matched weekdays` | `same weeks last year`; every row written before it was a prior window), `baseline_raw` (the before-window reading before any seasonal adjustment; `baseline_value` is what the after-window is compared against), `after_detail`, `delta_pct`, `attribution` (`none|associated|consistent|held`), `concurrent` (JSON `[{kind, label, date}]`; **NULL means never checked** — a row evaluated before it existed, graded at most `associated` until its re-check reads the window), `recheck_on` / `recheck_value` / `recheck_verdict` (`held|faded|reversed|unknown`) / `rechecked_at`, `accrued_through` (the accrual cursor: the last day `outcome_value_days` has read for this row). Invariants: **one tracker in flight per metric** (`outcomes.record`'s gate, checked again inside `BEGIN IMMEDIATE`; per metric *family* for automatic starts; `metric` stored normalised by `metrics.normalize`) — enforced in code, not by an index, because a family spans metric keys; `started_on` / `evaluate_on` are the restaurant's own calendar dates; an observed action's `source_key` (`observed:<action>:<YYYY-MM>`) appears at most once in any status; a row whose re-check `faded` or `reversed` no longer counts in Delivered and accrues nothing after `recheck_on`. `owner_checkin` is JSON `{did_it, conditions_changed, at}` (older rows may also carry `attribution_before`, no longer read: the grade is recomputed from the stored result by `outcomes.regrade`). Calibration columns (confidence audit 9/24/26 — boot ALTERs from `outcomes._ADDED_COLUMNS` in `init_outcomes`, never on a request path): `trigger_start` / `trigger_end` / `trigger_value` (the window that fired a triggered tracker's recommendation and the metric over it; NULL = not triggered), `baseline_overlaps_trigger` (INTEGER, default 0; 1 = the baseline overlapped the trigger window — the result is shown and **never counted**, in learning or in value), `noise_band` (this restaurant's own band for the comparison, in the metric's unit; NULL = the stated band only), `noise_sigma`, `false_alarm_rate` (two-sided, with no real change), `band_basis` (words). Invariants: a triggered tracker's baseline never overlaps its trigger window unless `baseline_overlaps_trigger = 1`; a result with a "something else changed" check-in stops counting and accruing exactly as a "no" does; `observed:supplier_order_sent:*` and `observed:untaken:<rec_id>` trackers are informational (like `observed:alert_*`) — shown, never counted, never blocking a real change. Memory audit (9/29/26): `measures_key` (from `outcomes._ADDED_COLUMNS`) is the recommendation a tracker measures when its own `source_key` is not that recommendation's — a fill-a-night text's `campaign:<Day>:<date>` measures `slow_day:<Day>` (or the feed card it began on), Ask's `ask:<title>` the recommendation it followed; the module credited, the trigger window and the episode it links to at start are read from it, and the nightly and platform syncs read the verdict under it, while `source_key` stays the tracker's own identity. `changed_at` (millisecond UTC, `idx_outcomes_changed` `(changed_at, id)`) is kept by two triggers `models.ensure_tracker_change_stamps` re-creates each boot: `trg_outcomes_changed_ins` stamps every insert, `trg_outcomes_changed_upd` stamps an update only when one of `models.TRACKER_LEARNING_COLUMNS` changed (status, verdict, the windows, the re-check, the check-in, delta, baseline…) — the daily value accrual's writes are not a change the learning reads. `intelligence.feedback.sync` reads trackers forward from a `(changed_at, id)` cursor.
- `outcome_value_days` — measured dollars, one row per tracker per measured day, PK (outcome_id, day): `restaurant_id`, `day`, `module`, `metric`, `family`, `sign` (+1 a win, −1 a change that got worse), `dollars` (signed; 0 on a day the move was read and did not hold), `held`, `counted`, `basis` (`window` — the evaluated after-window; `daily` — a trailing re-read after it). Invariants: only days actually measured get a row (`metrics.accrual_days`: a per-day metric's day with no `labor_daily_history` row gets none, a comp/void day only when the POS was asked AND it traded, a food-cost day only when it traded); a sales-priced row's `dollars` is its monthly figure's share of one TRADING day (`metrics.days_per_month`); exactly one row per (restaurant, family, day) is `counted` — the broadest held reading of the family (`metrics.BREADTH`: labor % over overtime, food cost % over waste), then the largest — so waste and food cost over the same days are one saving and a labor % win with an overtime loss is the labor % reading. `outcomes.cumulative` elects the same row at read time in SQL (a window function), leaves out trackers the owner disowned, leaves out a labor/food-cost/comp/void row on a day a sales row moved the same way, and sums sales rows apart (`sales_lift`); it is never monthly × months. Written by `outcomes.accrue_window` (at evaluation) and `accrue_daily` (the `outcome_rechecks` job), never on a request.
- `owner_goals` — target per metric, one `active` per metric (older rows become `replaced`); also `abandoned`, `achieved`, and since 9/29/26 `proposed` / `declined`, and (re-audit R3) `missed` — an active goal whose deadline passed without reaching it, retired `goals.MISSED_GRACE_DAYS` (14) later by the 6am outcomes job (`goals.retire_missed`; `progress` already leaves it out past the grace): out of every prompt and target, kept in history, listed once in Goals to renew (a new active goal, the missed one `replaced`) or close (`abandoned`). `owner_memory.target_for` reads the newest active goal still in date. A goal is the target every module judges its figure against (`owner_memory.target_for`), so only an account holder's (or an internal caller's) goal takes effect: a delegate's or an admin's is stored `proposed` (`goals.propose_goal` — a newer proposal on the metric replaces the one waiting), read by nothing that judges a figure, until an account holder confirms it (`active`, replacing the live one) or declines it (`declined`). Columns (boot ALTERs): `authority` (`permissions.answer_authority`, `system` for a job), `source`, `confirmed_by`, `confirmed_at`. A set, replace, confirm or end writes a `change_log` row; a proposal changes no target and writes none.
- `ops_issues` — issue, assignee contact, status open→acknowledged→resolved, `escalation_contact_id`, `escalated_at`, `resolution_note`, `notify_suppressed` (filed with notify=False — `issues.tick` never texts it; reassigning by name lifts it), `meta_json` (e.g. a coverage issue's suggested covers and who was asked; `modules` — the view modules an issue's content draws on, `permissions.MODULE_VIEW_PERMISSIONS` keys — which the Monday plan writes per item (`strategy_jobs.plan_item_modules`) and every viewer-facing list filters by (`issues.hidden_modules` / `viewer_sees_issue`: a login without Food Cost never reads a food-cost plan item — memory re-audit PEOPLE-14)). Timestamps UTC `YYYY-MM-DD HH:MM:SS`. Since 9/29/26 an issue text is CLAIMED before it is sent (`UPDATE … WHERE notified_at IS NULL`) and retried: `notify_attempts`, `notify_next_at` (5, 15, then 45 minutes), `notify_error`, and `notify_failed_at` once it fails for good or reaches 4 attempts — then the owner is told by push and email instead (`issues._fall_back`). ## AI reads

`insight_cache` (`insight_store.py`): one stored model read per `(restaurant_id, kind)` — reviews, food, marketing — with the `fingerprint` of the prompt it was written from. A read is reused while the fingerprint matches (and for at most a week), so web and iOS show the same words and a new read is written only when the data changes. A read written by a call site that runs the Response Validation Layer (workstream A) is stored wrapped — `payload` = `{"_rv": <engine version>, "raw": <the model's text before validation>, "out": <what the owner is shown>, "validation": {verdict, caveats, controls, codes, version}}` (`insight_store.put(..., raw=)`). When the engine's `VERSION` changes, `insight_store.get(..., revalidate=)` re-validates `raw` (no model call) and rewrites the row's payload, its `created_at` unchanged; a pre-engine row (a bare string) is re-validated from its own text, its old `UNVERIFIED:` line removed first. No column was added. The same rule holds for two reads stored elsewhere, also without a new column: `restaurants.competitor_intel` (a JSON blob, `competitor.intel_blob`) now carries `validation` (with its `version`) beside the insight, and `competitor.current_intel` re-checks a blob from an older version or from before the engine on read (never storing the model's raw text, since the blob is served to the browser whole); `review_diagnoses` / `food_cost_diagnoses` rows have no room for a version, so `get_diagnosis` / `get_diagnoses` re-validate each row's text on every read and do not serve one that no longer stands.

## Retention — the one registry

`ops._RETENTION_DAYS` / `ops._RETENTION_COLUMN` is the one registry (`models._LOG_RETENTION_DAYS` is a view of it), and since the memory audit (9/29/26) each table declares three more things: its **floor** (`_RETENTION_FLOOR_DAYS`), the **rollup** run before its rows go (`_RETENTION_ROLLUP`) and its **readers' windows** (`_RETENTION_READERS`). `ops.prune_ledgers` runs nightly straight after the backup (so the pruned rows are in it): first every declared rollup, once each (the AI daily rollup `ai_utils.rollup_usage`, which also prunes the AI-operations tables, then `history_rollups.roll_alerts`, `roll_engagement`, `stamp_newsletter_results`) — a rollup that fails keeps its tables' rows that night; then each table in chunks of `RETENTION_CHUNK_ROWS` (5,000) with a commit each, at most `RETENTION_PASS_MAX_ROWS` (200,000) rows per table per pass (the rest goes on the following nights, reported as `capped` and captured, not paged), stopping taking on tables after `RETENTION_MAX_SECONDS` (10 minutes); then a bounded `PRAGMA optimize`. Every registered column is indexed (`ops._ensure_retention_indexes`). Each window is an env override (`RETAIN_<TABLE>_DAYS`); 0 disables one (kept forever).

**Floors.** A window set under its table's floor — a typo such as `RETAIN_ALERT_LOG_DAYS=18`, which would have erased every restaurant's alert history overnight — is REFUSED: nothing is deleted from that table, the run is partial (`refused` in its result), a `job_failures` row is captured and the operator is paged (`ops.page_operator("retention_floor")`, hourly cooldown); `ops.retention_refusals()` lists them. Each floor is at least the longest window any declared reader reads; where the default IS the floor the window may be raised, never lowered. The same rule holds for the boot prune of `login_history` and for the special prunes below. `tests/test_mem_m7_retention.py` fails when a registered table has no floor, or a declared reader's window (days, or its own constant) does not fit inside it, or a lifetime reader does not read a summary; the readers that reach past their window today, each with its reason, are in `ops._RETENTION_KNOWN_GAPS` (a list that may only shrink).

## What `delete_restaurant` keeps

`models.delete_restaurant` (run only by an admin: the demo delete, or the offboarding checklist's `delete_restaurant_now`, both behind the typed name) removes every row in every table with a `restaurant_id` column, the `restaurants` row, and then any row left pointing at a row it removed — except the tables in `models._KEEP_ON_RESTAURANT_DELETE`: `admin_events`, `offboarding_steps` and `billing_status_history`. The account is gone; the record of what was done to it, and that it was deleted and by whom, is not.

And its **anonymised learning** (owner decision, Will, 9/29/26): for a restaurant that could teach (`models.learning_exclusion` — never a demo, a test or an internal account), its `intel_rec_events` rows from its `learning_since` on are kept, re-keyed to `restaurant_id = -learning_tombstones.id` with every recommendation key's subject hashed (`models._anonymous_key`: a key can name a dish or a person), so cohort priors do not forget what a churned restaurant measured. `learning_tombstones` holds only the restaurant's type and whether it was confirmed, when, and how many rows were kept — no name, no id, no raw rows. Its `intel_features` weeks are deleted with it (Will, 9/29/26): a band reads only the last three weeks, so they taught nothing once the restaurant lapsed. A tombstoned row points at no restaurant by design (the delete's orphan sweep skips it); it passes `models.learning_filter_sql` and counts toward a cohort, and nothing can show a name for it. Everything else of the restaurant's own is deleted. What teaches (memory re-audit 9/29/26, FORGET-16): the kept `intel_rec_events` keep their stamped `cohort` and partition labels, so they go on teaching the priors. `learning_tombstones.category` has no reader — an intentional record, kept so a future cohort-history reader can place the kept outcomes. The `members_json` of the stored bands is handled separately: a restaurant alone in its organisation is removed from every list at the delete (*Intelligence engine*).

## What leaves the server in a backup — the scrub registry

The LOCAL nightly snapshot is never scrubbed: it is the restore artifact, on the same volume as the database. Every OFF-SITE copy (object storage and the emailed copy) is a scrubbed, Fernet-encrypted copy, and the scrub is one registry in `offsite_backup.py`:
- `SCRUB_TABLES` are emptied: `sessions`, `two_fa_backup_codes`, `trusted_devices`, `device_tokens`, `login_reports`, `staff_portal_tokens`, `app_secrets`, `view_as_sessions`, `user_backup_codes` (an internal login's own backup codes), `user_totp` (an internal login's authenticator-app secret, R10) and `async_jobs` (a job's payload and result can carry what an admin typed or a model returned).
- `SCRUB_COLUMNS`, plus every `credentials.FIELDS` column (read at call time), are nulled (a NOT NULL column such as `webhooks.secret` is blanked): reset tokens and recovery codes on `users`, every OAuth / POS / reservation / back-office credential on `restaurants`, `restaurants.stripe_customer_id`, `restaurants.temp_password`.
- `KEEP_COLUMNS` are credential-LOOKING columns kept on purpose, each with its reason (`users.password_hash` — a salted hash; dropping it locks every user out of a restored copy; token-expiry dates; hashes of one-time links; public link ids already printed in guest texts and posts).
- `SCRUB_ROWS` (memory re-audit 9/29/26): rows whose words never leave the server — every removed review (`reviews.deleted_at IS NOT NULL`) has its guest text (`history_rollups.REVIEW_GUEST_TEXT`) blanked in the copy, the same night it is removed; the server itself erases it after 30 days (*Retention*).
- Any other column whose name matches `offsite_backup.CREDENTIAL_NAME` (token, secret, api key, password, passcode, private key, credential) is scrubbed anyway and reported in `backup_runs.detail_json`; `tests/test_fix_d_backup.py` fails until it is classified. The copy is `VACUUM`ed so the old pages go too.

## Conventions that apply across this schema

- **Additive-only migrations.** A new column is added via a guarded `ALTER TABLE` in `init_db()`'s list or `ensure_columns()`'s (both run at boot; 57 columns live only in the latter), never a destructive rewrite, so old rows keep working and a rollback of the code doesn't orphan data.
- **`restaurant_id` scopes every tenant table**, and the newer tables declare `NOT NULL REFERENCES restaurants(id)`. About thirty older tables (`alert_log`, `schedule_history`, `email_log`, `sessions`, `login_history`, `ai_usage`, `push_deliveries`, …) carry the column without the FK clause, so `PRAGMA foreign_keys=ON` does not protect them; the `WHERE ... AND restaurant_id=?` convention does. New tables declare the FK.
- **Append-only tables stay append-only** (`login_history`, `ask_cavnar_actions`, `alert_log`, `capability_changes`, and since 9/29/26 `admin_events`, `support_notes`, `billing_status_history`, `operator_alerts`, and from the memory round `change_log` and `intel_pattern_history`, whose trigger refuses an UPDATE) — they are audit trails; a "current state" view is always computed by querying the latest row, not by mutating history in place. Append-only is not unbounded: each has a retention window or a reason it has none (*Retention*).
- **Timestamps are UTC** in SQLite's `YYYY-MM-DD HH:MM:SS` form unless a column says otherwise (a restaurant's local business date, a `local_day`). `email_log.sent_at` was the exception until 9/29/26 and was migrated.
- **JSON-in-a-column** (`*_json` fields on `restaurants`, `summary_json` on `schedule_history`) is used deliberately for structured settings that don't need their own table and are always read/written as a whole blob by one piece of code — not for anything queried by its internal fields.
