# Security — Cavnar AI

What protects the platform, where each control lives, and the environment
variables it depends on. Written after the enterprise security audit
(Sep 2026) and rewritten after the admin-console fix round (9/29/26). Read
`RECOVERY.md` (beside this file) for what to do when something is broken.
`tests/test_docs_controls.py` checks the controls stated here against the
code, so a change to one fails a test until this file says so.

## Environment variables the controls depend on

| Variable | Required | What happens without it |
|---|---|---|
| `SECRET_KEY` | yes | A random key per boot (and the admin key panel says so, `CAVNAR_SECRET_KEY_EPHEMERAL`; the boot warning names what stops working at each restart). Its real reach is narrow: sign-in sessions are database tokens and do NOT depend on it. It signs the 2FA pending token and keys the 2FA code hashes (a sign-in in flight fails across a restart), the mobile reset-code hash, the Google connect state (`gmb._state_secret` raises without it), the marketing-tap visitor key, and the LEGACY forms of pay links (`<rid>.<sig>`), join links and unsubscribe links. New pay, join and issue links are signed with kept secrets (below) and survive a rotation; rotating `SECRET_KEY` still breaks pay and join links issued before 9/29/26 — resend pay links and reprint QR codes first |
| `CAVNAR_PIN_PEPPER` | **yes** | Staff PINs **cannot be set** (`auth.set_membership_pin` raises). Existing PINs still verify. |
| `CREDENTIAL_KEY` | yes (production) | Client credentials are stored **unencrypted** and the admin system card warns. Encrypts every `credentials.FIELDS` column (see *Data at rest*); the plaintext values already stored are re-saved encrypted at the next boot. Also lets a sales-audit share link be copied again after it is created. **Keep a copy off Railway** — a lost key makes every stored credential unreadable (`None`, never ciphertext), and every value an off-site backup carries sealed under it (OPS-1) is blanked on restore. Generate: `python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` |
| `STRIPE_WEBHOOK_SECRET` | yes | Read on every request. Unset: every Stripe webhook is refused **401** and counted (it fails closed); a bad signature is 400 |
| `DOCUSIGN_WEBHOOK_SECRET` | yes | Every DocuSign Connect call is refused 401 and counted |
| `RESEND_WEBHOOK_SECRET` | yes | Every Resend webhook (bounces, complaints, deliveries) is refused 403 and counted |
| `TWILIO_AUTH_TOKEN` | yes | Inbound texts and delivery-status callbacks cannot be verified and are refused 403 (and texts cannot be sent) |
| `BACKUP_ENCRYPTION_KEY` | yes | **The nightly backup fails** (and pages): no copy may leave the server unencrypted. Keep a copy off Railway — it is the only way to read an off-site backup |
| `BACKUP_S3_ENDPOINT` (https), `BACKUP_S3_BUCKET`, `BACKUP_S3_ACCESS_KEY_ID`, `BACKUP_S3_SECRET_ACCESS_KEY` (+ `BACKUP_S3_REGION`, default `auto`; `BACKUP_S3_PREFIX`, default `cavnar-backups/`) | yes | No object-storage copy; the emailed copy (≤ 25 MB) is then the only off-site path, and when it too fails the backup fails and pages. Give the key access to that one bucket only |
| `ADMIN_REQUIRE_2FA` | opt-in (`1`) | Set it **after** every admin and support login has enrolled at `/admin/two-factor`; unset, an internal login without two-factor signs in with a password alone |
| `ADMIN_PASSWORD` | once | Used only when NO admin login exists at all (the boot seed); it must pass the password policy. Keep it set and strong |
| `LOGIN_UNLOCK_USERNAMES`, `ADMIN_2FA_RESET_USERNAMES` | break-glass only | Unset in normal operation. Set, redeploy, then **unset** — the 2FA reset re-applies on every boot while it is set (*Break-glass*) |
| `WILL_PHONE` | recommended | Operator pages go by email and push only; the text is the channel that survives a Resend or APNs outage |
| `HEALTHCHECK_PING_URL` | recommended | Nothing outside Railway notices a scheduler (or a whole process) that stopped |
| `TWILIO_OTP_MESSAGING_SERVICE_SID` | recommended | Sign-in codes go on the general messaging service |
| `DEMO_PASSWORD` | optional | The demo login has a generated password that is shown nowhere (use a reset link); set it and the same credential works everywhere. Held to the password policy |
| `ALLOW_LOCAL_SCHEDULER` | never on a laptop by accident | `1` lets a non-Railway backend run the scheduler AND send admin email/SMS with production's keys |
| `ALLOW_NO_VOLUME`, `ALLOW_EMPTY_DATABASE` | emergency only | Override the boot's refusal to run without the volume, or with an emptied database on a volume that held clients (`RECOVERY.md`) |
| `ALLOW_LEGACY_JOIN_LINKS` | default off | `1` still accepts bare-integer `/join/<id>` links |
| `HIBP_DISABLED` | default off | `1` skips the breached-password lookup (tests set this) |
| `BACKUP_RETAIN_COUNT` | default `3` | local snapshot retention (the newest N gzipped snapshots; was `BACKUP_RETAIN_DAYS`, 10/7/26) |

The admin console's system card (`GET /admin/api/system`, `platform_monitor.key_report`) checks every variable this table marks required — presence, never a value; `CREDENTIAL_KEY` and `BACKUP_ENCRYPTION_KEY` must also parse as Fernet keys, and a per-boot `SECRET_KEY` reads as missing.

## Authentication

- **Passwords**: scrypt (`werkzeug.security`). The policy lives in `auth.create_user` and every set path: at least 8 characters and not in a known breach (HIBP k-anonymity, `security.password_pwned`, fails open). Only a secret the code mints at random skips it (`create_user(..., generated=True)`).
- **Account holders and two-factor** (scale fix 10/19/26, SEC-11): `auth.login_needs_second_factor` asks a second factor of an owner or co-owner (`permissions.is_principal`) whatever the restaurant's switch once the rollout reaches them — `PRINCIPAL_2FA_REQUIRED_SINCE` (restaurants created on or after that date) and then `PRINCIPAL_2FA_REQUIRED=1` (all); both unset today. Never for a login with nowhere to send a code. The switch itself is still per restaurant, not per login.
- **Passkey sign-in options are filtered before they write** (R7-07): each `/auth/passkey/options` and `/mobile/api/passkey/options` call writes a challenge row, and the per-address limiter counts only failures, so `request_limits.memory_limited` (`passkey-opt:<ip>`, `auth_routes.PASSKEY_OPTIONS_PER_MINUTE` = 10 a minute) answers 429 before anything is written.
- **Passkeys** (owner, 9/30/26; `passkeys.py`, Duo Labs' `webauthn`): a login adds one from Account → Security only after typing its password (`/api/passkeys/options`, throttled per address) and never in view-as; sign-in is `/auth/passkey/options` + `/auth/passkey/verify` from the login page (CSRF token in the body, throttled per address). Every challenge is server-side, single use and 5 minutes old at most; user verification (Face ID, Touch ID or the device PIN) is required both ways; the origin and RP ID must be this site's own host (`config.base_url`, localhost, or `PASSKEY_HOSTS` for a test tunnel); a signature counter that does not rise is refused as a cloned key. A passkey sign-in is the session's second factor (the device plus what unlocked it), so a 2FA restaurant asks no code — but **not for an internal login**, which keeps its authenticator app. "This wasn't me" (`must_reset_password`) still blocks it, and removes the login's passkeys with its sessions. Adding a passkey is emailed to the login's own address with that one-time "This wasn't me" link (`send_passkey_added_email`, security mail: suppression-exempt and flood-capped); removing one is refused in view-as.
- **Sign in with Apple on the web** (`auth_routes.apple_web_signin`, shown only when `APPLE_WEB_SERVICES_ID` is set): Apple's popup hands the page an identity token, verified against Apple's keys for that Services ID and a nonce whose raw value sits in an httponly cookie (`a_sso_nonce`, 10 minutes). Matched as the app's sign-in is (Apple user id, else an email Apple says it verified), and gated as Google's is: an inactive or reset-pending login is refused, and a login whose 2FA no remembered device covers is sent to the password form.
- **Sessions**: 24-byte tokens, **SHA-256 at rest** (`auth.hash_session_token`), `HttpOnly`/`SameSite=Lax`/`Secure` on Railway; HSTS when cookies are secure. `expires_at` is SQLite `YYYY-MM-DD HH:MM:SS` UTC and compared through `datetime()`. Lifetimes:
  - owners and teammates: 30 days absolute, and on the web an 8-hour inactivity rule (iOS and staff PIN sessions are exempt from it);
  - staff PIN sessions: 14 hours;
  - **admin and support: 12 hours absolute** from sign-in (`auth.ADMIN_SESSION_HOURS`), on every device, never extended; older rows were capped at boot;
  - **view-as: 2 hours absolute** from when it was opened (`auth.VIEW_AS_HOURS`), never extended.
- **Login throttling and lockouts** (`security.py`, table `login_attempts`), durable across deploys and workers:
  - by account: 5 failures in 15 minutes locks it — 5 minutes, then 30 minutes at 10 failures in a day, then 24 hours at 15;
  - by IP: 25 attempts naming accounts, or 5 naming none, in 15 minutes;
  - **an admin or support login is locked per address** (account + IP), so a stranger's guesses cannot lock the operator out from everywhere, with a separate cap of 100 failures a day across all addresses (a 60-minute lock);
  - a device the login remembered at a two-factor sign-in skips the account lock (the IP budget still applies);
  - a lock writes `login_locked` to the owner's activity log.
- **An email change is confirmed at the new address** (re-audit 10/20/26, R7-17): `POST /api/update-email` and `/mobile/api/account/update-email` (one body, `auth_routes._do_update_email`) take the current password and then email a 6-digit code to the NEW address (`emails.send_email_change_code`, security mail; `auth.start_email_change` — `users.email_change_pending`, the code HMAC-hashed, 15 minutes); the change, and an account holder's `restaurants.owner_email` with it, is made only when that code comes back with the same address, and the 5th wrong code ends the request (`auth.finish_email_change`). The first answer is `{ok: false, verify_required: true}`. Never in view-as. The old address is still told once it is done.
- **Password reset**: 32-byte token, 1-hour expiry, **hashed at rest** (`models._hash_reset_token`). Admins never set a password: every admin reset route sends a reset link only; a `password` in the request is ignored and the answer says so; admin logins and staff PIN identities are refused as targets.
- **Temporary passwords are never stored or emailed.** A new owner gets one welcome email, whoever sends it — the post-signing outbox, checkout provisioning (through the same outbox) or the console's Resend welcome all call `emails.send_welcome_with_set_password_link` — with a one-use set-password link valid for 72 hours from the send (`models.SET_PASSWORD_LINK_HOURS`; `billing_jobs.WELCOME_LINK_HOURS` is the same value, and the email says 3 days). Minting the link changes nothing about the login, so a failed send leaves the owner as they were. No password is reset at contract signing.
- **Two-factor (a restaurant's logins)**: one challenge per sign-in attempt (and one per login for "Send test code") in `two_fa_challenges`; the code and the pending secret are **HMAC-hashed at rest** (keyed by `SECRET_KEY`) and single-use (`auth.issue_two_fa_challenge` / `check_two_fa_code`). Codes are delivered by `auth.deliver_two_fa_code`: texts go on the OTP messaging service and **fall back to email** when the number has sent STOP or the text fails; the sign-in screens say what really happened (mobile login returns `code_sent`, `fell_back`, `delivery_error`). Backup codes (hashed, single use, any case, with or without the dash — `models.normalize_backup_code`), 30-day trusted devices, revocable, each the login's that ticked "remember" (`auth.remembered_device_ok` on every sign-in path). **Guessing is bounded per challenge and per login** (re-audit 10/20/26 R7-01): the 5th wrong code deletes the challenge (`two_fa_challenges.attempts`, `auth.TWO_FA_CHALLENGE_MAX_WRONG`; a resend keeps the count), so the sign-in starts again from the password; and every wrong second step — code or backup code, any method, from any address — counts against the login (`login_attempts` key `2fa-user:<id>`): `security.SECOND_FACTOR_DAY_MAX` (10) in a rolling day locks that login's second step (`auth.second_factor_lock_left`, 429 on web and phone, even for the right code) until the oldest ages out, writes `two_factor_locked` to the owner's activity and emails the login once per lock (`emails.send_security_notice_email`, security mail). A remembered device never reaches the step; the console's Clear lockout, the break-glass unlock and a password reset lift it. The per-address budget (`2fa:<ip>`) still applies. Resending a code needs the pending token login issued and is throttled per address; a send that fails is a 502 with a sentence, never "sent". Codes go to the login signing in (`auth.two_fa_destination`), never to the owner's contact for another login. The restaurant-wide switches (web and mobile) refuse internal logins and non-principals.
- **Two-factor for admin and support logins** (fix round, 9/29/26): an internal login's second factor lives on its own row (`users.two_fa_enabled` / `two_fa_method` — email, sms or app — its own `user_backup_codes`) — never the restaurant switch, never the restaurant's backup codes. Every sign-in path asks (`auth.login_needs_second_factor`): web password, Google, Apple, mobile. Google and Apple sign-ins by an enrolled internal login are refused ("use your password for the code") unless the device is remembered. `auth.admin_second_factor_state` gates every admin request (`admin_required`, and `login_required` / `mobile_login_required` for an internal login): `ok`; `enrol` (only when `ADMIN_REQUIRE_2FA=1` — 403 `{two_factor_required, enrol_url: "/admin/two-factor"}`, or a redirect there for a page); `verify` (a session from before enrolment is ended — 401 `session_expired`); `error` (fails closed, 503). **Enrolment**: `/admin/two-factor` — choose email or SMS, `POST /admin/two-factor/send` sends a code (no fallback here; 429 within a minute of the last), `POST /admin/two-factor/verify` confirms it, turns it on, stamps the session's `two_factor_at` and returns the backup codes once. Disable and new backup codes need step-up (and disable is refused while `ADMIN_REQUIRE_2FA=1`). A restaurant's sign-in alert is never sent for an internal login.
- **Authenticator app for admin and support logins** (R10, 9/29/26): a third method, `two_fa_method = 'app'` — TOTP per RFC 6238 (SHA-1, 6 digits, 30-second steps, one step either side accepted), scanned into Duo Mobile, Google Authenticator or any authenticator app. `POST /admin/two-factor/send {method: "app"}` makes a random 160-bit **pending** secret (`auth.start_totp_enrolment`) and answers with its QR code — drawn on the server by the `qrcode` package as an SVG data URI, never by a third-party QR service — plus the key in groups of four, `Cache-Control: no-store`; nothing is sent. The pending secret is dead after 15 minutes, and only a code from the app makes it active (`auth.confirm_totp_enrolment`, `POST /admin/two-factor/verify {method: "app"}`), in one transaction with `two_fa_enabled=1, two_fa_method='app'`. Both secrets live in `user_totp` (not on `users`, so a secret never rides on the user every request loads), **encrypted under `CREDENTIAL_KEY`** — the app is refused (409) without a working key — never logged, never in an audit payload, and `user_totp` is emptied from every off-site backup. Each 30-second step passes once per login (`user_totp.last_step`, claimed compare-and-set), every candidate is compared in constant time, and wrong app codes are throttled **per login** as well as per address (`auth.second_factor_throttle_key`: 5 in 15 minutes, at sign-in and at enrolment). At sign-in an app login is asked for the app's code (`auth.check_sign_in_code`): nothing is emailed or texted, Resend is refused (400) and there is no email fallback — a lost phone signs in with a **backup code**, which still works; a lost `CREDENTIAL_KEY` leaves only backup codes and `ADMIN_2FA_RESET_USERNAMES`. **Switching** an enrolled login's method (email or SMS to the app, the app to a new phone, or back to email or SMS) goes through the same two routes and needs the step-up (`auth.reauth_refusal` in `admin_two_factor_send` and `admin_two_factor_verify`) on a session that already passed its current second factor; the old method keeps working until the new one is confirmed, the backup codes are kept, leaving the app forgets its secret (`auth.clear_user_totp`), and the change is audited (`admin_two_factor_method_changed`, before and after method; `admin_two_factor_app_qr_shown` when a QR code is made).
- **Step-up for an account holder's own security changes** (blind re-audit 10/20/26, R7-03): a stolen owner session or an admin's writable view-as could invite a co-owner, revoke the real owner and turn 2FA off without a password. These now ask for the password within `auth.RECENT_AUTH_MINUTES` (15) — the session's `reauth_at`, stamped by a password sign-in or by `POST /api/account/reauth` / `/mobile/api/account/reauth` (`auth.account_reauth`; five wrong passwords on a session end it), or a sign-in that minutes old by any method (Google, Apple and passkey logins may have no password they know) — and are refused outright in a view-as (403 `{view_as}`): turning 2FA off (`/api/toggle-2fa` off, `/api/account/2fa/disable` and its app twin), new backup codes, inviting a co-owner or making / unmaking one (`team/invite` with role `client`, `team/<id>/role`), removing an account holder (`team/<id>/revoke`), changing the owner's phone (the account holder's SMS 2FA destination, `account/profile` / `update-profile`), signing other devices out (`sessions/revoke-others`) and closing the account (`account/request-deletion`). The refusal is 403 `{reauth_required, reauth_url, window_minutes}` (`auth.account_step_up_refusal`); the dashboard's fetch wrapper and the app's `APIClient` ask for the password, post it and send the change again. 2FA off, new backup codes and a new co-owner are emailed to every account holder (`auth.notify_account_holders` → `emails.send_security_notice_email`). The email change already needed the current password. **A writable view-as asks the admin for the password** within the window (the confirm page's password field; the app's `POST /mobile/api/admin/view-as/<rid>` answers `reauth_required` with the app's step-up route); support's read-only view does not. **"This wasn't me"** (the email link and the app's push button) also suspends every account-holder login created at that restaurant in the last 7 days after the reporting login (`auth._suspend_recent_principals`: deactivated, signed out, remembered devices forgotten), names them on the page and in the app's answer, and writes `principal_logins_suspended` to the activity; older account holders are never touched.
- **Signing an admin out ends its views** (R7-06): `auth.end_login_access` (deactivate, sign all sessions out) also deletes every view-as session the login opened (`sessions.acting_admin_id`), and so does an internal login's 2FA reset (`auth.end_view_as_opened_by`); a view-as whose admin is no longer `is_admin` (demoted to support) reads as read-only whatever its row says.
- **Full control through view-as (the owner's grant, 9/30/26)**: an owner can give an admin full control for 1–90 days (`restaurants.admin_control_until` / `admin_control_note`, set from the client page — step-up, and one `record_admin_action` row, `full_control.set` / `full_control.end`). While it runs, an **admin's** (never support's) writable view-as on that restaurant counts as the owner's (`permissions.counts_as_owner`): `answer_authority` is `principal`, `acting_via` is none and writes are stamped `via='normal'` — ratings count, answers train, edits are the owner's voice — while the admin behind each write is still the recorded user id and every view-as write is still logged. Security settings, billing and the rest stay exactly as view-as has them.
- **Step-up for sensitive admin actions**: `@auth.recent_auth_required()` (directly under `@admin_required`) refuses **403 `{reauth_required: true, reauth_url: "/admin/api/reauth", window_minutes: 15}`** unless the session's password was typed in the last **15 minutes** (`sessions.reauth_at`, stamped by a password sign-in — never by Google or Apple — and by `POST /admin/api/reauth {password}`). A wrong reauth password is 403; the fifth miss in 15 minutes ends the session (401 `session_expired`). The console asks for the password and sends the action again. **Applied today** (the decorator, on 51 routes):
  - logins: deactivate a login, change a role, reset a login's 2FA, clear a lockout, sign a session out, sign all of a login's sessions out, create a support login, and the admin's own 2FA disable / backup codes / username;
  - passwords: send a reset link (`/admin/send-reset-link/<user_id>`, and the older `/admin/reset-password/<user_id>` and `/admin/reset-password-by-restaurant/<id>`, which also only send a link) and resend the welcome;
  - the account: creating a client (a restaurant and its owner login) and reactivating a login (blind re-audit 10/20/26 R7-13), freeze, the demo flag, the owner's grant of full control (`/admin/api/client/<id>/full-control`), delete a demo, delete a client, add a location;
  - billing: change plan, lift a hold, mark signed, attach a Stripe customer;
  - POS credentials: the Toast, Square, Clover and RPOWER admin saves and disconnects, and RPOWER bootstrap; since Audit #23 (F7, 10/21/26) the RPOWER partner credential's rotation and revocation (`/admin/rpower/credentials/<id>/rotate`, `/revoke` — audited `rpower.credential_rotated` / `rpower.credential_revoked`, version before and after, never a token), a demo's live-store override (`/admin/rpower/live-mirror/<id>`, `rpower.live_mirror_set`, a reason required), releasing a bulk store's owner hold (`/admin/rpower/owner-check/<id>`, `rpower.owner_check_released`, how the owner was confirmed required), and the offboarding POS archive export (`/admin/api/client/<id>/pos-export` and its `/download`, `offboarding.pos_export_built` / `offboarding.pos_export_downloaded`).
  - AI spend (orchestration design, 10/7/26): a workflow's route override (`/admin/api/ai-routes/<workflow>/override`), its revert (`/admin/api/ai-routes/<workflow>/revert`), applying or dismissing a learner recommendation (`/admin/api/ai-routes/recommendations/<rec_id>`), and entering a vendor's monthly invoice (`/admin/api/ai-costs/invoices`) — each audited with its before and after (`ai_route.override_set`, `ai_route.reverted`, `ai_route.recommendation_applied` / `_dismissed`, `ai_invoice.recorded`).
  - invoice intake's sender check (10/16/26): an email to a restaurant's secret intake address is read only from a listed sender, and only when Resend vouches for it (DMARC pass, or DKIM where there is no DMARC policy) — or, when nothing is signed (SPF and DKIM gray or unknown, neither failed) and the route's reader can vouch. With DMARC fail as well (`email_intake._unsigned_dmarc_fail` — Fintech's own 10/15–10/16/26 mail read exactly this, and so does a spoofed From) the mail is never trusted on its own word: it is read only through that file check, never otherwise (owner 10/16/26; the lasting fix is Fintech signing its mail) (`email_intake.VOUCHERS`: Fintech), when every attached file, read without writing, names a store on every invoice, only stores and distributors that restaurant's invoices already carry, has the format and column set of an earlier file, keeps every invoice total within 3x the distributor's largest on file and every price within 3x of the item's prices on file, and changes no invoice already on file (`fintech_invoices.vouch`, SEC-02). A new store or distributor, a store-less invoice, a new layout, a price out of band, a failed signature, or a file that does not parse keeps it held for an admin's Release; one read on its files' word shows "file vouched, mail unsigned" on the admin's Invoice intake card.
  - website analytics ownership (scale fix round, 10/19/26, SEC-01): approving a pending GA4 property / Search Console site binding by hand (`/admin/api/external-bindings/approve`, audited `external_binding.approved` with before and after).
  - invoice intake (bar fix round, 10/15/26): rotating a restaurant's intake address (`/admin/api/client/<id>/intake/rotate`) and purging a received file (`/admin/api/client/<id>/intake/purge`) — audited as `intake.route_rotated` / `intake.file_purged`.
  - onboarding at scale (scale audit 10/19/26): applying a provisioning list (`/admin/api/onboarding/provision/apply` — it creates restaurants and owner logins and keeps an RPOWER partner token, encrypted; the dry run, `/admin/api/onboarding/provision/dry-run`, writes nothing and needs no step-up) saving a partner (`POST /admin/api/partners` — with `PARTNER_BILLING=1` a partner billing its stores under a signed master agreement takes their own contract and checkout off them) and attaching a store to one (`POST /admin/api/partners/<pid>/stores` — the same billing effect for that store; scale re-audit 10/20/26 R8-22) — audited as `bulk_provision.started` / `bulk_provision.applied`, `partner.saved` and `partner.store_attached`. No password is typed, shown or emailed for a provisioned owner: the welcome is the set-password link (`emails.send_welcome_with_set_password_link` through `billing_jobs`' outbox).

  Five routes ask for it only for the part of what they do that needs it, through `auth.reauth_refusal(current_user)` (the same 403): a client-settings save (`save_client_settings`) that CHANGES the billing status, a module switch, the owner email or the owner's phone (`_SETTINGS_STEP_UP_FIELDS`) — the phone since R7-13, as it is where an account holder's sign-in codes are texted — asked after every other check, so a refusal the admin can fix is said first and nothing is written before the password is given; an offboarding step marked done that acts (`offboarding.ACTING_STEPS`: integrations, Stripe, DocuSign); the review-account seed when it rotates the password; and an internal login's own two-factor send and verify when the login already has two-factor (a method switch — `admin_two_factor_send`, `admin_two_factor_verify`).

## The staff app (employee-app fix round, 10/2/26)

An employee's identity is a `memberships` row with a PIN (scrypt under `CAVNAR_PIN_PEPPER`, `docs/ops/PIN_PEPPER_RUNBOOK.md`); a staff session is the least trusted session in the product — it often sits on a shared tablet — so:
- **One PIN policy** (`auth.validate_pin`, for an owner's set, sign-up, Change PIN and forgot PIN alike): 4–8 digits; no single repeated digit, no straight run up or down, no repeated pair (`abab`), no year (19xx, 20xx), and none of the 110 most published PINs (`auth.COMMON_PINS`).
- **Attempts are counted before the PIN is checked** (`auth._reserve_pin_attempt`, in `BEGIN IMMEDIATE`): when in-flight attempts have spent the budget (5), the request is refused without running the KDF and the login locks — parallel guesses cannot outrun the lockout. A lock lasts 15 minutes × 2^(locks in the last day), capped at 24 hours. A bad join code on PIN sign-in is counted on the per-address portal budget before the code is looked up.
- **A spray is refused** (scale fix 10/19/26, SEC-15): an address with `PIN_SPRAY_BLOCK_FAILURES` (20) wrong PINs across `PIN_SPRAY_BLOCK_PEOPLE` (4) or more people at one restaurant in the last `PIN_SPRAY_BLOCK_MINUTES` (60) gets no PIN check there until the window clears (`auth.pin_spray_blocked`) — the KDF is still paid, nobody's attempts are spent, and another address signs in as usual. New PINs can be held to a longer floor with `STAFF_PIN_MIN_LENGTH` (default 4; existing PINs keep working).
- **The owner hears**, through `auth.alert_staff_admins` (Railway only — `scheduler.scheduling_allowed()`): a lock (once per lock), a spray (10 or more failures across 3 or more people from one address in 15 minutes, at most once an hour per restaurant and address, `ops.claim_cooldown`), every claim (the name and the phone's last four only), and an account deletion. The audience is named, never "every phone here": `auth.staff_admin_user_ids` — owner, client and manager memberships by role, never an employee or an internal login — as push type `staff_signin`, and email to the owner when no device took it.
- **Change PIN has its own counter** (`pin_change_attempts`): 3 wrong current PINs lock it 15 minutes and end the session, so the next person at a shared tablet cannot lock the session's owner out of sign-in.
- **The browser portal** (10/7/26, parity audit #100: `/staff/r/<code>` PIN pad, `/staff/home`): the same PIN sign-in, nonce, lockout and per-address throttle as the app, and an HttpOnly, SameSite=Lax `staff_session` cookie whose token is never in a response body for a browser. Every cookie-authenticated write on `staff_bp` and `staff_knowledge_bp` passes the double-submit CSRF check (`staff_routes.staff_csrf_check`, app-wide in `hosted_dashboard`): a request carrying a Bearer token (the app) is left alone — a cross-site page cannot add that header — and so are the pre-session routes (sign-in, sign-up, forgot PIN). What guards those is not the sign-in nonce (anyone can fetch one): they act only on an `application/json` body (`request.get_json()`, never a form), which a cross-site page cannot send without a CORS preflight this server never grants, and a POST whose `Origin` names another site is refused outright (`staff_routes._foreign_origin`; re-audit 10/8/26). Sign-out: a GET only asks; the POST carries the token.
- **Sign-out ends the session on the server** (`POST /staff/api/logout`, the bearer token or the cookie) and unregisters that phone's staff push. A PIN set or reset, a deactivation, an unlink or a deletion ends the staff sessions **at that restaurant only** (`auth._end_staff_sessions_for_membership`) and unregisters the phones.
- **Forgot PIN by text** (`auth.start_pin_reset` / `verify_pin_reset` / `complete_pin_reset`): the code goes only to a number already on file for a login there (the login's own, the one it was claimed with, or the owner-typed roster number), checked in that order; the same answer whether or not the number has a login (no text when it has none, nothing when it matches more than one); one message for every verify failure; the code and the reset token are stored hashed, the token lasts 15 minutes and works once; the new PIN passes the policy, lifts the lockout and ends the login's other staff sessions there.
- **Verification texts** (sign-up and forgot PIN share one gate): only `STAFF_OTP_COUNTRY_CODES` (default `1`, and +1 needs exactly 10 digits); fair shares inside a platform backstop (scale fix 10/19/26, SEC-04) — each restaurant its own `STAFF_OTP_RESTAURANT_HOURLY_CAP` (default 30) an hour, counted by the join code the sign-up named (both clients ask the restaurant code before the phone) or the forgot-PIN's restaurant; a send naming no restaurant draws on its own `STAFF_OTP_ANON_HOURLY_CAP` lane (default 30, closed by `STAFF_OTP_REQUIRE_JOIN_CODE=1`) and can never spend a restaurant's share; an unknown join code sends nothing; all under `STAFF_OTP_HOURLY_CAP` (default 600). **Sized for onboarding** (re-audit 10/20/26, R7-05): the platform backstop grows with the restaurants that have a staff join link (`STAFF_OTP_PER_RESTAURANT_PLATFORM`, 4 an hour each, never below `STAFF_OTP_HOURLY_CAP`); a restaurant's share grows with its staff (`STAFF_OTP_SHARE_PER_STAFF_PCT`, 125% of the larger of its staff logins and roster contacts, never below `STAFF_OTP_RESTAURANT_HOURLY_CAP`); sign-up and forgot-PIN are separate lanes of that share, so a join-code holder spending sign-ups never stops forgot-PIN; a sign-up code is sent only while the restaurant has a roster name nobody has claimed (`auth._has_unclaimed_roster_name`, fails open); and an owner's deactivate or unlink of a staff login rotates the restaurant's join code (`auth.rotate_join_code` — the staff link and everyone's PIN are kept; the answer carries the new code). Counted in `staff_otp_sends` (kind, time and restaurant only), each scope's hit captured once an hour after the send's transaction ends; the code is returned in a response only with `STAFF_SIGNUP_DEV_CODE=1`, with Twilio unconfigured, off any deployment (`auth.dev_code_allowed`). Log lines carry the phone's last four only (`mask_phone_last4`). The sign-up's claimable-names list is throttled and takes its token in the `X-Signup-Token` header (`?signup_token=` is read only for older app builds; the web page sends the header).
- **Identity**: one active employee login per name per restaurant (code checks plus the partial unique index `uq_memberships_active_employee_name`); a claim is one `BEGIN IMMEDIATE` transaction and refuses a phone that already has a login there; an unlinked or deleted login is never restored by the roster switch; no PIN is upgraded or claimed without the pepper. **Delete my account** (`POST /staff/api/account/delete`, App Store 5.1.1(v)) ends the login and its links (*DATABASE_SCHEMA.md* → Staff portal).
- **Switching location never mints a session** (`POST /staff/api/switch`): each location's PIN is its own credential — its owner resets it, its lockout guards it — so the switch answers that location's PIN pad (portal token, membership id, a fresh nonce) and the app signs in with that PIN.
- **Push**: a staff-app phone is `device_tokens.tier = 'staff'`; it is reached only when `fire_push` names its login, only by the staff alert types (`push.token_may_receive`), only while the membership is active, and never carries an owner's badge — a restaurant-wide alert can never reach an employee. `/mobile/api/device-tokens` still refuses a PIN session.
- **Counted only when delivered**: a staff notice is "sent" only when a channel took it (`people.deliver`: a push counts once Apple accepted it; a publish writes its app share row only then), and a text needs the employee's own consent for that purpose (`staff_sms_scope`) on the staff messaging service only.
- **What staff can read**: their own figures only — hours and tips from their own POS id (two POS people under one name is `ambiguous`, never a guess), their own attendance, never a reliability score, anyone's pay, or another person's notes. Anything a model writes for staff passes the `staff` audience (Response Validation rule S1: no money, pay, owner's numbers, ratings or another person's name) or is not shown (`PROMPT_LIBRARY.md` → Staff surfaces).
- **Proof photos**: stored only after the sheet is confirmed the caller's, at most 60 per login an hour (counted in the database), served `private, no-store` to this restaurant's signed-in viewers only.

## Authorization

- Roles in `permissions.py`: owner, client, manager, member, employee, **support**. Support reads the admin console; every admin write returns 403 (`auth.admin_required`) except opening a view-as and managing its own two-factor (`auth._SUPPORT_WRITE_OK`): enrolment, switching method with the password step-up (`/admin/api/reauth` — the step-up unlocks nothing else for support), new backup codes, and turning it off where it is not required. Each touches only the login's own row, so no one resets a support login's two-factor for it (9/29/26). The role is on the request (`g.admin_role`, `auth.current_admin_role()`).
- **No console session** (none, expired or not an internal login): `auth.admin_required` answers a request that wants JSON — any non-GET, and any GET under `/api/`, `/admin/api/` or `/mobile/api/` (`auth._admin_wants_json`) — with **401 `{session_expired: true}`**, and the console's `api()` sends the admin to sign in again; a page GET is a **302** to the login page. (An expired `/admin/api/` GET used to be a 302 to an HTML page, which `fetch` followed and then failed to parse.)
- **View-as** (owner decision, 9/29/26): a POST (a GET only asks) carrying a reason the restaurant sees in its own account activity (10/19/26, SEC-12); it opens only on the restaurant's OWNER login (404 otherwise — no fallback to a staff or manager row); it lasts 2 hours absolute; the session carries the acting admin (`sessions.acting_admin_id`); a view-as a support login opened is read-only on the row (every non-GET 403, fails closed). The dashboard shows a banner naming the admin whenever the session's `device_type` is `admin-view-as`, with a POST "Back to admin". Start (with its end time) and stop are recorded, and every write made through a view-as is recorded against the acting admin (`admin_events` `view_as_write`: actor, login, path, status, result) — read-only refusals included; a write refused before its handler (billing 402, module 403, a moved tab 409) is not. `/admin/stop-viewing`: a GET only asks; a POST ends only a view-as session and restores the admin's own session from a path-scoped cookie. The tab ping (`/api/log-activity`) is skipped for a view-as session. **From the app** (10/8/26): an admin signed in on the iPhone opens the same session through `POST /mobile/api/admin/view-as/<rid>` (internal logins only, the admin request ceiling applies) and ends it through `POST /mobile/api/admin/stop-viewing`; the app wears the view's token for its own requests only, keeps the admin's in its usual Keychain slot for the widget, Share extension, Live Activities, lock-screen actions and Siri, and a view-as session never files a push or Live Activity token (the server answers `skipped`), so the admin's phone never receives the client's alerts.
- **The admin request ceiling**: 240 requests and 60 writes a minute per admin session (`security.admin_request_allowed`, process-local), 429 `{rate_limited, retry_after}` with `Retry-After`. It runs through `auth.admin_required`, the one gate on every blueprint with admin routes (admin, status, sales-audit and the four POS blueprints).
- **Role changes** go through `auth.admin_set_role`: `users.role` and the membership together; client, owner, manager or member only; a last-owner guard; admin, support and staff rows are refused; before and after are audited.
- **Staff-account routes reach staff only** (R7-23): `/account/staff/<membership_id>` (update, `pin`, `unlock`, `deactivate`, `unlink`, web and app) act only on an `employee`, `member` or `manager` membership at the caller's restaurant, never the caller's own (`mobile_api._staff_target_refusal`) — they matched any membership id, so a co-owner could demote or deactivate the owner past Team's own guards. Remembered devices (R7-25): a teammate lists, removes and clears only its own; the restaurant's list, and clearing all of it, is the account holder's.
- Account-holder switches are `permissions.principal_only`: outbound webhooks (and their signing secret, and the test delivery), POS credentials, Google Business connect, callback and disconnect, review retention and auto-approve, alert settings, the owner's email switches (on every route and through Ask), the brand voice and the owner's name — `voice_notes`, `never_say`, `menu_notes`, `sign_off_name`, `owner_name`, trusted instruction to every drafter and the offer source public copy is checked against (`client_api._do_brand_voice`; `mobile_update_profile` refuses a teammate's change and leaves the fields as they are on a teammate's save; memory re-audit PROMPTS-9) — alongside 2FA and backup codes (`is_principal`). Every Bar write except counts and waste entries — product sorts, the bar mapping, stopped distributors, bar settings, packs, product links, the deal sheet, the drink map and drink specs — is the account holder's too (`mobile_api._bar_write`; a view-only Food Cost grant re-sorted products and moved the liquor figure, barfix 10/15/26 V21), stored under the acting login and logged with before and after.
- **Ask acts with the asking login's rights** (R7-19): `set_staff_contact` runs the REST route's own body (`mobile_api._do_set_staff_contact`: SCHEDULE_PUBLISH or TEAM_INVITE, the change history, the employee told at the address they had), is offered only to a login that may use it (`ask_cavnar_tools._STAFF_CONTACT_TOOLS`), and changes nothing without a signed-in login — a member login could point an employee's schedule link and forgot-PIN texts at itself.
- **Pay stays with the logins that see pay** (`strategy_routes._sees_pay`: the account holder and whoever may send the schedule; R7-24): the schedule check (`labor/schedule/violations`) withholds the edit's `cost` and prices its overtime moves on no rate for anyone else (`pay_hidden: true`) — one 10-hour shift against an empty baseline read that person's own wage off the cost — and so does Ask's one-shift edit plan (`floor_api.shift_edit_plan`); a person save from such a login that sends any pay value gets one fixed refusal, never one that says whether it matched the role's rate.
- **A job poll answers only its own kind** (R7-21): `ops.read_async_job(..., kinds=)` — the schedule poll (`labor/schedule-status/<job_id>`, web and app) reads only `schedule` jobs and the competitor polls (`intel/refresh-status`, `/api/competitor-intel-status`) only `competitor_intel`, so a manager without Food Cost who learned an invoice scan's id cannot read its costs through them (`ai_async.result` keeps its own per-login check).
- What a login may not read it may not act on by id: a loss issue (LOSS_VIEW) is a 404 to resolve, reassign or ask-cover; a goal on a metric it cannot see is a 404 to end; a queued supplier order's label drops its dollars for a login without food cost.
- Every `/api` and `/mobile/api` route is either module-mapped (`auth._MODULE_PREFIXES`) or listed with a reason in `auth._UNGATED_PREFIXES`; a test fails on a route that is neither.
- Module-view gates fail closed; billing/entitlement gates fail open by design. A HOLD is different: a dispute or refund pause (or one an admin set) is lifted only by an admin (`models.billing_hold`); the owner's Resume refuses it with 409.
- **The audit trail** (`admin_events`): every write on every blueprint that carries `/admin` writes (admin, status, the four POS blueprints, the sales-audit tool) is recorded AFTER the response, with its status and the redacted body, and only for a console login (admin or support) that passed CSRF (`admin_events.audit_admin_write`). Anonymous, non-admin and CSRF-failed attempts go to `admin_audit_refused` instead — capped at 5,000 rows, 30 days, and 20 rows per IP per 10 minutes — so nobody outside can flood the trail. An action that records itself does so through one typed call (`admin_events.record_admin_action`; `admin_routes.py` has no other) — directly (the RPOWER token save, bootstrap and disconnect now too, with the store binding before and after, R7-13), or through `admin_events.audited(action, snapshot=)`, the decorator that writes the same row for a write that has no before/after of its own to state (since the re-audit, 10/20/26 R7-13: create client, the status banner and incidents, staff availability, data and menu uploads, templates and the changelog — the names of the fields sent, never their values): actor and actor id, target, before/after (secrets redacted by key name — never a credential value), result, ip and request id; a write made through a view-as names the acting admin. A summary-only row (`admin_events.record`) is left for events no console login makes — the break-glass unlock and 2FA reset, the boot seed, `scripts/unlock_login.py`, the Stripe and DocuSign webhooks, checkout provisioning, an owner's close-account request and its skipped notice — and for the vendor-cost entry (`admin_ops.set_vendor_cost`). A stored request body keeps only the last four digits of a value under any key naming a phone (`admin_events._redact`), as the typed rows do. The trail, the offboarding checklist and the billing status history survive a restaurant's deletion.
- `status_bp` (`/admin/status/*`, whose writes post the public banner) is CSRF-protected and takes JSON object bodies only; its views take `auth.admin_required`, the console's own gate (since the integration wave, 9/29/26): support may read the incidents but never post the banner, the internal login's second factor is asked per state, the per-session request ceiling applies, and a refusal is admin_bp's (401 for a write and for `GET /admin/api/ops/state`; a 302 to the login for its GETs under `/admin/status/`).
- A JSON body that is not an object (`"x"`, `[1]`) is a 400 on every JSON blueprint (`security.json_object_guard`), never a 500.
- Side-effecting GETs are gone: `/logout`, `/admin/view-as/<id>`, `/admin/stop-viewing` and `/auth/not-me/<token>` ask on GET and act on POST; paid generation is POST only; `GET /admin/audits/new` only asks, and its POST creates the sales audit.
- **Operator sessions on owner routes**: an admin or support session is refused (400 `operator_session: true`) on the session-scoped owner writes that would otherwise land in the operator's own home restaurant — `/client/upload-data`, `/api/templates*` and `/api/import-tripadvisor` — unless it names the restaurant. The console has admin-scoped routes for each (`/admin/upload-data/<rid>`, `/admin/api/templates/<rid>`, `/admin/import-reviews/<rid>`).

## Tenant isolation

Identity comes from the session row, never the request. Owners switch locations only inside their group. Row access is `WHERE id=? AND restaurant_id=?`. A write by primary key alone on a tenant table follows an ownership check, and a new one that does not name `restaurant_id` fails `tests/test_tenant_scope.py` (`scripts/check_tenant_scope.py`, a ratchet on the 201 there were on 10/19/26 — SEC-16), and since the re-audit (10/20/26, R7-18) so does a new `SELECT ... FROM <tenant table> ... WHERE id=?` that does not name it (`tenant_scope_reads_baseline.json`, 125 reads held as found on 10/20/26 — the audit traced none crossing tenants); Postgres row-level security is the stronger guard, not on yet. Public pages use hashed or signed tokens (`/s/<token>`, issue links, `/join/<token>`, `/pay/<token>/<period>`, `/u/<token>`, `/staff/cal/<token>.ics`). The two staff link types are throttled per address on the portal's budget (`auth.portal_attempts`), answer a branded page or a bare 404 to an unknown token, and die when the holder is deactivated (read at every open, and ended durably by `staff_insights.expire_links_for`). A route that takes `<int:restaurant_id>` from the URL is `@admin_required` — never `@login_required` alone, which is any client login (`tests/test_staff_availability_scope.py` sweeps `admin_routes.py` for it). The legacy admin pages escape every tenant value they put into markup (one `fcEsc` / `fcNum` helper; `tests/test_fix_b1_admin_scoping.py` scans the template for an unescaped interpolation).

**Guest mail cannot spend the platform's sender reputation** (scale fix 10/19/26, SEC-02): a restaurant whose guest emails (newsletters and review requests) drew more than `GUEST_EMAIL_COMPLAINT_PAUSE_PCT` (0.1%) spam complaints or `GUEST_EMAIL_BOUNCE_PAUSE_PCT` (5%) bounces over 7 days, on at least 50 accepted, is paused until the window clears (`guest_email.guest_mail_paused`): a new newsletter is refused with the reason, a running one holds its recipients pending, a review-request email answers 409; the hit is captured once a day. `GUEST_FROM_EMAIL` moves guest mail to its own verified domain, apart from owners' sign-in codes and reset links (unset until Will verifies the domain in Resend).

**Security mail has its own lane** (re-audit 10/20/26, R7-10): every email goes through `emails.deliver` to one Resend team; bulk types (`emails.BULK_EMAIL_TYPES` — newsletters, review requests, digests, briefs, summaries, onboarding) take a slot from one shared bucket at `RESEND_BULK_PER_SECOND` (1.5, below the team's rate; `rate_bucket` `resend:bulk`, up to 30 s, then sent anyway), and security mail (`_SUPPRESSION_EXEMPT`: sign-in codes, resets, change notices) and operator mail never wait on it. The guest campaign's fleet bucket is on by default (`GUEST_SMS_FLEET_PER_SECOND` 4/s). The Resend plan's rate and the campaign's registered MPS are outside the code (Will).

**One tenant cannot spend the shared guest-text campaign** (scale fix 10/19/26, SEC-03): each restaurant's campaign texts share one database bucket at `GUEST_SMS_PER_SECOND` across all its campaigns and processes, and every campaign text one fleet bucket at `GUEST_SMS_FLEET_PER_SECOND` (`rate_bucket`; 4/s by default since R7-10 — set it from the campaign's registered rate); single texts — review requests, join confirmations — never take from them. A restaurant whose campaign texts drew more than `GUEST_SMS_STOP_PAUSE_PCT` (3%) STOPs over 7 days cannot start a new campaign until the week clears (`guest_marketing.stop_rate_pause`, captured once a day). A STOP still unsubscribes the number from every restaurant on the shared number, deliberately (consent). Per-tenant brand and campaign registration (Twilio ISV / TrustHub) is outside the code.

**Texts go only to North America** (scale fix 10/19/26, SEC-05; sign-in and staff verification codes too since 10/20/26, R7-09, each number at most `notify.OTP_SMS_PER_NUMBER_HOURLY` (8) codes an hour, and the owner's phone — where an account holder's codes are texted — refused on save unless it is such a number): every alert, staff and guest text passes `notify.sms_country_allowed` (`SMS_COUNTRY_CODES`, default `1`, exactly ten digits after it) in `notify.send_sms_result`, the one sender — anything else is logged `blocked` (`country_not_allowed`) and never reaches Twilio. The public join form refuses such a number before it writes anything (no unconsented contact, no request row), and its confirmation texts are capped across the fleet (`GUEST_JOIN_FLEET_HOURLY_CAP`, 300 an hour) and per restaurant (`GUEST_JOIN_RESTAURANT_DAILY_CAP`, 150 a day), each hit captured once an hour. Since the re-audit (10/20/26, R7-04) the fleet ceiling grows with the restaurants running Marketing (`GUEST_JOIN_FLEET_PER_RESTAURANT`, 6 an hour each, never below the floor), one restaurant's link may send at most `GUEST_JOIN_RESTAURANT_HOURLY_CAP` (40) an hour, and a restaurant inside its reserved share (`GUEST_JOIN_RESTAURANT_RESERVED`, 10 an hour) is never refused for the fleet's sake, so one public link's flood cannot close every restaurant's sign-up sheet. Twilio-side Geo-Permissions limited to US/CA are the outside half (Will).

A POS store may be bound to one live restaurant only (`models.pos_binding_conflict`): the admin saves for Toast, Square, Clover and RPOWER (400) and `rpower.bootstrap` refuse a store another live restaurant holds (demos exempt) — the operator's message names that restaurant. The owner's own connects refuse it too, 409, with a sentence that never names the other restaurant, which is another client's (`models.owner_pos_binding_refusal`): `POST /api/toast/save`, `/api/square/save`, `/api/clover/save`, and the app's `POST /mobile/api/connections/toast`, `/square`, `/clover`.

**Instagram & Facebook is the marketing logins'** (owner, 10/20/26: "all marketing ppl should be able to connect"): connect, the app's confirm and disconnect take `permissions.social_connect_refusal` — an account holder or a login holding `marketing.approve` (owner, client, manager), never a legacy member or an employee — because the connection is the restaurant's and the people who run its pages are often not the account holder (Simple EJ's Danny).

**Connect flows are bound to the login that started them** (scale fix round 10/19/26, SEC-09). A restaurant-only signed state let one tenant start "Connect Instagram", hand Meta's authorize URL to another tenant's owner and receive their Page. The web start sets an HttpOnly nonce cookie whose hash the state carries (`gmb.sign_bound_state`, `social_routes.nonce_bind`); the callback and the Page picker bind only in the browser holding it. The app's state names its login; the callback saves nothing and hands the app a sealed ticket that only that login, at that restaurant, confirms (`POST /mobile/api/connections/instagram/confirm`, the marketing logins). A Facebook Page or Instagram account bound to another live, non-demo restaurant is refused (`social_routes.page_conflict`, never naming it). Google Business's mobile flow is bound the same way since the re-audit (10/20/26, R7-16): the state names the login (`gmb.get_mobile_auth_url(rid, bind='u<id>')`), the callback stores nothing and hands the app a sealed ticket (`gmb.seal_connect_ticket`, 15 minutes) that only that login, at that restaurant, confirms (`POST /mobile/api/connections/google/confirm`, owner-only); a restaurant-only state is refused. The Place ID match still holds: another tenant's listing cannot be bound. App builds from before this round cannot finish a Google connect until updated.

**Website analytics is read only for the restaurant that owns it** (scale fix round 10/19/26, SEC-01). One Google service account reads every client's GA4 and Search Console, so "Cavnar AI can read it" proves nothing about whose it is. `external_bindings` holds one row per (provider, id, restaurant), `verified` or `pending`, and `web_analytics.sync` reads a source only when its row is verified for that restaurant (`web_analytics.ensure_ownership`; demo and simulated restaurants exempt). Proof is automatic when the property's own website is the restaurant's website, as fields only an admin sets name it — the Google listing's website (`google_place_id`, one Places Details read) or the menu URL (`web_analytics.trusted_hosts`): a Search Console site whose host is that host or the domain above it, a GA4 property with a web stream on it (Analytics Admin API). Anything else waits, unread, for an admin (`GET /admin/api/external-bindings`, `POST /admin/api/external-bindings/approve`, step-up, audited). An id already verified for another live restaurant is refused (409, `POST /api/web-analytics` and its app twin) with a sentence that never names the other restaurant; a pending row never blocks anyone. Every binding in place before the fix was recorded verified once at boot (`external_bindings.grandfather`, `data_migrations` `external_bindings_grandfather_v1`), duplicates named in its detail.

### POS credentials, store binding and POS data (Audit #23 F7, 10/21/26)

- **The RPOWER partner token is held once** (`credentials.pos_credentials`, sealed under `CREDENTIAL_KEY`, versioned). A restaurant keeps its store (`rpower_cg`, `rpower_store_mid`) and `rpower_credential_id`; `rpower._creds` resolves the token through the credential, reading the restaurant's legacy `rpower_token` only while the id is NULL, and never falling back to the row's copy for a store whose credential is revoked or unreadable. The admin save and bulk provisioning bind the credential (find-or-create by a digest of the token); at boot every row still on its own copy is bound (`credentials.bind_legacy_pos_tokens`, Simple EJ's and Will's demo mirror share one) and copies older than `credentials.LEGACY_TOKEN_KEEP_DAYS` are cleared. **Rotation is one step** — `POST /admin/rpower/credentials/<id>/rotate` checks the new token against RPOWER first (refused, 409, when it cannot see a bound store unless forced), re-seals it, bumps the version and clears the legacy copies; `/revoke` retires a leaked one. The request budget is keyed by the credential id (`rpower._bucket_key`), so a rotation keeps its bucket. Bulk provisioning admits at most `RPOWER_MAX_STORES_PER_CREDENTIAL` (500) live stores per credential until RPOWER states its limit.
- **Credential encryption fails closed on Railway** (`credentials.must_seal`): with `CREDENTIAL_KEY` missing or invalid a credential save raises `credentials.CredentialKeyError` (the RPOWER saves answer 503 with the reason), the boot pages (`credentials.key_problem_page`), a stored credential that decrypts to nothing pages hourly (`credentials.undecryptable`), and the RPOWER provider probe reports a credential that does not open as **failing**, never "unconfigured". A laptop with no key still stores plaintext.
- **One store, one live restaurant, in the database too**: partial unique indexes on `(rpower_cg, rpower_store_mid)`, `toast_restaurant_guid`, `square_location_id` and `clover_merchant_id` WHERE not a demo (`models.ensure_pos_binding_indexes`); making a demo real is refused (409) while another live restaurant holds one of its stores (`models.demo_binding_refusal`). **A demo reads a live RPOWER store only with the audited override** (`restaurants.pos_live_mirror`, `/admin/rpower/live-mirror/<id>`; Will's demo of Simple EJ's kept it at the migration); the simulated store (`demo-store:`) needs none.
- **A bulk-onboarded store is held for its owner** (`restaurants.pos_owner_hold`): every login of it reaches only the store check (`/api/pos/store-check` and its app twin — the store's name and serial number from RPOWER, five misses an hour, a keyed digest of the serial kept, never the serial), sign-out and its account basics (`auth._pos_owner_hold`, 403 `{pos_store_check}` or the check page); the archive keeps running. An admin who confirmed the owner another way releases it (`/admin/rpower/owner-check/<id>`). A list signed by RPOWER (`manifest_signature`, HMAC-SHA256 of the CSV under `RPOWER_MANIFEST_HMAC_KEY` — provisional until RPOWER names a format) holds nothing. ## Data at rest

## Outbound requests

**Error reports** (re-audit 10/20/26, R7-14): `ops.capture` hands Sentry the raw exception, so every event and breadcrumb passes `sentry_setup.scrub_event` / `scrub_breadcrumb` (`ai_guard.redact_secrets` over the exception values, the message, the request's URL, query string and data, and the extras; an event that cannot be scrubbed is dropped) and frame locals are never sent (`include_local_variables=False`). Only with `SENTRY_DSN` set.

Every outbound HTTP call names a timeout (`scripts/check_timeouts.py`). A request to an address someone else chose — a customer's webhook URL, a competitor's menu page, a link an admin pasted — goes through `net_safety.safe_get` / `safe_post`: the host is resolved ONCE, every address must be globally routable (private, loopback, link-local and cloud-metadata ranges are refused, `net_safety.vet` → `UnsafeURL`), the connection is made to the vetted IP with the real host as Host header and TLS name, and redirects are never followed (a caller that follows one passes each hop back through). Customer webhooks carry an event id and are delivered from a bounded pool; the test delivery is owner-only and queued.

## Inbound webhooks

Each provider's signature is checked before anything runs, and every failure is COUNTED per provider with the last verified event kept — `webhook_verifications` for Stripe and DocuSign (`webhook_routes._webhook_seen`), `inbound_webhook_health` for Resend and Twilio (`models.record_inbound_webhook`) — and captured to `ops.capture` at most once an hour per provider, so a rotated secret shows up as a failing count in the console instead of silent 403s. Stripe: the secret is read per request; unset → 401; bad signature → 400; event-id de-dup (`stripe_events_seen`) before any side effect; a failed billing write raises so the claim is released and Stripe redelivers. DocuSign: HMAC, 401. Resend: Svix signature with a 300-second timestamp window, 403. Twilio: `validate_twilio_signature` over the rebuilt https URL, fails closed without the token or header, 403 — for inbound texts and for `POST /webhooks/twilio/status` (delivery callbacks, which only move an `sms_log` row forward). Nothing throttles refused requests on these public routes yet (each writes one counter row).

## HTTP

- `Cache-Control: no-store` on `/api/`, `/mobile/api/`, `/admin` (JSON and pages), `/audit/r/`, `/staff/api/` and `/health` (`http_layer.add_cache_headers`): the admin payloads carry every owner's email and phone and sign-in IPs across the fleet, and a staff payload is one person's own.
- CSRF on every state-changing web request (`csrf.py`, the double-submit cookie; `csrf_protect` on the admin, client, audit and POS blueprints, `@csrf_required` per route on `auth_bp`, `staff_csrf_check` for the staff portal's cookie session); the mobile API and the staff app use bearer tokens.
- **A fair share of the request threads** (scale fix 10/19/26, SEC-07): every `login_required` / `mobile_login_required` request takes from its login's bucket (90, refilled 3 a second) and its restaurant's (300, 10 a second); the measured 10-second routes (`request_limits.HEAVY_PATHS`: the morning brief, good news, the publish review, web and phone) cost 5 and also take from a per-login heavy bucket (3 at once, then one every 5 seconds). Past it: 429 `{rate_limited, retry_after}` with `Retry-After`. Internal logins have their own ceiling. In memory, per process by design (one worker guarding its four threads); `REQUEST_LIMITS=0` switches it off. **The buckets bound starts, not how many run at once**, so since the re-audit (10/20/26, R7-02) every view also runs inside an **in-flight share** (`request_limits.run_counted`, from `login_required`, `mobile_login_required` and `staff_login_required` — a staff session is counted like a console login, start rate and in flight): a login never holds more than `REQUEST_THREADS`-1 threads; once the process is down to its last free thread it is held to `REQUEST_INFLIGHT_PER_LOGIN` (2); a restaurant's logins to `REQUEST_INFLIGHT_PER_RESTAURANT` (3); a login's heavy routes to `REQUEST_INFLIGHT_HEAVY_PER_LOGIN` (2) — heavy is `HEAVY_PATHS` plus any route `request_rollups` measured at 2 s or more over 7 days (`request_limits.measured_heavy_routes`, re-read every 10 minutes). A refusal is a 429 `{in_flight: true}`, Retry-After 1, made before the view ran, which the web (`_csrf_fetch.html`) and the app (`APIClient.perform`) send again up to three times after a short wait. A streamed answer gives its slot back when the view returns.
- **The in-memory limits are bounded and address-aware** (R7-15): a full store drops what is idle, then the least recently used (`request_limits._sweep`; it dropped the oldest-inserted half, so a flood of new addresses evicted the busiest live windows), an IPv6 address counts as its /64 everywhere a limit keys on an address (`request_limits.ip_key`, in `memory_limited` and the sign-in throttle's keys), and the sign-in limiter's fallback dict is pruned on every write and bounded (`auth_routes._LOGIN_ATTEMPTS_MAX_KEYS`).
- **Anonymous traffic is filtered before it writes** (SEC-08): the guest join form's and the staff availability page's per-IP limits, the marketing-link tap budget and the staff portal's flood check are in memory (`request_limits.memory_limited`) — `ai_utils.ai_rate_limited` wrote a row per allowed call — and a bad-signature webhook flood stops writing the health ledger after 30 a minute per address (`models._refused_flood`); the durable counters behind them are written only for traffic that gets through.
- Every response carries `X-Request-ID`; the access log and the JSON log carry the route RULE and the request id, never the raw path (paths carry reset and share tokens).
- **What the public `/health` shows**: `status` (ok / degraded / error), problem or error CODES (never exception text — the detail goes to the log), the write probe's state and milliseconds, the journal mode, database and WAL sizes, free and total disk and the two thresholds, the scheduler state and heartbeat age, backup and off-site ages, the names of overdue jobs, and the build's commit prefix. No tenant data, no keys, no host paths. It is unauthenticated because Railway's deploy check and an external monitor call it.

## Break-glass

For when the operator cannot get in. Each is audited; set, redeploy, confirm, then unset:
- **`LOGIN_UNLOCK_USERNAMES`** (comma-separated usernames): at every boot `security.apply_boot_unlocks` clears each name's account lock and every per-address lock (IP budgets are left alone). It checks that the name is a login (by username or email): a name that is none prints `NO login is named '<name>'` in the boot log — check the spelling — though the failure rows under that name are still cleared, and the `lockout_cleared_break_glass` event records `login_exists`.
- **`ADMIN_2FA_RESET_USERNAMES`**: at every boot `auth.apply_boot_two_factor_resets` turns off the named INTERNAL logins' own two-factor and deletes their backup codes and trusted devices, and alerts on Railway. It re-applies on every boot while set — unset it once you have enrolled again.
- **`python3 scripts/unlock_login.py <username>`** (in the container, `railway ssh --`; `--dry-run` shows the lock and changes nothing): clears one login's account lock and every per-address lock on it (`security.clear_account_lock`) without a redeploy, and records it in `admin_events` — no password, session or two-factor is touched.
- **The boot seed** (`auth.ensure_admin_login`): only when NO admin login exists at all — renaming the admin never re-arms it — with an `ADMIN_PASSWORD` that passes the policy, on its own "Cavnar AI Admin" restaurant row; the event is recorded and alerts on Railway.

## Who teaches the learners, and who reads memory

Memory audit, 9/29/26. What Cavnar AI learns about a restaurant changes what it tells the owner, so who may teach it is a control.

- **Whose answer it is**: `permissions.answer_authority(user)` — `admin` for an admin or support login, or anyone acting through a view-as (the session's `acting_admin_id`); `principal` for an account holder; `delegate` for a manager or employee. Every answer records it: `rec_ledger.record` derives it from the request's signed-in login when a caller does not pass it (`rec_ledger.request_authority`), so NULL is left only for a system answer (a job, a sync); an Ask confirm or dismiss records it too (`ask_cavnar_actions.authority`). A principal's answer is the restaurant's preference. A delegate's decline, hide or snooze silences only that login (`rec_silences`, at most 90 days) — on every surface that login is shown (`rec_ledger.present_many` and `silenced_keys(viewer=)`, the brief, Ask, the queue, pushes) — and trains only that delegate's own view (`rec_learning.effectiveness(viewer_id=)`: one manager's no never reshapes another's). A delegate's accept or Done closes the restaurant's episode. What pooled learning and the feature rows count is the restaurant's own answers (`rec_ledger.counts_for_restaurant`): never an admin's, never a delegate's decline. A delegate's goal is stored `proposed` until an account holder confirms it, and only an account holder ends one (`goals.end_goal`, 403 at the route). An admin's answer trains nothing: it changes no status or silence, and an admin's goal is only a proposal too.
- **View-as never teaches.** Support triaging a queue is not the owner deciding. Each learner leaves an admin's write out by its own marker: recommendation answers (`rec_events.authority`; the platform sync, the restaurant's ranking model, admin rates and the decisions history skip them); review approvals and skips (`support_approved` / `support_skipped`) and a draft edited through view-as (`reviews.draft_edited_via`, sticky until a fresh model draft) — out of reply style, edit learning and auto-approve trust (`models.reply_voice_sql`); the reprice ratio (`reprice_decisions.authority`); supplier-order corrections and supplier trust (`purchase_orders.authority`); marketing edits and the voice block (`marketing_edits.authority` / `via`); the win-back draft's starting text (principal senders only); the calendar angles the owner chose (`marketing.chosen_calendar_angles`); schedule saves (`schedule_versions.saved_authority` — an admin's week neither confirms nor reverses a pattern) and schedule suppressions (`schedule_recommendation_events.authority`); staff identity answers and person signals (`person_questions.answered_authority`, `person_signals.authority`); Ask's answer ratings (`ask_feedback.authority`, left out of the learning scorecard too); Ask chats, their notes and topics — a view-as chat is filed under the admin behind it and marked `ask_cavnar_conversations.via = 'view_as'` (`permissions.acting_login_id`), so it never reaches the owner's history, "often asks" or past chats, and a support rating is its own row, never the owner's; employee ratings (`staff_capabilities.authority` / `via` / `updated_by_user_id`, `capability_changes` likewise) — an admin's rating is shown and not counted in the Operational Score. A fact an admin saves to memory is labelled "Cavnar AI support" and filed under the admin, never the owner's words.
- **View-as reads.** Through view-as the reader is the admin behind it (`permissions.acting_login_id`): support does not read the owner's author-only memory lines (`memory_context.visible`), their Ask chats, notes or past conversations. Reading Account memory, Ask history or a conversation through view-as is recorded like a write (`admin_events` `view_as_read`: actor, login, path).
- **Owner-only lines never reach a shared output.** A memory line carries an audience: `team`, `principals` (personnel plans and money — `owner_memory.is_private` files such a remark there whatever the model asked and whoever said it: a pay rate, a raise, a PIP, a sale of the business, or a personnel action about a named person; only a person's own "Share with the team" in Account, `POST account/memory/audience`, makes it the team's) or `author` (one login's own). A line about several modules needs the view of every one of them, and a comps-and-voids line (module `loss`) needs `LOSS_VIEW`. An output with no login behind it (the weekly digest, an unattended Ask) is assembled as `memory_context.PRINCIPALS` — never one login's own line. The Account activity log every console login reads records a memory change's type and audience, never its words (`owner_memory.activity_detail`; older rows' text is not returned). `memory_context.visible` fails closed on an unknown audience. An output more than one login reads — the surfaces in `memory_context.SHARED_SURFACES`: the schedule draft, the labor, review, food and competitor reads, the review and food diagnoses, the reply drafter, marketing, the nightly report's narrative and the weekly plan — is assembled for the team viewer (`memory_context.TEAM`, `team_viewer(surface)`) whatever login asked: `team` lines only, a manager's module view (plus food cost for the food surfaces and the weekly plan), so no comps and voids. The Monday plan's whole run (its snapshot's decisions, last night's report, commitments and read tools) is projected through that viewer, and each plan item names its modules so the issue list hides a food-cost item from a login without Food Cost; the nightly narrative reads `decisions.context` as the team too. A new surface must be classified (`tests/test_mem_int_privacy.py`). The stored reads and claims of owner-level surfaces (the monthly review, the digest, the brief, the weekly plan, the nightly narrative — `ai_reads.OWNER_ONLY`) are served back to account holders only (audience `principals`, e.g. Ask's `read_recent_reads`). The outputs themselves are not all owner-only: the weekly plan and the nightly narrative are assembled for the team viewer (above), and the morning brief is built per login from what that login may see.
- **Demo, test and internal accounts teach no pooled learner**: `models.learning_eligible` (a demo; `exclude_from_learning`; internal billing; an account whose every login is internal; a test-pattern name — with the admin's `learning_override`). A demo or an account an admin excluded learns nothing, its own included (`models.learns_for_itself`); a test-named, internal or admin-home account learns only for itself, and a paying test-named account raises an admin issue. A converted demo's rows before its `learning_since` teach nothing (`INTELLIGENCE_ENGINE.md` → *Who may teach*).
- **What is pooled across restaurants** is what `public/privacy.html` says: de-identified ratios, pooled across at least five restaurants (`intelligence.privacy.MIN_COHORT`), counted by organisation, never a figure that identifies one. A Google-connected restaurant contributes no review-derived figure to anything pooled, the admin calibrations included (`intelligence/provenance.py`, Google API Limited Use).
