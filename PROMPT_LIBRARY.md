# Prompt Library — Cavnar AI

Every place a model call happens: which provider, which model, what it's asked to do, and what it's forbidden from doing. Every Anthropic call routes through `ai_utils.create_with_retry()` (budget check, retry with backoff, usage logging to `ai_usage`) — nothing calls `messages.create` directly. Perplexity is not an SDK call: the AI-visibility check posts to its REST endpoint with `requests` (`client_api.py`, `_do_ai_visibility_inner`), metered through the same `ai_usage` ledger.

The model for each call comes from one registry, `ai_utils.MODELS` (purpose → env override, default), read through `ai_utils.model_for(purpose)`; the client comes from `ai_utils.get_client()`, built on first use rather than at import. The table below is that registry; when a row changes, change both.

### Review analysis (`analyser.py`)
Model: Haiku. Input: one review's text + rating. Output: sentiment (positive/neutral/negative), category list, one-line summary, urgency (high/normal), **severity tier** (safety/legal/operational/service/minor), **`specific_complaint`** (≤8 words) and **`entities`** (dishes, staff roles, daypart, service mode). Deterministic-feeling by design — same review text should score the same way; the prompt does not ask for creative variation.

Every structured field is validated against an enum and dropped when it misses (`_validate_entities`, `_severity_floor`), for the same reason `categories` always was: an un-enumerated value is a cluster of one that no trend query will ever group with anything, and it would be shown to the owner as if it were one of ours. The entity fields carry explicit EXTRACTION RULES forbidding inference — a dish may not be inferred from a category, a role from a complaint, or a daypart from a rating. An absent field means the review did not say; it is never a gap to fill. `_severity_floor` also stops the tier contradicting the urgency that already fired on the same row. A review the model gave no tier is stored with NULL severity — **unclassified** everywhere (`analyser.UNCLASSIFIED`, counted in `severity_breakdown.unclassified` and each cluster's `unclassified`, sorted like `service` via `UNCLASSIFIED_RANKS_AS`); it used to be "minor" here and "service" in the clusters (H14).

**Safety disagreements (H5).** Once a review is analysed its urgency alone decides the health alert (`notify._is_health_alert`) — the negation reading is why the keyword list is only the fallback. `analyse_review` logs every review where `notify.HEALTH_KEYWORDS` fire but the model said normal (`notify.record_safety_disagreement` → `ops.capture` job `safety_disagreement`, no guest text; `notify.safety_disagreements(days)` counts them), and `models.auto_approve_candidates` never returns such a review — the rule that publishes unread does not bet on the model being right about the negation. That log is the evidence for judging Haiku against Sonnet here. **Code escalates where the model contradicts itself (R4):** `analyser._escalate_urgency` makes a review urgent when its severity is safety or legal, or when a strong health keyword (`STRONG_HEALTH_KEYWORDS` — "food poisoning", "health department", "hair in", not "hospital" or "mold") appears on a review of two stars or fewer; the result carries `urgency_escalated` and keeps the model's own `model_urgency`, which the disagreement log reads. `notify._is_health_alert` applies the same keyword rule to rows analysed before it.

### Review root-cause diagnosis (`review_intelligence.py`)
Model: Sonnet (`CLAUDE_REPORTER_MODEL`). Runs on a schedule (`scheduler.run_review_diagnoses`, 6am daily), never on a page load. Input: one complaint cluster (its reviews, their concentrations by dish/role/daypart/weekday, the guests' own complaint phrases) + what the other modules recorded over the same period + a fixed CAUSE VOCABULARY. Output: a likely operational cause, an alternative explanation, what would tell them apart, an action, an expected outcome, a confidence, and the review ids it rests on.

This is the module's answer to "why", and its guards are the point of it: `_validate_diagnosis` rejects any citation that was not in the prompt (the same discipline `verify_figures` applies to numbers — a root-cause paragraph is only worth more than a summary because the owner can click through to the reviews behind it), an unsourced figure (counts included) flags the result, and an empty cross-module block tells the model in so many words that it has no operational evidence. The prompt requires an alternative cause and a tiebreaker on every answer, because a single confident cause with nothing to weigh it against is the shape of a plausible guess.

**Code enforces what the prompt asks (H1, K6).** Each `operational_evidence` entry is kept only when its value is the line of the module it names (`_operational_lines` → `ai_guard.verify_operational_evidence`: every figure in the value to its written precision, or the value verbatim) and carries `verified: true`; the rest are dropped and captured — "Cross-checked against" never shows a figure the model wrote. **Since R1 the match is to a named field, not the line:** each module line is an `ai_guard.OperationalLine` carrying its named figures (labor %, understaffed/overstaffed days, waste $, posts, reach…; the target and window length are context), a value must carry a figure, every figure must be one of that module's fields and at least one a measured, non-zero one, the kept entry's metric and value are the fields' own labels (code's words, not the model's), and entries merge to ONE per module — padding, duplicates, a zero count or a template word ("understaffed", "target") never adds a cross-check. Stored rows are served through `ai_guard.served_operational_evidence` (verified, with a figure, one per module), so every reader counting the list counts distinct modules. A diagnosis naming a person its input never held (`ai_guard.unsupported_names`, R11) is refused whole and the previous one stands. The model's high/medium/low is stored as `model_confidence`; `confidence` is that band capped by `ai_guard.cap_band` — at most medium with no verified operational evidence, low with an unverified figure — and is never raised. `get_diagnoses` applies the same filter and cap to rows written before the check. The model's band is an input that can only lower evidence; the owner-facing confidence is built from data (the K1 object). **The guest's complaint phrase is fenced (H10):** `specific_complaint` is the analyser's extraction from guest text, so it goes in inside the UNTRUSTED fence like the excerpts, and a number in it verifies nothing.

### Review reply drafting (`drafter.py`)
Model: Sonnet (`DRAFTER_MODEL`). Input: the review + the restaurant's brand-voice fields (`voice_notes`, `sign_off_name`, `never_say`) + recent reply history (avoid repeating the same phrasing). Output: one draft reply. **Never** commits the restaurant to anything not already true. The prompt says so (a FACTS line on every rating; the 1–2★ length note asks for an apology and an invitation to get in touch, and no longer asks the model to "explain what will be done differently"), and `ai_guard.unsupported_commitments` checks the draft afterwards: actions taken ("I have spoken with our kitchen team"), actions promised ("we will be retraining the line", "going forward, every order will be…"), comps/credits/refunds ("a complimentary dinner on us") and named-staff discipline ("our manager has spoken to the server"), contractions included. A flagged draft is `draft_needs_review` and the auto-approve rule never publishes it. Since NS5 (9/24/26) the flag reason also comes from `ai_guard.public_reply_claims` (`reply_review_reason`): an allergen / free-from / "safe for" promise, an admission of fault or liability, an inspection or compliance claim, a comp or discount ("on me", "20 percent off", "buy you a drink", "your next glass is free"), "fixed / made sure / won't happen again / make it right / guarantee", a guest's private visit details, a sourcing claim ("made fresh daily", "organic") not in the owner's voice or menu notes, and an explanation nobody gave ("short-staffed, which caused…", "never happens on a normal night") unless its words are in the guest's review or the owner's notes. Auto-approve and bulk approve run `ai_guard.check_review_reply` (check_public_reply + those claims + commitments) on every reply; a 3★ review is an auto-approve candidate only when analysed with no specific complaint, severity minor or none, and not negative; allergy and undercooking terms are health keywords (`notify.HEALTH_KEYWORDS`, `_REACTION_RE`). An owner's edit (`client_api._do_save_draft`) is re-checked the same way — an edit no longer clears the flag — and the model's text is kept in `reviews.original_draft`.

**What the owner changes is fed back (ROI audit #40).** At a person's approval `models.record_reply_edit` compares `original_draft` with the approved reply (`reply_edits.compare`: a word edit distance, a category — unchanged / light / heavy / rewrite — and signals from a closed vocabulary: shortened, lengthened, removed/added exclamation marks, apology, invitation to come back) and stores them on the review. Two things read them, both deterministic: the few-shot examples (`models.get_approved_examples`) put a reply the owner EDITED first — their own words, where an unedited one is the model's — and the prompt gains an OWNER'S EDITS line (`reply_edits.style_note` over the last 12 edited approvals) naming only the signals at least half of them (and at least three) share, plus the length the owner leaves (the median approved word count), e.g. "they cut the draft down; they take out exclamation marks. The replies they approve run about 28 words." Nothing the owner or a guest wrote reaches the prompt through it — only the vocabulary. Fewer than three edited approvals: no line. What counts as the owner's edit is only a change the owner made (re-audit C11): a punctuation-only edit (every "!" taken out) is a light edit with its signal — the word distance alone read it as unchanged; a save that changes only whitespace is not an edit; a regenerated draft resets the edited flag with the original, so approving it as written records "unchanged"; and a rewrite Ask's model wrote at the owner's request (`edit_review_reply`, `client_api._do_save_draft(by_model=True)`) is a fresh model draft, never the owner's words. The few-shot block is bounded: each approved reply is cut to `drafter.EXAMPLE_REPLY_CHARS` (600) and the block stops before `drafter.EXAMPLES_BLOCK_CHARS` (2,400) — one 1,500-word approved reply used to put ~10k characters into every later draft's prompt. A saved reply is at most `client_api.REPLY_SAVE_MAX_CHARS` (4,096, Google's own limit).

### Food cost insight (`inventory.get_claude_insights`)
Model: Sonnet (`INVENTORY_INSIGHT_MODEL`). Framed as a restaurant CFO, not a waste consultant, and handed all five engines: `analyse_inventory`'s waste/overstock/reorder, `cogs.build_food_cost_pct` (food cost % against the restaurant's own target), `food_cost_intelligence`'s ranked cost drivers, the recipe-coverage and counted-vs-inferred trust block, the weekday and year-over-year patterns, what labor/reviews/marketing recorded over the same period, and the stored root-cause read.

The guards are the point of it: `_supported_savings_block` pre-computes every dollar the model may quote, the drivers arrive already ranked and the prompt is told not to re-rank them, a cause may only come from the ROOT-CAUSE READ block, a figure marked not-computable may not be estimated, and `verify_figures` appends an `UNVERIFIED:` marker rendered as a distinct caveat on both clients. Two checks now run on what comes back, deterministically: a **cause check** (`ai_guard.unsupported_causes` — a sentence with "because / due to / caused / driven by / led to / as a result of / thanks to" must carry the stored diagnosis's cause or a ranked driver; H2) and a **claim→fact binding** (`ai_guard.unbound_figures` over `inventory.food_insight_facts` — a sentence naming an ingredient may quote that item's own figures and the week's totals, never another item's; H3, the DSR narrative's `check_item` ported to prose). **No confidence in the read (R9):** the ROOT-CAUSE READ header carries no band, the Why sentence and the numbered lines are no longer asked for one (" — $240/month, low effort"), and any confidence the model writes anyway is removed (`ai_guard.rewrite_confidence_claims`) — the owner's figure is the computed one beside the line. Either failing adds to the same `UNVERIFIED:` line (`ai_guard.unverified_note`; figures alone keep the old "$145, 38%" form), which withholds the read's controls. The honest-zero path is real: *"If the data does not support a genuine, specific opportunity, say so plainly and write no recommendations at all."* The opening paragraph is prose; the numbered recommendations are the only numbered lines (the prompt used to forbid numbered lines and then ask for them).

**Money words (NS3 M6, 9/24/26).** The supported-figures block is "Dollar figures the data supports (opportunities and per-order differences — none of them is money already saved)"; an order row reads "$X less per order (a one-off difference per order, not a monthly figure) if N is ordered instead of repeating the last order of M" (it said "$X saved by ordering", and came back as "$168/month"); the recoverable line is "Recoverable (waste above tolerance — an opportunity projected from one week, not money saved)"; and each recommendation ends with its figure IN THE PERIOD IT IS GIVEN (" — $38 per order"), never converted to a month and never called saved. The CFO diagnosis's driver block (`food_cost_intelligence._drivers_block`) states a total only when every driver is one money kind; mixed drivers get a subtotal per kind (`totals_by_kind`: estimated cost already being spent vs opportunity) and the instruction never to add them.

One read per restaurant and prompt: `insight_store` keeps it keyed on a fingerprint of the prompt (every figure, the diagnosis, the date), so web and iOS show the same words and a new read is written only when the data changes. Each numbered line is a recommendation with a rec_ledger key (`insight_food:<hash of the line>`), logged as shown, with Done / Not for us / Track on both clients; an answered line is not shown again. The same holds for the Reviews read (`reviews` kind; the "Do today" line is `insight_review:<advice signature>` when it names one, else `insight_review:<hash>`, each diagnosis's action `diag_review:<category>`), the food diagnosis's action (`diag_food:<lead driver>`) and the Marketing read (`marketing` kind, `insight_marketing:<hash>`). A read carrying an UNVERIFIED flag (or, for Marketing, `figures_verified` false) offers no controls. The prompt carries the date of the stored diagnosis, never its age in hours, so the fingerprint holds across the day; the age reaches the clients as metadata. Lines the owner has already answered on that module (`insight_store.answered_lines`) go into the prompt under ALREADY ANSWERED — "do not suggest these again, in these words or any others" — so an answer holds when the read is reworded. Done silences for good; Track starts an `outcomes` tracker on the module's own metric (`strategy_routes.REC_TRACK_METRICS`) or, with nothing measurable, says it only hides the line; Intel offers no Track. Guest texts (`guest_marketing.draft_campaign_message`) are told never to invent an offer and are rejected when one appears that the owner's topic or menu notes do not contain (`invented_offers`).

### Food cost root-cause diagnosis (`food_cost_intelligence.py`)
Model: Sonnet (`CLAUDE_REPORTER_MODEL`). Scheduled (`scheduler.run_food_cost_diagnoses`, 06:00), never on a page load. Input: the ranked drivers with the dollars each carries, the food cost position, the prime-cost projection, the trust block, the weekday/seasonal patterns, the cross-module context, and a fixed CAUSE VOCABULARY. Output: a headline, a cause naming at least one given driver, an alternative explanation, what would tell them apart, a confidence, an action and an expected outcome.

`_validate_diagnosis` rejects a cause naming a driver it was not handed — the same discipline `verify_figures` applies to numbers — and an unsourced figure flags the result. An empty cross-module block tells the model in so many words that it has no operational evidence, because an empty block otherwise reads as "nothing notable happened" rather than "we have no data". As for reviews (H1, K6, R1): operational evidence is verified against the named fields of the one module line it names (`_operational_lines` → `OperationalLine`), merged one per module, and kept with `verified: true` or dropped — its Evidence Strength counts distinct corroborating modules, and the K1 input reads the CAPPED band; a person it was never handed refuses the diagnosis (R11); `model_confidence` is the model's band, `confidence` the band capped (medium without verified operational evidence, low with an unverified figure), never raised; `get_diagnosis` serves only verified entries.

### Labor AI insight (`labor.py` → Claude via `ai_utils`)
Model: Sonnet (`LABOR_INSIGHT_MODEL`). Input: the period's aggregated labor numbers (by day, by role) — never raw shift rows. Output: 2–4 sentences plus a short recommendations list. Every dollar/percentage figure named must trace back to a number `labor.py` actually computed; where the model states something it can't verify against the passed-in numbers, the response is expected to mark it `UNVERIFIED` rather than assert it plainly (see the real example: *"about $145 over target each day... UNVERIFIED: $145"* when the exact dollar figure wasn't in the aggregate passed to it).

**What Python decides, not the model (H8, H2, H3).** The single biggest opportunity is `labor.diagnose`'s lead driver, handed to the prompt as THE SINGLE BIGGEST OPPORTUNITY (or "none — say labor is on target"); the model phrases it and does not pick it. There is no FORECAST instruction: a FORECAST line the model writes anyway is removed, and `_labor_forecast_line` appends the computed one — this period's labor % carried forward with the measured move on the last comparable upload stated beside it — logged to `forecast_log` as `labor_week` once per ISO week (`insight_store.record_weekly_forecast`). After the call: small percentages are checked (the ≤10 skip is gone), each figure must belong to the weekday, date, role or person its sentence names (`labor_insight_facts` → `ai_guard.unbound_figures`), and a causal sentence must carry the diagnosis's cause (`unsupported_causes`); the prompt now says both. A name the prompt never held is flagged too (`unsupported_names`, R11), and the industry figures — now only the `benchmark_registry` entry for the restaurant's type (`industry_band_for`), none for a type the registry does not cover — bind only to a sentence that says "industry"; as a global figure it verified "Wednesday ran 36%" (R13). Anything failing lands in the one `UNVERIFIED:` line.

**The gap is an opportunity, never savings (NS3 C1, H4; 9/24/26).** The data line is "Opportunity (gap above target, not money saved): $X a month (the gap above target over the N days synced, projected to a month — an opportunity, never money already saved; say "could" or "at stake", never "saved")"; it was "Estimated monthly savings with optimized scheduling", and the model wrote "you saved $2,305 a month with Cavnar's scheduling". Below `MIN_DAYS_TO_EXTRAPOLATE` days WITH sales (`data_days`, not the calendar span) it states only the period's gap. "Overall labor cost: $X on $Y in sales" reads `costed_labor` — labor on the days with a sales figure, the pair of `total_sales` — so the stated ratio is the percentage beside it. Ask's LABOR context (`ask_cavnar._labor_gap_line`) says the same, and a short period states its gap rather than "$0".

Its three numbered lines are recommendations on the ledger now, exactly like Food's and Marketing's (ROI audit #25): `insight_labor:<hash of the line>`, presented on the `labor` surface by both routes, Done / Not for us / Track on each (web HTML controls; `insight_rec_keys` on iOS), an answered line left out, an UNVERIFIED read offering no controls. Lines the owner answered (`insight_labor`, `diag_labor`) go into the prompt under ALREADY ANSWERED, and the note's cache key (`labor.labor_note`) carries them, so an answer changes the next read rather than waiting for the data to move. The deterministic `labor.diagnose` step's check (`what_would_confirm`) is keyed `diag_labor:<driver>` (the weekday, the role, or overtime) and presented the same way.

### Schedule generation (`labor.generate_schedule`)
Model: Sonnet (`model_for("schedule")`), `max_tokens` 16000, thinking off. Input: one ranked PRIORITIES list at the top (1 hard constraints, 2 shift requirements and floors, 3 leadership, 4 the hours ceiling, 5 quality preferences — no other block claims a rank of its own); a SHIFT REQUIREMENTS table per date × daypart (people per role = max(owner floor, typical headcount), the day's hour target, the scorer's demand level and leader need, and the daypart-presence rule from `shift_quality.present_dayparts`); experienced/developing staff by name (`models.get_employee_tenure` + `staff_settings.experienced_names`, omitted when nobody qualifies), who is authorised to close, each person's usual days/dayparts (`models.get_prior_shift_pattern`); for a regeneration of chosen dates, the previous draft's named weaknesses (`focus`); all rendered by `schedule_requirements`. Then the roster grouped by role (active names only, from `staff_settings.roster`), availability and notes, approved and pending time off, the compliance rules and role floors (`schedule_rules.prompt_block`), the owner's dated events and reservations (`demand_signals.prompt_block`), pairings, reliability, what the manager keeps changing (`schedule_versions.prompt_block`), the demand profile and the hours budget (a ceiling, backed by a weekly revenue figure from the restaurant's own median week when it has one), sales per labor hour by daypart, what published weeks actually did by daypart, the rotation ledger and the multi-week ROTATION PLAN (`schedule_intel.rotation_block`), the SALES PER LABOR HOUR objective with each shift's target and the hours its usual sales carry (`schedule_economics.splh_objective_block`), for a restaurant with no history a BORROWED STARTING HEADCOUNT note with the borrowed figures marked in SHIFT REQUIREMENTS (`intelligence.staffing`), holiday lift measured here, stated and learned staff preferences, who could hold a station, the cohort's hours-per-$1k ratio, and a jurisdiction pack's starting values (worded "Starting values from the X pack (set in Cavnar, not a statement of the law)" — NS5 L13; the minors line lists each minor's age band and the limits the code checks, as starting values, not legal advice — NS5 H4). Output: `output_config` with `labor.SCHEDULE_SCHEMA` (rows plus a short `narrative`), with a CSV fallback when structured output is unavailable. Rosters over `schedule_engine.CHUNK_ROSTER_THRESHOLD`, or a response that stopped on `max_tokens`, are generated in two or three date slices and merged; each slice is told every person's hours, days, last shift, closes, weekend shifts and busy shifts so far. `schedule_engine._run_schedule_job` then repairs, backstops, sweeps the rules, fixes and grades the week. The "what changed" text the owner reads is `schedule_versions.diff` against the last published week — deterministic; the model's own note is shown separately, and since R10 each of its bullets passes `labor.schedule_note_problem` (the digest's line checks: no figure or count its prompt did not hold, no name outside it, no cause it does not state, no link or injection tell) or is dropped and captured (`schedule_note`).

### Competitor analysis (`competitor.py`)
Model: Haiku (`CLAUDE_MODEL`) for the two menu-extraction calls (a competitor's menu page or PDF into structured items); Sonnet (`CLAUDE_REPORTER_MODEL`) for the weekly comparative read. Input: this restaurant's and nearby competitors' Google Places data (rating, review count, category) and the extracted menus. Output: a short comparative read with **zero to three** recommendations — "Nothing worth acting on this week." is a correct answer (it used to be forced to exactly three). Every competitor review handed over carries an id (`R1`, `R2`, …, kept on the stored review as `ref`) and each recommendation must end with the ids it rests on (`[R2, R5]`); `competitor._validate_recommendation_citations` drops any line that cites nothing or an id it was never given, the same discipline review diagnoses apply to review ids. `competitor_intel_format.parse_competitor_intel` is the one parser every surface reads (`extract_recs` is a thin reader over it), and an insight carrying an `UNVERIFIED:` flag promotes no recommendations. Recommendations are keyed `insight_intel:<hash>` (`/api/intel/recs`). Since H11: a line that names a competitor may cite only that competitor's reviews (`_cites_about_named`) — an id that exists but belongs to another restaurant is a complaint pinned on the wrong place; the DOING WELL / DOING POORLY bullets must also end with their review ids and are dropped by the same rule (`_validate_bullets`, which then takes the ids off so the section reads as before); PRICE POSITIONING is no longer written by the model but computed from Google's price levels (`competitor.price_positioning`, withheld under two listed levels); and both menu extractions keep only items whose words — and, since R13, whose prices at any length — appear in the page or PDF text they were read from (`spot_check_menu`). **Only the review text is fenced (R8):** the ratings, review counts and price levels around it are Google's data, so the figure check can verify a true "4.5★, 812 reviews" and the UNVERIFIED flag means something. A strength/weakness bullet must share a content word with a review it cites (`_cites_support`, R13): "best patio [R3]" stood on a cold-coffee review. Never fabricates a competitor that wasn't actually returned by the Places API — see `project_gia_mia_places_testing` in memory: this codebase has previously fabricated competitor data by accident, and the fix was to make the prompt strictly grounded in the fetched snapshot rows.

### AI-visibility check (`client_api.py`'s `AIVIS_MODEL`, via Perplexity)
Model: `sonar`. Input: a fixed panel of realistic customer-style queries for the restaurant's cuisine/neighborhood. Output, per query: whether the restaurant was mentioned (`appeared`) and whether the query itself got answered at all (`answered`) — these are recorded separately so "the model didn't answer" is never conflated with "the model answered without mentioning us." Rate-limited server-side (see `ai_utils`'s comment: an earlier bug fired nine sonar queries a minute per restaurant, unmetered — fixed with staggered submission + logging).

### Marketing draft (`marketing.py`, `guest_marketing.py`)
Model: Sonnet (`MARKETING_MODEL`, `GUEST_MARKETING_MODEL`); the marketing *insight* card (`client_api._do_mkt_insight`) is Haiku (`CLAUDE_MODEL`), one stored read shared by web and iOS; its reach trend is claimed only across 4+ weeks of 2+ posts each moving 20%+, with no "strategy pivot" language. ### Ask Cavnar (`ask_cavnar.py`, `ask_cavnar_tools.py`)
Model: Sonnet (`ASK_CAVNAR_MODEL`), tool-calling enabled (`ask_with_tools`), `max_tokens` from the depth contract `_MAX_TOKENS` — brief 400 / standard 1200 / executive 4000, chosen from the question by `_depth_for`. The system prompt is a LIST of content blocks: static rules with a `cache_control` breakpoint, then the live snapshot (never interpolate per-restaurant data into the static block, or the cache stops hitting for everyone). Input: the full context snapshot (`build_context()` — identity, sibling locations, alerts, memory, per-module data the tier grants) + the filtered tool list for this restaurant's modules + conversation history (sanitized via `_sanitize_history`). System framing: an AI restaurant COO with direct data access, not a generic chatbot — encouraged to call tools rather than guess, required to mark anything it can't verify, and required to route any outside-effect action through a `write`-kind tool's proposal rather than claiming to have done it. See `MODULE_OVERVIEW.md`'s Ask Cavnar section for the tool-kind contract. **Legal, compliance, allergen and food-safety questions (NS5 M11)**: the static block tells the model its own knowledge stops there — call `read_schedule_rules` (the rules set in Cavnar, returned with a "starting values, not legal advice" note) and quote them as the rule set here, never as the law; hedge anything general; end with "check with counsel" (or the health department); never say "that's legal / you're compliant / that's safe" flatly, never OK a food-safety or allergen shortcut, never advise disciplining a named person. The deterministic check on the answer (A2 in the response-validation contract) belongs to `response_validation.py`.

**What an answer's figures may be checked against (H4).** The verification corpus is the snapshot, every tool result of the turn, and only those earlier assistant turns whose own check the server recorded as clean (`ask_answer_checks`: `record_answer_check` on every answer, `_verified_history` on the next). History comes back from the client, so an answer's invented figure used to verify the next answer that repeated it; and the owner's own words are never in the corpus — a figure the owner typed is not "from your data", so the model's echo of it is reported unverified. That includes the remembered facts (`_memory_context`), which sit inside an UNTRUSTED fence since R3 ("rent $8,200" was reported "checked against your data").

**What an answer's confidence is built from (R3, R5, R11).** The figure check runs with counts on. Evidence Strength counts the distinct, LIVE reads that back a figure the answer states (`_reads`: a repeated payload, a sample-only or empty one, or one backing none of its figures counts 0; a snapshot counts one per module it read live data for, and only those are `modules_consulted`), and the basis says "N of M figures checked" over the kinds the check reads only. A causal sentence must carry, in its cause clause, a cause the snapshot or a tool result states, and a name must be one it read; either is counted against evidence and returned in `meta`. The system prompt no longer asks the model to state its confidence ("Do NOT state a confidence of your own"); anything it writes anyway — "high confidence", "I'm about 85% sure" — is removed before the answer is recorded (`_finish`; the computed % is shown beside the answer, never stamped onto one sentence of it).

**The check is the Response Validation Layer (workstream A).** `_finish` runs `response_validation` twice over one context (`_validation_context`: typed facts from the tool JSON via `facts_from_dict`, the whole corpus as `context_text`, cause anchors from the corpus's cause-bearing sentences — a co-movement line as "association", the rest "likely" — the fenced guest/owner words as `untrusted`, `models.other_tenant_names` as `tenant_names_denied` less any name the restaurant's own data holds, `actions_done` = the direct actions the turn executed). Pass 1's findings are the flags (`_engine_flags`: F1–F8/X1 spans → `unverified_figures` / `unverified_all`, K1 → `unsupported_causes` as whole sentences, N1 → `unsupported_names`) the K1 confidence is measured from; pass 2, with that confidence, is what the owner reads: its rewrites go into the text (C1 certainty to the computed %, C2, F4 "saved" on an opportunity, K1 a cause lowered to its anchor, A1 "I've sent…" → "queued … for your OK"), its drops leave the text (T1 another tenant's name, A2 firing staff / food-safety shortcuts), and `meta` carries `validation` ({verdict, caveats, controls, codes, version}) and `validation_findings`. An answer with nothing left is replaced by `ASK_REFUSED_ANSWER`. Both Ask routes (web and mobile, streamed and not) pass `unsupported_causes`, `unsupported_names` and `validation` through `client_api._ask_meta`.

**Suggestions and ratings (ROI audit #48).** An answer's free-text advice is keyed WITHOUT a second model call: `ask_cavnar.extract_suggestions` reads the answer's own bulleted or numbered lines that start with an imperative verb from a closed list (`SUGGESTION_VERBS`), are 12–240 characters and carry no figure the answer's own check (`_meta` → `unverified_figures`) could not trace — at most three — and `record_suggestions` presents them on the `ask` surface as `ask_tip:<hash>` (the response's `suggestions`). Answers can be rated (`POST ask-cavnar/feedback`); the snapshot carries an ANSWER FEEDBACK line (`_feedback_context`: "N of M answers rated helpful" over 90 days, and the two latest "not helpful" notes inside an UNTRUSTED fence — the owner's words, never instructions). Built from SQL when the snapshot is built; nothing about it calls a model on load.

**The nightly DSR in Ask** (`dsr/memory.py`). The snapshot carries a `LAST NIGHT'S DAILY SALES REPORT` section — the latest final or provisional report of the last three nights: its headline figures by fact key (`sales.net 5,000 · labor.pct 27.1%`), what was missing, and the narrative's lead and actions — the facts plus the narrative, never a third prose document; the model is told to quote the report's figures, never recompute them. Four read tools, all `wants_viewer`: `read_dsr(date)` (one night: metrics per block, a capped detail, the verified summary as plain strings, the closer's words under `notes`; provisional / in-progress said so; the latest finished version while a rerun collects), `find_days(metric, op, value, start?, end?, limit?)` (indexed SQL over `dsr_metrics` — `labor.pct > 25` — with how many nights were measured; the metric is checked against what this restaurant recorded), `read_week(date)` and `read_period(date)` (`dsr.rollup` through `access.redact_grid`). **Redaction is the screen's**: every read goes through `dsr.access` for the asking login (`viewer_restaurant` stamps it as `_ask_dsr_user`; no login = the owner's view), so a manager never reads the budget, prime cost, comps/voids/refunds (without LOSS_VIEW) or food cost (without FOOD_COST_VIEW) — `find_days` refuses those metrics before looking them up, and the context cache key carries the DSR view, so an owner's snapshot is never served to a manager. `read_dsr` and `read_week` are public-text tools (the closer's words are fenced as untrusted, and direct actions are refused for the rest of the turn). Offered only where `dsr_enabled`.

### Daily Sales Report narrative (`dsr/narrative.py`)
Model: Sonnet (`DSR_NARRATIVE_MODEL`), `max_tokens` 3000 (real replies measured ~1,900; 1,600 truncated every one), a 60 s client timeout, `create_with_retry(retries=1)` — one request per night, retried once only on a transient provider failure — with `output_config` `json_schema` (`narrative.OUTPUT_SCHEMA`) so the provider holds the model to the shape. Usage is logged as action `dsr_narrative`. Called by the DSR pipeline as `narrative.write(ctx, facts)` → `{"ok", "narrative", "reason"}`; it never raises. Estimated cost ~$0.015–0.02 per restaurant-night (~2,500 input tokens, ~900 output at $2/$10 per million).

**No call** unless the sales block is ready with a measured figure **and** at least one more measured block (labor, food, reviews, marketing, intel) is: sales alone is the KPI strip in prose, and the manager's closeout never counts toward the floor. The owner-facing reason says which ("Not enough data tonight for a summary — sales are still syncing.").

Input, compact — never a dump: the night's metrics by fact key (`sales.net = 19,850.4`), comparisons already computed from them (`sales.net vs sales.net_last_week: +2,640.25, +15.3%`), what is missing and why, and — each inside an `ai_guard` UNTRUSTED fence — the detail lists (a list shows its size and first five entries), the manager's closeout, the last seven nights' executive summaries, open issues and `decisions.context` (both with loss issues left out: one narrative renders into the owner's and the manager's view), plus the DSR actions the owner already declined. System framing: a Director of Operations writing the owner's morning read, with seven numbered evidence rules. Output: `executive_summary` (2–3 sentences), `operations_summary` (optional, 2 sentences — the Manager DSR's opening: operations only, citing no `food.*`, `budget*`/`vs_budget*`, `prime_cost*`, comps/voids/refunds/loss key and naming none of them in words), `went_well[]`/`needs_attention[]` (≤4 each), `biggest_{risk,win,financial_opportunity,staffing_concern}`, `highest_priority_issue`, `largest_{money_saving,guest_experience,staffing}` (each OPTIONAL — left out, never `anyOf`-nullable: eight nullable singles made the API refuse the schema as "compiled grammar too large"; the schema with `operations_summary` was probed live on 9/23/26 and accepted), and `actions_tomorrow` (≤3: text, why, dollars_monthly, urgency, effort, kind, subject); every item carries `cites`, the fact keys it rests on.

The guards are deterministic and are the point of it:
- **The Response Validation Layer first (workstream A).** `check_item` runs `Facts.rv_check` on each item (and an action's why) as a whole line on surface `dsr` (unattended): facts are ONLY its cites (`Facts.rv_facts` — `kind_of`, a `vs_` key computed, a monthly / weekly key its period, anything else one night; a cited detail list's numbers as counts), the cites' measured components as likely anchors (so "drove" becomes "may have driven"), the closeout and review detail as untrusted, tenants denied. It replaces this module's injection, echo, cause (R5) and name (R11) checks and adds certainty, benchmark, tenant and unsafe-action rules; a drop on a non-figure rule gives the engine's reason in the old wording (`_rv_reason`), a drop on a figure rule gives the DSR's own trace / money reason when it has one. `_tolerance` and `_shingles` now call `ai_guard.precision_tolerance` / `shingles`; `_direction` stays the DSR's own (ai_guard's reader treats "to" as a filler). The rest of the list below stands.
- **Shape** (`narrative.validate`): a missing field, a field of the model's own, a fourth action, an off-list enum or a lead that is not 2–3 sentences refuses the whole answer — the same answer an obeyed injection would produce. Nothing is repaired.
- **Figures** (`narrative.check_item`, reading `ai_guard.figure_claims`): each cite must be a fact key of a ready block, and every number in the text must trace to the item's *own* cites — a value, a difference or percent change between two cited facts, one as a share of another, points between two percentages, or a figure/count in cited detail — within the precision it was written to (`$4,212` is ±0.50; `$4,200` may round to its zeros but never by more than 0.5%). "Up"/"down"/"above"/"below" must match the sign of the comparison (actual minus comparator). Dates must be the report's own, in M/D/YY; an ISO date is a failure. An action's `dollars_monthly` must equal a cited monthly figure — a night is never multiplied into a month.
- **Injection**: an action may not cite the closeout at all, the lead must rest on a measured figure outside it, and any line with a link, an email, an injection tell (`ai_guard.injection_residue`) or a six-word echo of the manager's or a guest's words is dropped.
- **The operations summary** (`narrative.check_operations_summary`): the lead's checks plus manager-safety — after the cites are completed, no cite the manager view hides and no owner-only topic in words. A failing one is dropped, never the narrative. `dsr.access.narrative_for` shows it as `executive_summary` (with `lead_from: "operations_summary"`) wherever the real lead is withheld, so the Manager DSR keeps an opening.
- A failing line is **dropped** and recorded in `narrative["verification"]["dropped"]` with why; a failing **executive summary refuses the whole narrative**. Drops reach the failure digest (`ops.capture`), so invented figures show up as a rate.
- **Estimates are named and counted apart (H13).** `narrative.is_estimate` marks a fact key as an estimate or forecast (`est_food_cost_pct`, `forecast_net`, anything projected). An estimate never counts as the measured figure an item must rest on (nor toward `can_write`'s floor), a line quoting a figure only an estimate backs must say "estimated"/"forecast", and `verification` carries `estimated` (kept lines citing one) and `measured` beside `kept`, so the footer's "traced to a measured fact" never covers an estimate.
- **Money kinds (NS3 C2, R1-R7, R13, R14; NS2 C2 — 9/24/26).** `narrative.kind_of` classifies every fact key: `recoverable|opportunity|potential|savings|at_stake` → opportunity, `budget|target|goal|plan` → plan, `est_`/estimate → estimate, forecast/projected → projection, a `vs_` variance → measured. Only measured facts carry a line (an opportunity may carry a hedged one; a plan only beside an estimate), count toward `can_write`, or count in the footer (`verification.by_kind` {measured, estimate, opportunity, plan}; `measured` is lines resting on measured facts alone). `money_claim_problem` drops, deterministically: saved/savings/recovered/"paid off"/"you made|kept" beside a $ figure unless hedged ("could be recovered") over an opportunity fact; "on pace/on track for/run rate/would be" unless a projection is cited; "together/combined/in total/add up" over more than one fact; a $ figure stated per month, week or year that no cited fact OF THAT PERIOD backs ("$84.50 a month" from one night's waste); an opportunity figure without could/at stake/recoverable; a plan figure not named as a budget or target; and a causal sentence whose figures trace to two blocks ("Net sales fell short because labor ran 34.8%"). `complete_cites` never adds a fact of a kind the model did not cite (a plan only when the words name it); an action's `dollars_monthly` is never a restaurant-wide monthly total (`RESTAURANT_WIDE_MONTHLY`) put on one `subject`. The slot `largest_money_saving` is retired (`RETIRED_SINGLES`; it put a $420 budget shortfall under "Largest saving") — the model writes `largest_opportunity` (worded as an opportunity), `biggest_win` cites measured facts only (`SLOT_KINDS`), and every narrative, stored ones included via `dsr.access.narrative_for`, carries `largest_money_saving: null`. Prompt rule 9 states all of this to the model.
- **Urgency is checked, effort is labelled (H13).** "before_service" (Today) stands only when a cited figure moved at least `URGENT_MIN_CHANGE_PCT` (10%) from the comparator it cites — `URGENT_MIN_POINTS` (2) for percentages — or a cited critical/urgent count is above zero (`check_urgency`); otherwise it becomes "this_week" with `urgency_adjusted` saying why. Effort stays the model's label, marked `effort_source: "model"`.
- **Causes and names are checked (R5, R11).** A cause ("because", "after", "drove", ", so guests …") must name, in its own clause, something a fact the line cites measures — a key's words or a name in a cited list (`Facts.cause_anchors`; prompt rule 8) — and a name must be one tonight's measured facts hold (`Facts.name_context`); spelled-out figures ("three thousand dollars") are normalised to digits before tracing (R7).
- **Urgency and confidence read only the supporting cites (R2).** `traced_cites` are the cites that back a figure the action's text or why states; `supporting_cites` adds the kind's home block. `urgency_basis` reads the supporting cites, and `action_confidence` counts the traced ones (the home block once when none is traced) — an unrelated moving pair or padding with more of the block's facts no longer makes an action "Today" or more confident.
- **Actions** the owner silenced or said "not for us" to (`rec_ledger.silenced_keys`, `decisions.history`) are dropped — and so is an action whose **advice signature** was declined on any surface (`insight_store.advice_signature`: "labor:day:tuesday" for Home's `trim_day:Tuesday` and for a DSR action cutting Tuesday's hours alike; each kept action carries its `advice_signature`; H16); the rest are ranked by `home_brief.order_recommendations` (urgency × dollars × ease) and keyed `dsr_action:<kind>:<block>[/<entity>]` — presented to `rec_ledger` when a reader is shown them (the report view on `dsr`, a delivered email on `dsr_email`; `narrative.ledger_items`), never when the narrative is written — the kind from a closed list, the block the action is about, an entity only when the model named one verbatim in a measured block's detail — so the same action on another night is the same recommendation however it is worded.

What it cannot rule out deterministically: a model that paraphrases an injected instruction into an action citing real, measured figures. The fence, rule 5, the closeout-cite ban and the echo check narrow that; an action is only ever a suggestion the owner answers — nothing it says is executed.

### Recipe drafts and recipe scan (`recipes.py`)
Model: Sonnet (`RECIPE_MODEL`). Two calls: a draft recipe (ingredients and quantities) for a dish that has none, accepted line by line by the owner; and OCR of a photographed recipe card into the same shape. Nothing is written until the owner accepts.

Units and yields are Python's (H6). ## Benchmarks, data floors and data age in prompts (workstream B, NS4 / NS6 §B)

- **One benchmark source.** Every outside figure a prompt carries comes from `benchmark_registry` by the restaurant's type, quoted with its source and year through `benchmark_registry.line()` (a published median as the source states it; Cavnar's band "set from it"; a rule of thumb called one; "type inferred from the restaurant's name" when Cavnar guessed). A type with no entry gets an explicit "Industry benchmark: none for this type of restaurant" (labor) or no line at all. The labor prompt's fixed full-service 33–36%, the food prompt's "industry target is 4-5%" and the digest's peer wording are gone; the waste 4–5% is "Cavnar's starting target, not an industry figure". Ask's snapshot carries a `PUBLISHED INDUSTRY BENCHMARKS FOR THIS TYPE OF RESTAURANT` block and the static prompt's BENCHMARKS AND COMPARISONS rule (a figure only from that block or a cohort line; otherwise "general industry knowledge, not measured here", no figure).
- **Comparison lines** (Ask context, the schedule's `_cohort_block`, `read_platform_intelligence`) are the Benchmark Engine's one wording, `engine.prompt_lines`: the peer group as the engine names it ("12 other Pizza on Cavnar", or "12 other restaurants on Cavnar, all types" — behaviour metrics only, never labor %, food cost % or hours per $1k — never "like yours"), how the group was chosen (same type, set by the owner or inferred from the name), "measured at k of m in the group", the band's as-of date and the comparison strength %. Bands are ≤ 8 weeks old, over ≥ 8 other restaurants, coarse-rounded (see `INTELLIGENCE_ENGINE.md`). Every figure in them is also a validation fact (`engine.facts`) that the surface registers, so B1 binds a claim to it; Ask's context and tools are projected by the login's module permissions.
- **Data floors — no call below them.** Reviews insight: no reviews, or fewer than `notify.MIN_TREND_REVIEWS_PER_WEEK` in the last 28 days → `client_api.review_insight_floor_payload` (fixed copy, `insufficient_data: true`, no recs; the web shows it as an empty state, iOS as plain text). Weekly digest: nothing measured this week in any module on → `DIGEST_NO_DATA_HEADLINE` with no call, and `scheduler.run_weekly_digests` sends nothing (`reporter.digest_has_data`). REVIEWS is a required digest line only when there were reviews; ACTION may be "none this week".
- **A missing measurement is never 0.** The reviews prompt says "lifetime average rating not measured"; the digest says "Average rating: not measured — no reviews this week" (was `0.0/5`); the food prompt says "Waste rate: NOT MEASURED … do not write 0%" when nothing was logged or nothing was purchased (was `0.0% … vs industry`).
- **Data window and age.** Labor insight and schedule prompts carry `labor.labor_window_line` (the dates, and "the last shift on file is N days before today", on the restaurant's own calendar; once `data_freshness.state_for("labor", age)` is not `current` it forbids "this week"/"today"/"currently" — the registry's rule since 9/24/26, `LABOR_FRESH_DAYS` is kept only as a candidate for cleanup); the digest's labor line carries its age, "older than this week" once not current, and counts as the week's data only while not stale (`reporter.labor_is_current` / `labor_is_usable`); the food prompt carries `inventory.food_prompt_data_lines` (the waste window — "Waste logged M/D/YY–M/D/YY", summed from dated waste events, never the cached rollup, with the newest waste entry and any undated typed-in figures named — and "N of M items counted in the last 7 days; oldest X": `count_stale` is each item's OWN count, the `ordering.count_freshness` rule, DH3-3; when no item is current the count is old before any order advice, when some are, those items are). The food read's `stale_sources` come from `data_freshness.source_state` for inventory, waste and purchases (`inventory.food_stale_sources`), not from the newest count. The deterministic "this week on stale data" check is response_validation's (V).
- **Missing inputs are stated.** The schedule prompt says `NO WEATHER FORECAST` / `NO DEMAND HISTORY` instead of omitting the block; `labor.schedule_note_problem` drops a note bullet about the weather when the marker is present. The "typically Fri/Sat for most restaurants" heuristic is gone (it backed notes as an anchor).
- **Labor recommendations are 0–3**, one per opportunity the figures show; "None — …" parses as zero recommendations (`client_api.parse_insight_sections`).
- **Marketing** names BEST/WEAK only over `MKT_BEST_WEAK_MIN_POSTS` (6) measured posts (under it the top and bottom three were the same posts), and with no results at all says "none measured yet" and forbids "worked/performed". The digest's "best post" needs `DIGEST_MKT_BEST_MIN_POSTS` (3) and states the count.
- **Reviews** read the competitor median only over `review_intelligence.MIN_BENCHMARK_COMPETITORS` (3), with its STALE flag in the prompt; revenue per star is `is_independent`-gated and names Luca (HBS, 2016).
- **The digest's guest snippet is fenced** (name and excerpt inside `wrap_untrusted`, the UNTRUSTED note at the top), and every digest line also runs `ai_guard.injection_residue` and the six-word `echoes` check against the reviews it quoted (`digest_line_problem(..., untrusted_shingles=)`).

## Response Validation

`response_validation.py` (layer 0: no database, clock, model or network) is the one deterministic check between what a model writes and what an owner or guest reads. It was built from the "Never Say" audit (9/24/26, NS1–NS6): the checks below existed in pieces (`ai_guard`) or only as prompt text, and each surface ran a different subset. **Status:** built by workstream V (the engine, its log, the admin read, the golden corpus) and adopted at **every model call site** by workstream A — see *Adoption* below; each call site's guards are now the engine plus the structural checks listed there.

```python
from response_validation import validate, validate_lines, ValidationContext, Fact, facts_from_dict, apply, log
v = validate(text, ValidationContext(restaurant_id=rid, surface="labor_insight", facts=[...],
                                     cause_anchors=[{"text": cause, "strength": "likely"}], confidence=k1))
v.text, v.verdict, v.findings, v.actions   # pass | caveat | withhold | refuse
```

- **Context.** `surface` (closed list: ask, review/food/labor/marketing insight, intel, review/food diagnosis, digest, dsr, weekly_plan, schedule_note, email_personalise, reply_public, guest_sms, social_post, calendar_idea), `audience` (owner / manager / guest_public / internal), `delivery` (interactive / unattended; digest, dsr, weekly_plan and email_personalise default unattended), typed `facts` (`Fact(key, value, unit, kind, period, entity, direction, as_of, data_days, source)`; kind measured / computed / estimate / opportunity / projection / plan / forecast / benchmark / price; a `None` value is a fact that was not measured and backs nothing), `untrusted` (guest and manager words — never a source, used for the echo check), `cause_anchors` with a strength (supported / likely / association), `names_allowed`, `tenant_names_denied`, `never_say`, `offer_source` (the owner's own menu/profile/offer text), `confidence` (the K1 object), `data_state` (`sample`, `stale_sources`, `partial_flags`, `required_disclosures`, `missing_inputs`, `data_age_days`, `as_of`), `policy` (`action`, `role_floors`, `keyholders`, `actions_done`, `must_start_with_if`, `check_counts`, `refuse_on_names`), and `context_text` — the prompt text, the legacy fallback while a site has no typed facts (the old presence check, F1/F3/X1/F8 only).
- **Kinds from keys.** `kind_of_key`: recoverable / opportunit / at_stake / potential / gap / savings → opportunity; budget / target / goal / plan → plan; est_ / estimat → estimate; forecast / project → projection; plus delivered / outcome → measured, vs_ / delta / change → computed, benchmark / industry / cohort / p25–p75 → benchmark, price → price. `facts_from_dict(d, kind_map, unit_map=, period_map=)` types a payload dict.
- **Rules** (codes are stable; each has golden cases in `tests/fixtures/validation_corpus/`):

| Code | What it enforces | Action (interactive / unattended) |
|---|---|---|
| F1 | a figure is one of the facts, to its written precision (the DSR tolerance; "about $1,200" may round to its zeros) | withhold / drop |
| F2 | a figure in a sentence naming an entity is that entity's (or a global) figure | withhold / drop |
| F3 | a money period matches the fact's both ways; a period-less fact gains no rate; "on pace" only on a projection; a night is never a month | withhold / drop |
| F4 | saved / recovered only on a delivered result; losing / wasted only on a measured one; an opportunity → "About $X a month is available (an opportunity, not money saved)"; an estimate → "could save about $X (an estimate)"; a budget stated as an actual, a forecast stated as what happened, "measured" on a non-measurement | rewrite, else withhold / drop |
| F5 | a figure that is a sum of facts of different kinds, or a "together" total that is not what it names | drop |
| F6 | an estimate quoted without "about"/"estimated" (inserted); a projection without its word ("(a projection)" appended) | rewrite |
| F7 | an annual or rate-scaled figure needs a projection label and ≥ 28 data days | rewrite, else withhold / drop |
| F8 | unit-typed: a % never backed by a bare "30 days" or a count | withhold / drop |
| C1 | certainty vs the K1 %: ≥ 75 "should", 50–74 "could", < 50 or unmeasured "might" (`HIGH_AT`/`MEDIUM_AT`); guaranteed / definitely / certainly / without a doubt / proves / ensures / 100% sure always go; always / never about an outcome → often / rarely; only ever lowered | rewrite |
| C2 | the model's own confidence ("I'm 90% sure", "high confidence") removed (`ai_guard.rewrite_confidence_claims`, without stamping the overall % onto one claim) | rewrite |
| K1 | the full connective list (because, due to, caused, drove, led to, since, when, after, following, once, with, is why, the reason, behind, responsible for, blame, triggered, explains, paid off, tied to, linked to, as a result, lifted, means …) may not state more than its anchor: too strong → rewritten down ("caused" → "may have contributed to"; association → "coincided with"); no anchor but a fact on each side → "moved together" wording ("while", "alongside", "in the same period that"); no anchor at all → caveat | rewrite / caveat / drop |
| X1 | a stated direction that disagrees with the fact's (one reader: `ai_guard.claimed_direction`) | caveat / drop |
| M1 | a required disclosure the text leaves out → its standard caveat; stale data read as "this week"; sample data → refuse | caveat / refuse |
| M2 | weather, demand, covers, reservations or guests/sales talked about when that input was missing | caveat / drop |
| B1 | a peer or industry claim, by grammar not a phrase list (Benchmarking audit 9/24/26, BM3-1): "industry average / band / median", "most [sports] bars", "similar / comparable / peer / typical &lt;group&gt;", "similar to yours", "like yours", "top / bottom quartile · quarter · half · decile · N%", "above the median for", "beats N% of", "best-in-class", "top performers", "area average" … binds to a benchmark fact FOR THE SAME MEASURE (labor, food cost, rating, replies …) or is not said. A figure no benchmark fact holds is dropped, interactive too (BM1-1). A Cavnar peer group (`source_kind` cohort, or the all-types group) needs n ≥ the fact's `min_n` (else 8); a published figure needs a source and a year, never an n. The all-types group is known by `restaurant_category` / `engine_kind` "platform", never its label: cited "N other restaurants on Cavnar, all types", and "like yours" / "similar to yours" on it (or on a published figure) is rewritten to the group's name. A bound claim is cited "(N other &lt;group&gt;, as of M/D/YY)" or "(source year)". A ranking word ("top quartile", "well above", "percentile") needs the fact's `strength_pct` ≥ 75: below it → "about the middle" / "about in line with" when the fact's standing says so, else caveat; a ranking the standing contradicts → caveat | rewrite / caveat / drop |
| P2 | "restaurants like / similar to yours reduced · cut · improved X by N%" needs a fact of kind "prediction" whose value matches N at its written precision with `source.n_restaurants` ≥ 5, else the sentence is dropped; "high likelihood" / "very likely" / "likely" in it are capped by the recommendation's own K1 level, never the effect size. The fact shape is in response_validation's docstring (the Restaurant DNA layer builds it) | drop / rewrite |
| N1 | a name the input never held | caveat / drop; a diagnosis refuses |
| T1 | another tenant's name; "a restaurant like yours runs X" | drop / refuse |
| A1 | "I've sent / posted / ordered / texted …" → "I've queued … for your OK" | rewrite |
| A2 | firing or disciplining staff, food-safety shortcuts, a cut below a role floor (`policy.role_floors`; a role with none is held to `policy.cut_floor_default`, the restaurant's "never cut below", else `CUT_FLOOR_DEFAULT` = 2 — never to one person) or of the only keyholder / closer, a flat "that's legal / you're compliant" | drop (legal: caveat / drop) |
| P1 | public text: allergen / free-from / "safe for", fault and responsibility, inspection / compliance, comps and discounts, "fixed / won't happen again / make it right / guarantee", awards and rankings, preparation or sourcing claims, private guest details, absolutes in a reply, the never-say list, links and contact details — unless the owner's own `offer_source` says it | refuse |
| I1 | injection residue, a model-written "UNVERIFIED:", a six-word echo of untrusted text on an unattended owner surface | drop (public: refuse) |

- **Severity → action.** info (log) · rewrite · caveat (`actions.caveats`, structured — never only the "UNVERIFIED:" string; `Verdict.text_with_caveats()` for a surface that cannot render them) · withhold (`actions.controls = False`) · drop (the sentence; the whole line under `validate_lines`) · refuse (`Verdict.text` is ""; the caller shows its fixed copy or the previous stored read). Unattended delivery turns anything above caveat into drop/refuse; public text turns anything above rewrite into refuse.
- **Properties** (tests): never adds a figure, never raises confidence, idempotent.
- **Mode.** `RESPONSE_VALIDATION_MODE` is JSON `{surface: "shadow"|"enforce", "*": …}`; default **enforce** everywhere (the rewrites only lower a claim; unattended and public text is where an unchecked sentence does most harm). `apply(text, ctx)` returns the text to show under the mode and logs the verdict; shadow shows the original.
- **Log.** `log(verdict, ctx)` → `ai_utils.log_validation` → `ai_validation_log` (created at boot). No answer or guest text: rule codes, counts, a hash of the original and each finding's offending token (≤ 60 chars; an echo stores none). Catch rates: `GET /admin/api/validation`.
- **Budget.** ≤ 10 ms p95 for an insight (≤ 8 KB of facts), ≤ 50 ms p95 for Ask; measured in `tests/test_response_validation.py`.
- **Hand-written copy** is covered by `scripts/check_owner_copy.py` (below), not by this engine.

### Adoption — every model call site (workstream A, 9/24/26)

Every call site validates after parsing and before it stores, caches, files, sends or returns: `rv.enforce(text, ctx)` (validate under the surface's mode, log, return the text as an `rv.Validated` str carrying `.validation`), or `rv.validate` / `rv.validate_lines` + `rv.log` for per-line and per-field surfaces. `tests/test_rv_adoption_source.py` fails any function that calls `create_with_retry` / `ask_with_tools` without running the engine, unless it is on its commented allowlist (analyser classification, recipes, invoices, sales-audit notes, the two competitor menu extractions, schedule rows) or relays a validated answer (the Ask routes). `tests/test_rv_probe_replay.py` replays the NS1–NS5 probes through the real call sites with a fake model client.

- **Facts.** Typed where the kind matters (money above all: recoverable / at stake / gap / potential → opportunity with its period and `data_days`; budget / target → plan; forecast / projected → projection; est_ → estimate; a delivered outcome → measured with `source="outcomes"`; benchmarks from `benchmark_registry.facts` / `cohort_facts`), the module's existing binding builder through `rv.entity_facts` (F2), and the prompt as `context_text`. **Hybrid mode:** a figure no typed fact holds but the prompt states is a fact with the old presence semantics, its kind read from the words in its own clause ("$867 a month above target (an opportunity)" → opportunity; cut at a neighbouring figure or a comparison), its period the one the prompt gave it — never less strict than the check it replaced. `policy={"context_facts": True}` reads a prompt-only context the same way (Ask's snapshot); `policy={"typed_only": True}` turns the fallback off.
- **Cause anchors and their strength.** A stored diagnosis's cause and a ranked driver are `likely`; an alternative cause and co-movement / operational-evidence lines are `association`; a recommended action is **never** an anchor (the digest used to anchor on it).
- **Other tenants.** `models.other_tenant_names(rid)` — every other restaurant's name and location name, never this one's own group (same `location_group` AND `owner_email`), generic names left out; cached per process, dropped on `models.on_restaurant_change` and after 5 minutes. - **The payload object.** `validation` = `{verdict, caveats, controls, codes, version}` (API_REFERENCE.md). ## Guardrails that apply to every call site

- **The figure check (`ai_guard.unsupported_figures` / `verify_figures`)** tests money and percentages of every size — values at or under 10 are held to their own written precision ("3%" is 2.5–3.5, "3.2%" is 3.15–3.25) instead of being skipped — and, with `check_counts=True` (the Reviews insight and diagnosis, the digest), a number counting reviews, guests, complaints, posts, covers, shifts and the like. Prose numbers ("the next 2 weeks", "top 3 ideas") are never counts.
- **Blind spots closed (R7).** `ai_guard.normalise_numbers` turns "45 percent", "three thousand dollars", "twenty-five percent" and "a dozen guests" into digits first; "up 7 points" is checked against the percentages and their differences; "3.1 out of 5" is a rating; review ids before a star ("4521 (2★)"), ISO dates and month-name dates are blanked from the context so they never back a figure; a money figure's stated period ("a week" vs the data's "this month") and a figure's stated direction ("fell to" vs the data's "up from") must match where the data states one.
- **Presence is not binding.** Where the facts are structured by entity (labor, food), `ai_guard.unbound_figures` holds each figure to the entity of ITS clause (or the nearest named before it), carries an entity into a following pronoun sentence and matches weekday abbreviations ("Wed") (R13); the DSR narrative's `check_item` holds each to its cites.
- **A model's confidence only lowers.** `ai_guard.cap_band` is the one rule: the model's band is capped by the evidence checks and never raised; it is stored apart (`model_confidence`) and never read as the confidence. No prompt asks a model for a confidence or hands it a model band (R9), no surface fakes a "medium" model band (Reviews Do-today and the Home intel card are flagged `inferred` instead), and a confidence a model writes anyway is rewritten to the computed figure or removed (`ai_guard.rewrite_confidence_claims`).
- **Causes are checked** (`ai_guard.unsupported_causes`) on the review, food, labor and marketing insights, the digest, the weekly plan, the schedule note, the DSR narrative and Ask (R5). Forward connectives (because, due to, driven by, thanks to, stemming from, attributable to, a move "after" something) put the cause after them and backward ones (led to, caused, hurt, which is why, contributed to, resulting in, drove, ", so guests …") before them; the anchor must be in THAT clause (`ai_guard.causal_clauses`), and a long anchor must share a third of its content words.
- **Names are checked** (`ai_guard.unsupported_names`) on the Reviews insight, the digest, both diagnoses, the labor read, the schedule note, the DSR and Ask (R11), including "Chef Marco", "server Tina", "Marco, the new weekend server", "Marco was rude" and "ask Marco".
- **Hand-written owner copy** is linted by `scripts/check_owner_copy.py` (a ratchet, like `check_email_tokens.py`, run by `tests/test_owner_copy_lint.py`): string literals in `emails.py`, `reporter.py`, `notify.py`, `strategy_jobs.py`, `milestones.py`, `value_delivered.py`, `sales_audit_cheatsheet.py`, Swift string literals and template / `public/` page text may not add a banned label (NS1 V7 / NS3 R9: "value delivered", "optimized", "typical restaurant", "claw back", "the one number", "grow your score", "not an estimate", "before they became problems", "will do better", "running on AI", "High/Medium/Low confidence", "Monthly/Annual savings" over a gap, "Saving vs. industry", "Largest saving", "THE PROMISE" …). It holds at its current count and fails on a new one; a line that must keep a phrase carries `owner-copy-ok`.
- **Forecasts a surface states are computed and logged** to `forecast_log` (`waste_week`, `profitability_month`, `labor_week`, `marketing_reach_week`, `review_rating_week`), never written by a model.

- **Budget enforced before the call fires** (`ai_utils.ai_budget_exceeded` / `global_monthly_budget`) — both a global monthly ceiling and a per-restaurant check for unpaid/trial accounts.
- **Retry with backoff, capped** (`create_with_retry`, default 2 retries, 1.5× backoff) — a transient API failure doesn't become a user-facing error immediately, but it also doesn't retry forever.
- **`temperature` is never passed** — the production Anthropic SDK build in use rejects it; `create_with_retry` strips it if present rather than letting the call 400.
- **Every call is logged** (`log_ai_usage` → `ai_usage` table: model, action, input/output tokens, estimated cost) — this is what the admin usage dashboard and the per-restaurant budget check both read.
- **Rate limiting** where a feature could be hammered (`ai_rate_limited`, keyed per restaurant+feature — and per USER for Ask Cavnar at 5/min, so an owner and an invited teammate don't throttle each other).
