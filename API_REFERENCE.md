# API Reference — Cavnar AI

This documents **patterns and resource groups**, not every individual route — there are 1,091 URL rules (1,000 unique paths) across the app (`python3 scripts/repo_inventory.py`, 9/29/26 after the memory round), and the specific handler is always one `grep` away once you know which file and prefix to look in. That lookup is intentionally cheap; re-deriving the whole route table from scratch every session is not. Use this file to answer "which file, which blueprint, which auth" before opening anything.

Every response carries `X-Request-ID` (an inbound `X-Request-ID` / `X-Railway-Request-Id` of 8–128 safe characters is echoed, else a new one) — quote it when reporting a failure; the logs are filterable by it. The outbound-webhook config routes (`GET/POST/DELETE /api/webhook`, `POST /api/webhook/test`) are in `client_bp`, not `webhook_bp`. `audit_app.py` is a separate standalone Flask app (the digital audit scorecard on :9000), not a blueprint. There is no web `/register` and no web `/me`; both exist only under `/mobile/api/` (and `/staff/api/me`). `hosted_dashboard` refuses to boot if two rules share a (path, method).

Two 409s a client may meet on writes. **`location_changed`**: the dashboard names the location a page was rendered for in `X-Cavnar-Restaurant-Id` (sent by `templates/_csrf_fetch.html` from the `cavnar-restaurant-id` meta tag); `auth.login_required` refuses a request whose id is not the session's current location, except `/api/switch-location` (DATA-10). A request without the header is unaffected. **Stale form**: a whole-form settings save (the phone profile save, both alert-settings saves) may carry `expected_version` — the `row_version` it loaded — and gets 409 with `current_version` if the row has moved on (`models.expected_version_from`, DATA-28); without it the save is last-write-wins as before.

## The `_m()` delegation pattern

59 of `client_bp`'s `/api/*` handlers are one line, and 100 are a bare `_m()` delegation once a docstring is set aside (counted 9/29/26; the rest own their body or share a `_do_*` with mobile — see *Which pattern to use* below):
```python
@client_bp.route("/api/ask-cavnar/opening")
@login_required
def ask_cavnar_opening(current_user):
    return _m("mobile_ask_opening")(current_user)
```
`_m(name)` looks up `mobile_api.<name>` and unwraps its `@mobile_login_required` decorator (`__wrapped__`), so the web route calls the exact same function body the iOS route calls — just with the already-resolved `current_user` from the web session instead of a decoded bearer token. **When a route's real logic isn't there, look in `mobile_api.py` first.** A genuinely web-only route (no iOS equivalent — e.g. CSV export, a desktop-only settings page) is one of the minority that doesn't delegate.

**Which pattern to use for a new endpoint both surfaces need.** Prefer a `strategy_routes._ROUTES` entry: one body, registered at both prefixes by the loop at the bottom of that file, with `_rid`/`_body`/`_principal` helpers. Second choice: a `_do_*` body in `client_api.py` called from both routes. Last: `_m()`. Never a third: 34 pairs still re-implement the same logic on both sides (885 lines, one of which has already diverged in its error handling), and each is a fix waiting to be missed on the other surface.

## Resource groups

### Account (`/api/account*`, `/mobile/api/account/*` — largest single group, ~36 mobile + ~26 client routes)
Profile, security (2FA setup/verify, backup codes, trusted devices, sessions list + revoke-others), team (invite/list/revoke — owner-role only), sign-in history, notification/alert-channel preferences, data export, billing status, marketing-email opt-out, timezone, connections status.

**Web/iOS account parity (9/25/26).**
- **Billing** — `GET /api/billing-info` and `GET /mobile/api/account/billing` are one body, `client_api._do_billing_info` (the `BILLING_PREVIEW_IDS` sample hook moved with it): `{ok, status, next_date, amount, interval, payment_method, portal_url, trial_end, invoices: [{date, amount, status, pdf_url}]}` — the web now has the last six invoices the app always had (Account → Billing → Recent invoices). Dates read M/D/YY (were M/D/YYYY). `{ok: false, reason: no_customer | no_key | stripe_error}` otherwise; a Stripe error's text is credential-redacted (`ai_guard.safe_error`) on both — the app's copy used to echo it raw. Scoped to the caller's restaurant's own `stripe_customer_id`. Since 9/29/26 every answer also carries `billing_status`, `pause_reason`, `paused_until` (M/D/YY) and `locked` (a hold the owner cannot resume); past-due, unpaid and paused subscriptions are listed, `portal_url` is returned whenever a Stripe customer exists, and a past-due account gets `past_due{hosted_invoice_url, amount_due, attempt_count, next_attempt}` and a `fix_url` (the invoice, else the card-update portal). A location covered by another location's subscription answers `{ok, status: "covered", billed_by{restaurant_id, name}, message, invoices: []}`. A login that is not the account holder gets 403 `{owner_only}`.
- **Email history** — `GET /api/email-history?limit=` (≤200): what was sent on the restaurant's behalf, each row with `sent_at` (UTC, what the phone parses), `sent_at_local` (the restaurant's own clock — what the web prints) and `label`; never a raw provider error.
- **Pause** — `GET /account/pause` (both prefixes) → `{ok, paused, paused_until, days, pause_reason, locked, lock_message, can_resume, can_pause}`; `POST /account/pause` `{days: 14|30|60}` → `{ok, paused_until, days}` (409 already paused or no subscription; 502 Stripe); `POST /account/resume` → `{ok}`, or **409 `{ok:false, locked:true, pause_reason, error}` for a hold** (a dispute, a refund or an admin pause — only an admin lifts it), 409 not paused, 502. (The web's billing-paused page does not yet know about holds: it offers Resume, which answers this 409.)
- **Close my account** — new web twin `POST /api/account/request-deletion` beside `POST /mobile/api/account/request-deletion`, one body (`client_api._do_request_account_deletion`): records `deletion_requested_at` for the caller's restaurant, emails Will once (not from a local backend — there the skip is recorded in the audit trail as `deletion.notice_skipped`), logs `deletion_requested`, and answers `{ok, requested_at, requested_on}` (`requested_on` is the date to show, M/D/YY on the restaurant's clock — the UTC stamp's own date reads a day late for an evening request); a repeat returns the first timestamp and sends nothing. Reachable with a lapsed subscription (billing-exempt, as the mobile route is). `GET /api/account-settings` adds `deletion_requested_at` (UTC stamp) and `deletion_requested_on` (M/D/YY, restaurant's clock) so the web card shows a request already on file. The web draws billing, Close my account, Manage alerts, the owner's email switches and the integration connect/disconnect buttons only for the account holder (`permissions.is_principal`, passed to the template as `is_principal`); another login sees a short owner-only note, and a `403 owner_only` from `/api/billing-info` reads as that note, never as "No active subscription". The web export picker lists `export_scopes` (`mobile_api.export_scopes_for`, the list iOS reads) and names any `refused` scope in its toast. The web card keeps the mailto to Will as a contact line.
- **Monthly review switch** — `GET /mobile/api/account` `account.monthly_review_enabled` (on unless off, as `/api/account-settings` reads it); iOS flips it through `POST /mobile/api/account/monthly-review` (`client_api._do_monthly_review_pref`, the web's `/api/account-settings/monthly-review` body).
- **iOS now uses** `morning-brief/settings` `briefing_level` (calm | normal | all — it always sends it), `issues/routing` (GET `{routing: {manager|escalation: {contact_id, name, phone, escalate_after_minutes}}, contacts: [{id, name, sms_consent}]}`; POST `{role, contact_id?}` — no `contact_id` clears) and `account/memory` + `account/memory/forget` — all existing `strategy_routes._ROUTES` twins (`account/memory` gained fields in the memory round, below).

**Memory round (9/29/26) — Account.** Every route here is a `strategy_routes._ROUTES` entry at `/api/…` and `/mobile/api/…` unless it says otherwise.
- **Memory.** `GET account/memory[?archive_before=<id>]` (`owner_memory.account_view`) → `{ok, facts, lanes, others_private, archived, archive_more}`. `facts[]` are the facts THIS login may read: `{id, fact, kind (constraint|context|preference|goal|followup), source, created_at, created_on (M/D/YY), author, author_id, audience (team|principals|author), modules, subject, valid_until, valid_until_label, due_on, due_label, origin, can_forget, worded_by ("Cavnar AI" for a note Ask's remember tool wrote in its own words), confirmed_by, confirmed_on (another login said it again), pinned, can_pin (an account holder), author_left (its author no longer has access)}` — draw "Only owners" for `principals` and "Just you" for `author`, and Forget only when `can_forget`. `lanes[]` `{kind, count, cap}` — `count` is the facts THIS login may read (re-audit R3; it counted every row) — caps `models.ASK_MEMORY_CAPS`: 30 constraints, 30 context, 30 preferences, 10 goals, 20 follow-ups, split by whose it is (DATABASE_SCHEMA.md → `ask_memory`); a write past a budget moves that bucket's least-used fact to the archive. `others_private` (account holders): how many private notes other logins keep — a count, never the text. `archived[]` — what left without anyone asking — `{id, fact, kind, author, reason (evicted|expired|retracted|forgotten|replaced|contradicted|author_left), reason_label ("its lane was full", "its date passed", "its review date passed — put it back if it still holds" for a sales-audit observation, …), archived_on, can_restore}`, only those the login may read — filtered before the page (30) is cut; `archive_more` true means `?archive_before=<last id>` reads the next page. `POST account/memory/add` now takes `{fact (≤300), kind?, modules?: [..], valid_until?, due_on?, audience?}` (and `replaces?`: the id or exact text of a note this one replaces — archived as `replaced`) → `{ok, fact, kind, audience, evicted, evicted_facts, similar: [{id, fact, kind}], replaced, confirmed}` — `similar` are notes this login can read that look like the same thing or its opposite (ask "does this replace …?" and post again with `replaces`); `confirmed` means another login had already said it and this one was stamped on theirs; an unknown kind is `context`, an audience that is not one of the three takes the default (a follow-up is its author's; an account holder's fact about letting someone go, pay or a sale is `principals`), and a fact the store refuses (a measurable target in ANY kind — "set it as a goal") is a 400 with the reason. `POST account/memory/restore` `{id, valid_until?, due_on?}` → `{ok, fact, valid_until, due_on}` puts an archived fact back, read from the archive by id with this login's filter (`owner_memory.restore`) — 400 without a numeric id or with a past date, 404 when this login cannot read it, 403 unless `can_restore` (an account holder, or the fact's own author); a date that has passed is cleared (a follow-up is due in a week) unless a new one is sent, and a departed login's note comes back as the restoring account holder's, owner-only. `POST account/memory/dismiss` `{id}` → `{ok}` lets an archived fact go for good (same checks). `POST account/memory/pin` `{id, pinned?}` → `{ok, pinned}` — account holders only (403), at most 10 pinned per kind (400); a pinned fact is never evicted. Re-audit 9/29/26 (R6, PEOPLE-13): `facts[]` also carry `scope` (org | location), `from_location` (another location's organisation-wide fact — `can_forget` and `can_pin` false there) and `can_set_scope`; the payload has `can_set_org`. `POST account/memory/add` takes `scope: "org"` and `POST account/memory/scope` `{id, scope: org | location}` → `{ok, id, scope}` moves one of this location's facts to every location or back — a group owner only (403 otherwise, 400 without an id and scope, 404 for a fact not kept here). `add` also returns `private_default` (true when the fact went to `principals` because it is personnel or money — `owner_memory.is_private`, for ANY author since the re-audit, PEOPLE-10). `POST account/memory/audience` `{id, audience: team|principals|author}` → `{ok, audience}` — the one-tap "Share with the team" beside an owners-only fact: 404 for a fact this login may not read, 403 unless it is the fact's author or an account holder (only its author may make it `author`). Memory changes are logged to the activity log as their type and audience, never their words (`owner_memory.activity_detail`).
- **Preferences.** `GET account/preferences` → `{ok, mine, location, can_apply_to_all, locations: [{id, name}], org_keys, unmutable_types, alert_types: [{type, label}], never_opened}`. `mine` is this login's own choices (`preferences.LOGIN_KEYS`: `push_enabled`, `push_muted_types`, `quiet_start`, `quiet_end`) plus `morning_brief` (whether they get this location's brief). `location` is each shared setting (`voice_notes`, `never_say`, `sign_off_name`, `briefing_level`, `morning_brief_enabled`, `morning_brief_hour`, `alert_quiet_start`, `alert_quiet_end`, `alert_max_per_day`) as `{value, source: "all locations" | "this location" | "default", set_at}`. `alert_types` is the checklist both clients draw (every labelled notification type except `unmutable_types` — `health`, `issue`, `issue_escalated`, `coverage`, `critical_low`). `never_opened` rows are `{alert_type, delivered, opened, days: 60}`: pushes delivered to this login's devices at least 10 times in 60 days and never opened by them. `POST account/preferences/mine` `{push_enabled?, push_muted_types?, quiet_start?, quiet_end?, morning_brief?}` — any console login, for itself only → `{ok, mine}`; an unmutable type is dropped from the mute list, quiet hours are `HH:MM` (400 otherwise). These only ever take a push away from that login's phone: the location's alert matrix, quiet hours and cap apply first (`push.fire_push` then applies each login's own overrides). `POST account/preferences/apply-to-all` `{keys: [..]}` makes this location's values of `keys` (`preferences.ORG_KEYS` — voice, never-say, sign-off, brief, digest, quiet hours, the alert switches and channels) the organisation's default and every location's → `{ok, keys, locations, skipped}`; 403 unless an account holder with LOCATION_SWITCH on a location in a group (`preferences.may_apply_to_all`); 400 with `skipped` when none of the keys may be applied.
- **Engagement, per login.** `GET /api/notifications/engagement` and `/mobile/api/notifications/engagement` (one body, `client_api._do_notifications_engagement`) → `{ok, suggestions, mine}`: `suggestions` is the restaurant-wide list it always was; `mine` is `never_opened` above with a `label` each — "You never open 5★ alerts on your phone — mute them just for you?" — and its action is `POST account/preferences/mine`, never the restaurant's setting.
- **Change history.** `GET /api/account/activity` and `/mobile/api/account/activity` (one body) add `changes: [{kind, field, subject, old_value, new_value, source, who, changed_at, line}]` (`change_log.for_viewer`, newest first, at most 100): `line` is the sentence to show — "Labor target: 30 → 28, by the owner on 9/12/26". Pay changes only for an account holder; the operator's learning switches (`exclude_from_learning`, `learning_override`, `is_demo`) never.
- **Targets.** `GET account/targets` adds `labor: {goal}` and `food: {goal}` — the active goal the module judges against while it holds (`owner_memory.target_for`), `{pct, label, until (ISO), until_label (M/D/YY), goal_id}` or null ("Your goal of 26% by 12/31/26 applies") — and `set_notes: {field: "Set by the owner on 9/12/26"}` for each of `labor_target_pct`, `food_cost_target`, `waste_target_pct`, `monthly_revenue_target`, `weekly_revenue_target`, `hourly_rate` the change log has a change for.
- **Trust.** `GET account/trust` adds `lapsed: [{scope, subject, lapsed_on (M/D/YY), reason, text}]` (the automations whose trust lapsed and has not been earned back — the owner is asked again), `schedule.undone_on` (M/D/YY, the last undo of an auto-publish); each `auto_approve.bands` entry adds `retracted`, `weak_credit`, `autoposted_clean` and either `earned_at` or `lapsed: {at, reason}`; each supplier adds `undone_at` and `clean_since_undo` (an undo of an automatic order means `ordering.ORDER_TRUST_MIN` clean orders after it before the supplier sends on its own again).
- **Policy notice.** `/api/home/brief`, `/mobile/api/home` and the group brief carry `policy_notice` — `policy_notice.notice_for`: `{key, updated_on (ISO), updated_label (M/D/YY), text, link_label, url, shown_until, shown_until_label, dismiss: {web, mobile}}` or null. Only an account holder sees it (never an admin's view-as), for `policy_notice.NOTICE_DAYS` (30) days from `POLICY_UPDATED_ON` (None until the date is set at ship, so null everywhere today). `POST account/policy-notice/dismiss` → `{ok, dismissed}`; 403 for anyone but the account holder. A dismissal is per login and holds on every device and location until a later change.

### Labor (`/api/labor*`, `/mobile/api/labor/*` — ~27 mobile + ~17 client)
Shift CSV upload, labor % + ribbon data, schedule generation/history/sharing, staff availability, staff contacts (for schedule delivery), Operational Score (`team`), scheduling profiles (demand levels), overtime/overstaffed-day detail.

**Schedule generation, review and publish** (both prefixes unless noted; bodies in `strategy_routes._ROUTES` except the first four):
- `POST /api/generate-schedule` / `POST /mobile/api/labor/generate-schedule` — ONE body (POST only since 9/25/26: a GET is not guarded by CSRF or view-as-read-only and this starts a paid job; a GET is 405) (`mobile_api.mobile_generate_schedule`; the web route calls it, 9/25/26) → `{job_id}` (needs `SCHEDULE_DRAFT`); **429** `{ok:false, error}` when rate-limited on both (the web copy used to answer 200); `week_start` from the body or the query string; returns `joined: true` when a generation for this restaurant is already running (`ops.active_job`) — poll that job. `GET …/schedule-status/<job_id>` → the finished payload: `preview_rows` (rows may carry `needs_review`/`review_reason`), `summary` (deterministic diff lines against the last published week), `narrative` (the model's own note), `quality` (each `shifts[].assignments[]` carries a `why` explanation), `review` `{hard, soft, by_kind, lines, hard_rows, fixes, unfixed}`, `rule_violations`, `pending_time_off`, `history_id`, `generation_seconds`, `chunked`, `roster`, `demand_by_date`, `learned_patterns`.
- `POST labor/schedule/score` `{rows, save?, history_id?}` → `{quality, violations, review}`; a save needs `SCHEDULE_DRAFT`, appends an `edited` version and writes `review_json`. A save of a PUBLISHED week tells nobody (F2-2, 9/25/26): it answers `unsent_changes` — the names whose shifts differ from what each was last told (`schedule_versions.unsent_changes`: the last `published` version, or for the two people in a later cover/swap that `swap` version); null when the week was never sent — and `late_change_warning` — a string when shifts changed inside the owner's `notice_days` window ("…the restaurant may owe the affected staff premium pay… check with counsel"; never a sum), else null (NS5 H2).
- `POST labor/schedule/violations` `{rows}` → `{violations, review, pending_time_off}` — re-check after an edit. `POST labor/schedule/apply-fixes` `{rows}` → `{rows, fixes, unfixed, quality, review}` — puts somebody legal on every hard breach; the owner still saves.
- `POST labor/publish-schedule` `{schedule_id, acknowledge?}` (needs `SCHEDULE_PUBLISH`). `schedule_id` is required (400 "Reload the schedule…" without it — it used to fall back to the newest row, maybe another week; F2-10). `acknowledge` is the list of blocker keys the client showed (`[key]`); a blocker not on it answers a new 409 (a bare `true` from an older client covers what the gate finds now; F2-9). The 409 is `{needs_ack, blockers[] (texts), blocker_keys[] (parallel), blocker_items[{key, text}], new_blockers[]}`. On a week already sent with `unsent_changes`, Send tells only those people (`client_api.send_schedule_changes`: same permission, gate and `send_delay_minutes` window — queued as delayed kind `schedule_changes_send`, voided if the week is saved again inside it) and answers `{changes_sent: true, sent, unreachable, failed}`; with none it answers `already_published`. A staff email is `sent` only when `deliver()` says ok — a failed one is in `failed` and its share row removed (F2-1). `week_label` is M/D/YY. → `409 {needs_ack, …}` until a human acknowledges (`client_api.publish_blockers`: NEEDS REVIEW rows, hard breaches, a weak or low-confidence quality verdict); on send stamps `published_at`/`published_by` and appends a `published` version. Friday auto-publish holds instead and tells the owner (`schedule_publish_held`).
  Since NS5 (9/24/26) the gate is `client_api.publish_review`, computed at send time: the rule sweep re-runs against today's data (time off approved after the draft, a floor, an age band) on top of the review saved with the week, plus `notice_short` against the notice rule. With a send delay the queued row stores the blocker KEYS the person acknowledged (`acknowledge: [keys]`); when it runs, a blocker not on that list holds it — `409`-shaped result `{needs_ack, blockers, new_blockers}` — and the owner is told (`schedule_publish_held`). Auto-publish (and its delayed run, payload `{schedule_id, automatic: true}`) is held by any blocker and by the soft flags `schedule_rules.HOLD_UNATTENDED` (meal break, daily overtime, unanswered time off); other soft flags are named in the `schedule_publish_pending` notice.
- `GET labor/schedule-history/<id>` also returns `economics` (the stored `economics_json`, `{}` for a week built before 9/26/26) and `projected_cost` — the rows priced as they stand now by `schedule_economics.priced_cost` (role rates, overtime from the 40h line per payroll week) — so a reopened week states its labor % and overtime like a fresh one (Schedule Studio).
- The page `GET /schedule/studio` is the dashboard opened on the Schedule Studio (same view as `/`; the template reads `request.path`).
- `GET labor/schedule-history/<id>/versions` → `{versions:[{version, reason: generated|edited|fixes|published, saved_by, changes, lines, score}], draft_vs_published}`.

## Admin console API (fix round, 9/29/26)

Every route here is `@admin_required` unless marked, CSRF-checked blueprint-wide, and audited by the request hook after the response (`admin_events`, source `audit`; typed actions add a `record_admin_action` row). Paths take `<rid>` = `<int:restaurant_id>`.

**The answers every admin route may give** (`auth.admin_required`, `auth.recent_auth_required`, `admin_ops.AdminBusy`):

| Status | Body | Meaning |
|---|---|---|
| 302 → `/login` | — | a page GET with no admin or support session (none, expired, or a client login's) |
| 401 | `{ok:false, error:"Your session expired — please log in again.", session_expired:true}` | the same, for a request that wants JSON (`auth._admin_wants_json`): any write, any GET under `/api/`, `/admin/api/` or `/mobile/api/`, and any request whose `Accept` prefers `application/json` — the console's `api()` sends that on every call (so `/admin/status/*` reads get the 401 too) and then sends the admin to sign in; or an enrolled internal login's session that never passed its second factor (the session is ended; `two_factor_required:true` too) |
| 403 | `{ok:false, error:"Support accounts are read-only."}` | a support login on any write except view-as and its own 2FA enrolment |
| 403 | `{ok:false, error, two_factor_required:true, enrol_url:"/admin/two-factor"}` | `ADMIN_REQUIRE_2FA=1` and this internal login has not enrolled (a page GET redirects there instead) |
| 403 | `{ok:false, reauth_required:true, reauth_url:"/admin/api/reauth", window_minutes:15, error}` | a step-up route and no password typed in 15 minutes: `POST /admin/api/reauth`, then send the action again |
| 429 | `{ok:false, error, rate_limited:true, retry_after}` + `Retry-After` | the per-session ceiling: 240 requests / 60 writes a minute |
| 503 | `{ok:false, busy:true, error, retry_after}` + `Retry-After`, `X-Admin-Busy: 1` | the fleet build (or a heavy analytics read) is already running with a waiter; retry after that many seconds |
| 503 | `{ok:false, error}` | the second-factor gate itself failed (fails closed) |
| 409 | `{ok:false, error, local_backend:true}` or `{ok:false, error}` | an action that would email, text, change Stripe or void a DocuSign envelope, refused on a backend where `scheduler.scheduling_allowed()` is false (the deliberate exceptions are in `docs/ops/SECURITY.md`) |
| 502 | `{ok:false, error}` (+ `reason`) | the provider (Resend, Twilio, Stripe, DocuSign) refused or failed — nothing claims it was sent |

A support login's `/admin/api/` JSON reads are masked (emails, phones, IPs, user agents, Stripe ids; on `admin_bp` and the sales-audit blueprint's `/admin/api/audits*`) and carry `X-Redacted: support`; the legacy HTML client pages (`/admin/client-settings/<rid>`, `/admin/client-data/<rid>`) answer support a 403 page that points at the console. **(step-up)** below marks a route that needs the password typed in the last 15 minutes (the 403 above). Every fleet payload says how fresh it is: `generated_at`, `cached`, `age_seconds`, `errors` / `query_errors` (a client page's own `errors` is its failure list; use `query_errors`), `unavailable`, `windows{tz, labels}` — a failed read is unknown, never zero. `?fresh=1` asks for a build no older than 5 seconds.

## Conventions

- **Success**: `jsonify(ok=True, ...)`, 200. **Failure**: `jsonify(ok=False, error=...)`, appropriate 4xx.
- **POST bodies**: `request.get_json() or {}` — never assume the body parses.
- **Side-effect emails/SMS**: every email sender returns an `emails.SendResult` and every text a result through `notify.send_sms_result`, logged against the restaurant (`email_log`, `sms_log`). A route whose PURPOSE is to send (a reset link, a resend, a test send, a recap, a pay link) answers from the real result — 200 with where it went, **502** with a sentence when the provider refused or failed, **409** when it was refused before sending (suppressed, on hold, covered, paying, or a backend that may not send) — never "sent" for a send that did not happen. A send that is a side effect of something else stays best-effort (`ops.capture()` on failure).
- **Status codes the guards use**: 401 `session_expired`; 403 `owner_only`, `read_only` (a support view-as), `reauth_required` (step-up), `two_factor_required` (admin enrolment); 409 `location_changed`, a stale form (`conflict` / `current_version`), a refusal with a sentence, `resolvable:false`; 429 `rate_limited` with `Retry-After`; 502 a provider failed; 503 `busy` with `Retry-After` (the admin console) or a gate that failed closed.
- **CSRF**: every state-changing web POST needs the CSRF token (`_csrf_fetch.html`'s helper attaches it automatically to `fetch()` calls in the dashboard's own JS).
- **Rate limiting**: Ask Cavnar is capped at 5/min per restaurant **and user** (`ai_utils.ai_rate_limited`, keyed on both); AI budget is also enforced globally and per-restaurant (`ai_budget_exceeded`) before any model call fires.
- **Streaming**: Ask Cavnar's chat endpoint is Server-Sent Events, with named progress labels per tool call (e.g. `"read_alerts": "Checking what needs you"`) sent before the tool result, so the client can show what's happening rather than a bare spinner.

## The `validation` object (Response Validation Layer, workstream A)

Every payload that carries model-written text now carries, beside it, the
engine's structured verdict on that text:

```json
"validation": {"verdict": "pass|caveat|withhold|refuse",
               "caveats": ["Some figures here aren't in your data: $4,300.", "..."],
               "controls": true,
               "codes": ["F1", "K1"],
               "version": "rv1"}
```

- `verdict` — `pass` (nothing found), `caveat` (the text stands; show the
  caveats beside it), `withhold` (show the text and the caveats, but no
  controls — no Done / Not for us / Track on its lines), `refuse` (the text
  was not shown; the payload carries the surface's fixed copy or previous read).
- `caveats` — owner-facing sentences, already worded; render them as given.
- `controls` — false whenever the verdict withholds or refuses.
- `codes` — the rule codes that fired (PROMPT_LIBRARY.md → Response
  Validation), including rewrites that were applied to the text.
- `version` — the engine version the text was validated under (a stored read
  is re-validated when it changes).

Until web and iOS read the object, the text keeps the legacy trailing
`UNVERIFIED: …` line whenever the verdict has a caveat or withholds controls;
its words are the caveats. The object appears on:
- **Food read** — `GET /api/inv-insight` (cached and stale paths too) and the mobile food analytics payload.
- **Labor read** — `GET /api/labor-insight` (cached and stale paths too) and all three mobile labor returns.
- **Reviews read** and **Marketing read** — their insight payloads (web and mobile). The Reviews read's
  `figures_verified` / `causes_verified` / `names_verified` now derive from the verdict's codes, and its
  Do-today controls also need `validation.controls`; the Marketing read's recommendations are offered only
  when `validation.controls` is true. Caveats with no flag of their own (a missing disclosure, a topic the
  data did not hold, a benchmark with no source) appear only in `validation.caveats`.
- **Intel** — the intel payload (`intel_recs_payload`, mobile `_do_mobile_intel`); the stored blob carries it.
- **Diagnoses** — each review / food diagnosis dict (merged over its fields).
- **Generated content** — `POST /api/generate-content` and `/mobile/api/marketing/generate-content` (`validation`
  beside `content`); `POST /mobile/api/guest-campaign/draft` and its web twin (`validation` beside
  `message`); regenerate-draft (`validation` beside `draft`, `needs_review`, `review_reason`).
- **Calendar ideas** — each kept idea carries its own `validation`.

**Ask** (`POST /api/ask-cavnar`, `/mobile/api/ask-cavnar`, both streams'
`answer` event): `validation` as above, plus `unsupported_causes` (the answer's
sentences whose cause nothing it read states — each client marks them in
place) and `unsupported_names` (names nothing it read holds), passed through
`client_api._ask_meta`. The text itself already carries the engine's rewrites
(certainty lowered to the computed %, "saved" on an opportunity re-worded, a
cause lowered to its anchor, "I've sent…" → "queued … for your OK") and its
drops (another restaurant's name, advice to fire staff or skip a food-safety
step); an answer with nothing left is replaced by a fixed sentence.

## Recommendation record (`strategy_routes._ROUTES`: each at `/api/…` and `/mobile/api/…`)

Restaurant-scoped and redacted per viewer (`rec_learning.viewer_sees`): a
login never sees a recommendation about a module it cannot open (food →
FOOD_COST_VIEW — a food kind filed under Home counts as food, and so does a
DSR action on the Food block), a loss recommendation without LOSS_VIEW
(`issues.viewer_sees_loss`), or an owner-only one (a DSR action resting on
budget, prime cost or loss figures) unless it is a principal. Counts,
rates and pages are computed after redaction.

- `GET recs/summary?days=30|90|180` → `{ok, days, since (YYYY-MM-DD, UTC),
  by_module: {<module>: {shown, answered, accepted, completed, implemented,
  dismissed, ignored, n, accept_rate, accept_rate_low, accept_rate_high,
  enough}}, by_tag: [{tag, label, module, modules, measured, improved,
  worsened, no_clear_change, unknown, success_rate, enough}], most_effective:
  {tag, label, module, modules, success_rate, measured, improved} | null,
  totals: {shown, settled, taken, open, measured, improved, taken_enough,
  measured_enough}, min_settled, min_measured}`.
  Episodes first shown in the window; superseded ones are not counted.
  `totals` is the #recs record strip: taken of `settled` (a rate only when
  `taken_enough`, settled ≥ 10), `improved` of `measured` (each change once;
  a rate only when `measured_enough`, measured ≥ 5), and `open` = shown −
  settled. Below a floor the page shows "—".
  `answered` = accepted + completed + implemented + dismissed (a taken
  episode whose change was made counts as implemented); `n` = answered +
  ignored (expired unanswered — **in the denominator**); `accept_rate` =
  (accepted + completed + implemented) ÷ n with a 90% Wilson interval;
  `enough` = n ≥ 10. `by_tag` is over taken episodes with a result:
  `measured` = improved + worsened + no_clear_change; `unknown` (not
  measurable, or discounted by the owner's check-in) is never in the
  denominator; `success_rate` = improved ÷ measured; `enough` = measured ≥
  5. One `by_tag` row per tag across every module it was recommended under
  (`module` = where most of its results came from; `modules` lists them),
  counting one result per change (one per tracker; on one metric, one per
  non-overlapping after-window); a result that faded or reversed at its
  re-check is `no_clear_change`, one the owner disowned or said conditions
  changed is `unknown` (`rec_learning.learned_verdict`, re-audit B9/B13).
  `most_effective` is the tag with `enough`, success ≥ 0.5 and the best
  lower 90% bound, carrying its own `improved` of `measured` — "most often
  followed by an improvement", not the cause of one. Any other `days` is a
  400.
